### 2.1 Process rules (how the step runs)

1. **The brief is saved verbatim in `10` and the lead lists what it asks, what the design already settled, and what it leaves open** (`09:28-30`). 2. **Open points that block the code are decided by the lead and recorded in `07` before or while the code is written; points that need the owner are listed in the report, not guessed silently** (`09:31-33`).
3. **Code is written complete: no placeholders, no `TODO`, no stubs that compile but do nothing. ### 2.2 Code rules (every crate)

15. **`#![forbid(unsafe_code)]` everywhere except `otap-sys`; there every `unsafe` block is minimal, Linux-only, opens with a `// SAFETY:` proof, the crate root keeps the inventory current; no `unsafe fn` anywhere** (`09:65-67`; E08 `07:178-181`). ### 2.3 Format and wire rules

31. **Changing a format or the wire** (`09:99-108`): (1) bump `FORMAT_MINOR` or `STREAM_MINOR` in `otap-format`; (2) write the new vectors into a new `tests/vectors/v2.<minor>/` with `cargo test -p otap-format -- --ignored write_golden_vectors --nocapture`, pin the printed hash, keep the previous directory so the N-1 lane keeps decoding it; (3) record the ruling (an F-ruling in the crate root for a layout, an S-rule in `07` for the wire) and the event in the log; (4) a reader must accept any minor of its own major and ignore reserved bytes on disk; on the wire reserved bits stay refused and new features are negotiated in `Hello`. Regenerating the current directory in place "was used once ... and is closed" (`09:110-111`; E05 `07:100-102`).
32. **The engine boots 2.3 pools only; a 2.2 pool is refused (`BootError::OldLayout`); no upgrade path exists because nothing was released** (E35 `07:1138-1146`; `06:490-491`). "Any later field takes bytes from `reserved` and bumps the minor again" (`07:1149-1150`). A format 2.4 for scope B would follow the same precedent (refuse 2.3 at boot, keep decoding the 2.3 vectors) unless the lead rules otherwise. E35 records the engine's refusal of older minors as "the exception" to `09`'s "any minor of its own major" rule (`07:1141-1144`), so a 2.4 refusal of 2.3 would be a second one to record. "2.3 pools only" held because 2.3 was the newest minor: the check is a minor below 3 (`crates/otap-cp/src/boot.rs:268-271`), so the precedent says nothing of the other direction, a 2.3 binary on a 2.4 pool, which the 2.3 boot accepts (section 4.6, "The forward direction").
33. **The F-rulings in force** (`crates/otap-format/src/lib.rs`): F1 superblock page 4 KiB, 20 KiB slot, `MAX_VOLS == 1024` (`73-81`); F2 map-entry packing `lseg:36 | off:16 | plen:12`, `lseg == 0` reserved, `addr == 0` is a hole with a non-zero birth and unmapped with a zero one (`82-92`); F3 stripe summary layout, "The on-disk stripe image is the chunk payload byte for byte; the 64-byte stream frame belongs to the transport and is never stored (R25)", a stripe is at most 8 MiB (`93-99`); F4 block kind `Data`/`Hole` per descriptor, stripe kind `Ingest | Relocate | Applied | Merge` in the header once (`100-102`); F5 CP numbers `u64` in headers and `u32` as `birth_cp`, `MAX_CP_SEQ`, CP 0 is mkfs so a zero birth means never written (`103-107`); F6 `cut_seq` and `cp_nonce` (`108-110`); F7 ring `A0 A1 B0 B1`, rank by `(owner_epoch, cp_seq, cut_seq)`, A wins a tie, a newer major is a hard error (`111-117`); F8 dense volume index below 1024 (`118-123`); F9 holes (`124-126`); F10 narrowings (`127-132`); F11 the Step 2 records (`134-150`); F12 the CP log is a directory of delta regions, a fold writes no delta region (`156-166`); F13 `SnapRootPage` (`167-171`); F14 the table regions: `map_roots` one `MapRoot` per volume index up to `vol_count`, `snap_table` in ascending id order, both padded to whole pages and sealed by the superblock's root reference (`172-179`); F15 the recorded geometry (`185-194`); F16 the catalogue: 512-byte records, canonical order, unique keys and names per scope, "A commit that changed no name carries the previous region forward unchanged" (`202-211`); F17 every commit lists the data stripes it wrote and the boot verifies them by summary CRC and identity (`212-220`); F18 `VOL_OFFLINE`, `page_entries` non-zero in any CP, `SegState::Relocated` and `reloc_index` stay reserved (`221-228`). Note: the section heading still reads "Format rulings (F1 to F15)" (`format/lib.rs:68`) although F16 to F18 follow and `BUILDING.md:35-36` and `06:96` say F1 to F18.
34. **The stream rules S1 to S10** (E06 `07:106-163`), all pinned by `stream_tests.rs` or `adversarial_stream_tests.rs`: S1 the header is the contract (kinds 1 to 12, codec flags only, `wire_len` and `raw_len` at most 8 MiB, `cp_seq <= MAX_CP_SEQ`, `base <= cp_seq`, no reserved bytes, so new kinds, codecs and flags are negotiated in `Hello` first) (`112-116`); S2 bodies are canonical, `chunk_idx` zero on every frame but a chunk, sparse ranges in a `HelloAck` sorted, disjoint, above `landed_contig`, inside `chunks` (`117-121`); S3 the builder refuses what the parser refuses and never clamps, `Cursor::to_page` returns a `Result` for this reason (`122-128`); S4 bounds: `MAX_DELTA_CHUNKS = 2^24`, `MAX_WIRE_RANGES = 4096` (a longer fragmentation is truncated, the chunks beyond are resent), `MAX_NAME_LEN = 255`, `CursorPage` keeps 500 ranges, `CREDIT_BYTES = 4096`, `INITIAL_GRANT_BYTES = 64 MiB`, `MAX_STAGING_BYTES = 2 GiB`, `MAX_CREDITS = 524,288` (`129-134`; the constants at `crates/otap-stream/src/cursor.rs:33`, `:37`, `:617` and `crates/otap-stream/src/flow.rs:17-23`); S5 decoder error semantics: a bad header poisons the decoder, a bad payload CRC consumes the frame and reports `PayloadCrc { kind, chunk_idx, cp_seq }`, "the receiver answers `Abort(Corrupt, idx)` for a chunk and `Abort(Corrupt, 0)` for anything else", `drain` never loses a decoded frame (`135-143`); S6 `DeltaBegin.bytes` and `DeltaEnd.bytes` are sums of the chunks' `raw_len` and never change under a codec; `DeltaEnd.digest` is BLAKE3 over the chunk images in index order (`144-148`; also `06:492-494`); S7 codecs negotiated, v1 sends raw payloads (`149-152`); S8 no sockets, the transport (`TlsTcp`, `FileSink`) is a consumer (`153-154`); S9 the error type is `#[non_exhaustive]` (`155-157`); S10 nothing proportional to an untrusted count is allocated before the count is checked, proved by a counting global allocator (`158-163`).
35. **The frame header lives in `otap-format`; a wire change is a `STREAM_MINOR` bump there** (E07 `07:169-172`).

### 2.4 Engine invariants the new code must not break

36. **The arena** (E16): layout 1.1/1.2, every transition one sealed-word store; re-attach "keeps `Placed` slots whose word and data verify (replayed in sequence order), drops `Filled` ones (never acknowledged), turns the dead process's reservations into `Committed`, takes the next sequence number as the maximum over every descriptor ..., and *reports* every slot it cannot trust ...; the engine treats any such report like a power loss" (`07:358-370`). Single writer: "Every arena method takes `&self` or `&mut self`; concurrent reactors in `dbladed` will partition the ring or go through an `otap-sys` cell type" (`07:375-379`).
37. **One generation per CP, one CP at a time**; a request on an idle engine still produces an empty CP; a clean shutdown cuts once more and commits `CleanShutdown`; a boot commits once before it serves (E17 `07:387-392`).
38. **On disk, in this order**: full data stripes (summary page first, `Ingest` kind, group 0), the metadata region, a pool flush, the superblock at `A` then `B`, each FUA; the map, the retired generation and the arena slots change only after `B` lands; a failed write fails the attempt and the generation is re-staged with a new nonce (E17 `07:393-398`).
39. **nvfail**: conservative mode by default; precise windows; `durable_active` is intersected when a slot is built, unioned by a landed intent or the `A` slot landing; `intent_seq_seen` is the highest intent whose completion was seen (E17 `07:399-421`).
40. **A dirty boot** is one whose selected CP is not `CleanShutdown` or whose boot rewound; it holds every volume in `boot_write_active` (`TornCp` after a rewind, `DirtyBoot` otherwise) "unless the arena re-attached whole and nothing was rewound" (E17 `07:422-429`). This is the rule scope A's re-attach rides on: a whole re-attach is what keeps the volumes online after `kill -9` (`smoke:271-276` asserts it).
41. **Durable before serving**: a runtime volume answers `NoSuchVolume` until `Event::VolumeCreated`; a clear keeps `NvFailed` until `Event::NvfailCleared`; a generation a client saw is never handed out twice (E17 `07:430-436`).
42. **Bounds**: volume sizes `1..=MAX_LBA + 1`; a request longer than `MAX_REQUEST_BLOCKS` (2,048) or than the arena answers `TooLarge` (E17 `07:437-442`); a punch is bounded by `MAX_PUNCH_BLOCKS` (262,144 blocks) (E23 `07:684-685`); a volume's index must fit a quarter of the pool and 4 GiB (`MetadataTooLarge`) (E22 `07:646-648`; `06:531-533`).
43. **Space**: `META_RESERVE_SEGMENTS` (2) is the floor no allocation crosses; metadata segments are recycled when CP `N` commits (every metadata segment naming neither `N` nor `N-1` nor a verified ring slot is freed); a CP that finds no segment fails, `is_pool_full` holds, writes answer `NoSpace`, reads are served, no CP until requested; a shutdown that cannot write stops without the clean marker (E17 `07:443-453`); every out-of-space failure of a CP, whoever placed the region, is a full pool; the metadata stream of a regular CP leaves `META_RESERVE_SEGMENTS` (2) free, a shutdown commit leaves one (the boot's), and a boot commit may take the last (E31 `07:950-953`); **a fold that fails for space is dropped**: the policy's folds wait, and snapshot requests wait, until more segments are free than there were at the failure; a shutdown's fold is retried at once as a plain CP so the clean marker still lands; a fold that failed because a map page it had to rewrite does not verify blocks every fold until the volume is repaired, `EngineError::MapDamaged` for new requests and `Event::SnapshotFailed` for the ones it held (E31 `07:953-960`); a sealed data segment whose live count reaches zero is freed after the same deferral as a metadata region, discarded under `WholeSegment` (E31 `07:963-966`); `reserve_for(n) = min(max(8, n / 12), n / 2)` kept from front-door writes, metadata may dip into it above the floor (E37 `07:1241-1248`); the admission rule (`07:1249-1255`); pacing 80% / 95% / 50 ms, reads never paced, the simulator runs `max_delay_ns = 0` (`07:1256-1262`); the full-pool pump, at most three CPs in a row (`07:1293-1300`).
44. **Arena damage while running** reads `Corrupt`; the stripe builder writes such a block under the recorded CRC and reports `Event::ArenaDamage` (E17 `07:454-458`).
45. **Flush-opaque backstores are trusted** under `TrustBarrierWithNvfail` (the default): the barrier stays where E17 put it, `OperatorWarning::FlushOpaqueTrusted`, every segment free deferred one more CP (`N+2`), nvfail quarantines after a power loss; `RequireFuaOrFlush` refuses (E21 `07:569-586`).
46. **The map** (E22): overlay first, then the page through a pba-keyed cache; every CP writes a delta region and a directory; a fold rewrites copy-on-write the pages the overlay and the CP's records touch, writes the indexes and roots of the volumes concerned, empties the directory, writes no delta region of its own; replay applies a delta region iff its CP is above the fold CP; `FoldPolicy` defaults 1 GiB, ten minutes, 1,024 CPs, 65,536 dirty pages, 8 million overlay entries; folds also on request, for a snapshot and at a clean shutdown (`07:627-648`).
47. **Holes**: a punch is one arena slot with a `HoleRecordBlock`, a `DirtyExtent` with `hole = true`, a `CpLogRec` hole with the CP as birth, never a stripe; "`diff` reports every entry born after the base, data or hole, including a hole punched over a block that was unmapped (a delta shipper punches zeros over zeros; 'what changed' is what the map knows)" (E23 `07:677-691`).
48. **The metadata stream and deferred frees** (E24): `MetaStream` packs every region back to back into whole stripes of the open metadata segment and into runs of adjacent free segments, on a copy of the segment table swapped in at commit; `data_live` and `meta_live` per segment; a region a CP stops referencing is released after the next CP commits (`N+1`, `N+2` flush-opaque); the boot CP's two segments protected for two commits; a segment whose discard is in flight stays allocated until the discard completes (`07:711-727`); a free that lands while a CP past its metadata preparation is in flight is re-applied to that CP's table copy (E31 `07:966-968`; lesson `08:786-788`).
49. **Snapshots** (E25): taken at the next CP, which the engine makes a fold; `SnapRootPage`; `Event::SnapshotCreated` at commit; `snapshot_read` through the pinned root; `snapshot_diff` and `live_diff` walk births above the snapshot's CP reading only pages whose `max_birth` says they may hold one; a snapshot pins what it references; a boot that rewinds below a snapshot's CP loses the snapshot (`07:746-760`); a snapshot request waits for the CP that carries the generation active when it was made (E31 `07:960-963`; `08:789-791`); the fold a snapshot rides can be dropped for space, in which case the request waits until more segments are free than at the failure, or blocked by a map page that does not verify, in which case the held requests get `Event::SnapshotFailed` and new ones `EngineError::MapDamaged` (E31 `07:953-960`; rule 43); the daemon waits for `SnapshotCreated` *or* `SnapshotFailed` (E38 `07:1338-1341`), and its `snapshot create` waits for its own uuid (E39 `07:1520-1521`).
50. **What a boot verifies** (E30, E35, E39): the stripes the list names, by summary CRC and identity with the nonce (`07:1131-1133`; F17); the directory's pages in every CP (`07:1133-1134`); under a trusted opaque barrier after an unclean stop every data block of those stripes against its descriptor CRC (`07:915-918`); a read error fails the boot (`BootError::Io`) to be retried, only a region that reads back and does not verify tears a candidate (`07:918-921`); a snapshot root page or pinned index that does not verify tears only when the candidate wrote it, otherwise `SnapshotDamaged` with reads and diffs refused and the data still pinned (`07:921-927`); a catalogue CRC failure drops the names (`OperatorWarning::CatalogDamaged`) while a read error still fails the candidate (`07:1482-1488`); the daemon probes the whole ring (`07:1489-1492`). Two gaps are recorded as limits and named Step 6 items: a block that already fails its CRC is relocated under its recorded CRC, and a rewritten snapshot root page is not listed as the CP's own (`06:515-523`; E39 `07:1523-1529`).
51. **Containment** (E32): a damaged map page answers `Corrupt`, the CP commits with the old entries unknown (bytes stay counted live, the safe direction), `OperatorWarning::MapPageDamaged`, folds stop until repaired (`07:984-990`); a volume's size is its root's and a configuration that disagrees refuses the boot (`VolumeSizeMismatch`) (`07:990-992`); `snapshot_diff` refuses a base that is not older than the snapshot (`SnapshotOrder`) (`07:994-995`); the front door answers the requests already decoded when it goes offline, clamps a zero high watermark to one, bounds the request size by the arena (`07:996-999`).
52. **The lifecycle** (E36): a deletion releases exactly what the snapshot alone referenced, judged against the *remaining* set with new snapshots included, `audit_liveness` checks it in every simulator recovery, pages are freed under one uniform rule, a damaged snapshot releases nothing (`07:1157-1180`). Pins: `PIN_USER`, `PIN_SCHEDULE`, `PIN_CLONE` are the operator's, `PIN_REPLICATION` marks the replication base; `delete_snapshot` refuses while any pin bit is set (`SnapshotPinned`, "unpin it or supersede the replication base"); `set_snapshot_pins` records a change for the next CP (`Event::SnapshotPinned`); "`set_replication_base(vol, Some(id))` sets the bit on the new base and clears it on the volume's previous base in the same CP, so a newer committed base supersedes the old one and the old one becomes deletable; `None` releases the base"; pins live in `SnapRecord::flags` (`07:1181-1190`). Limits: 255 user and scheduled snapshots (`MAX_USER_SNAPSHOTS`) and 16 replication baselines and divergent heads (`MAX_RESERVED_SNAPSHOTS`) per volume, pending requests counted (`SnapshotLimit`) (`07:1191-1194`). Rollback needs the volume offline and quiet, no newer snapshot, is done at a fold, bumps the generation, and "The CP refuses deltas of the volume" (`07:1195-1207`); grow online, shrink offline (`07:1208-1213`); volume deletion offline, quiet, no snapshots (`07:1214-1218`); offline is immediate and persisted; one pending operation per volume (`VolumeBusy`) (`07:1219-1225`).
53. **The cleaner** (E37, amended by E39): `plan_clean` runs when a CP job starts, never for the boot or shutdown commits, never while a snapshot deletion or a volume operation is pending, never while a map page is damaged (`07:1265-1268`); candidates by lowest live then oldest birth, below 80% live, excluding the open, protected, discarding, dead and uncleanable segments (`07:1271-1277`); the scan keeps only blocks whose `(vol, lba)` still maps to exactly this `(lseg, off)` in the live map or a snapshot; relocation stripes carry the old births and CRCs; snapshot trees are rewritten by `rewrite_pinned` with a new root page; `cp_stripes` lists every stripe; no relocation tables, "the map simply names the new address" (`07:1278-1292`). E39: a CP that carries clean targets takes no deletion and no volume operation and the next CP plans no clean while one is pending (`07:1435-1443`); rollback, resize and deletion refuse with `VolumeBusy` while a snapshot request of the volume waits or rides the CP in flight (`07:1444-1450`); "A summary of zeros is a stripe never written; anything else that does not parse skips the segment (`SkipReason::Summary`)" and a referenced count below the table's live count skips it too (`07:1451-1459`); `OutOfRange` is "not referenced" in the deletion's lookups (`07:1460-1466`); `rewrite_cost`, shared trees rewritten once, `clean_blocked_at`, `job_data_segments` freed at once on failure (`07:1467-1481`).
54. **The one-view rule** (the Step 5 lesson, now a rule): "Every decision a CP makes about shared state must be made against the same view, or refused until the view settles" (E39 `07:1530-1535`; `08:1018-1024`). Any new CP participant (a replication delta, an incremental table delta, a verify pass that reads the segment table) is bound by it.
55. **The daemon** (E38, amended by E39): one engine thread owns the `Engine` over `Box<dyn Backstore>` and a composite front door, ticks the engine and executes every control request between ticks, no lock around the engine (the index's own locks are E15's, uncontended on one thread; rule 83); a request that needs a CP ticks until its event within `--op-timeout` (120 s); requests whose durability has no event of their own (online and offline, a rename, a replication base) wait for quiet, request a CP and wait for its commit, except on a full pool, which never goes quiet on its own: there the CP is requested at once and the attempt's failure is the answer rather than a timeout (E39's closed hazard, "`pool sync` and `pool clean` on a full pool request the CP instead of waiting for a quiet the pool cannot reach, and answer the attempt's failure rather than a timeout", `07:1512-1515`; as built every such wait goes through `wait_quiet`, which returns at once when `is_pool_full()` holds, `crates/otap-daemon/src/pool.rs:558-566`, and `sync_now`, `:589-596`, then waits for `CpCommitted` or `CpFailed`, `wait_cp_outcome`, `:568-587`; a Step 6 request whose durability has no event of its own must go through `sync_now`, or a quiet wait of its own waits out `--op-timeout` on a full pool); one request at a time; idle backoff 200 µs to 2 ms (`07:1332-1351`). The events it waits on: `VolumeCreated`, `SnapshotCreated` or `SnapshotFailed`, `SnapshotDeleted`, `VolumeRolledBack`, `VolumeResized`, `VolumeDeleted`, `NvfailCleared`, `SnapshotPinned`, `CpCommitted`, `Stopped` (`07:1338-1341`). Devices on Linux are created and started on the engine thread for every online volume at boot and at `volume create` or `volume online`, taken down at `volume offline`, before a rollback, at `pool stop` and at exit (`ENODEV` while the engine drains, then `STOP_DEV` and `DEL_DEV`), recreated after a resize; `--no-ublk`; Windows never serves devices (`07:1352-1361`). `pool format` refuses a device that holds a pool, and anything but a blank device, without `--force` (`07:1362-1365`; E39 `07:1493-1494`); `pool boot` probes the ring, boots with no configured volumes, ticks until the boot commit is durable (`07:1365-1373`); file defaults and `--cp-interval` 1 to 15 s (`07:1373-1378`); every shutdown path ends in the engine's clean shutdown (`07:1379-1384`); the server rules (`07:1385-1395`); a non-loopback TCP control address is refused without `--allow-remote-control`, frames bounded at 4 MiB, idle connections closed after five minutes, a signal interrupts an operation's wait, `otapctl` waits ten minutes by default (E39 `07:1511-1522`); the daemon "holds no durable state at all beyond its command line" (`07:1406-1409`).
56. **The control protocol**: `Request` and `Response` internally tagged JSON (`op`, `kind`), `ControlError` with an `ErrorCode`, 4-byte little-endian length frames (`07:1320-1327`); list replies are struct variants and no report field is named `kind` (`07:1390-1395`; `08:871-877`); `deny_unknown_fields` on every request, reply and report (E39 `07:1499-1501`); the protocol test round-trips every variant (`07:1390-1391`). `otapctl` groups `daemon`, `pool`, `volume`, `snapshot`, `io`, exit 0/1/2/3 (`07:1396-1405`); a new `device` group follows the same shape.
57. **The front door** (E28): tags `Idle`, `Ready`, `InEngine`, `Aborted`; the decode and errno rules; "the request id is `generation << 32 | queue << 16 | tag`, the generation advancing at every completion or abort so a stale completion is dropped"; watermarks; a refused commit retires the tag; `MockTransport` drives all of it including abort, copy and commit failures (`07:836-848`). As built the generation starts at 0 in every process (`crates/otap-ublk/src/frontdoor.rs:208-215`, `:269`), so the id tells the uses of a tag apart within one process only; it is not the round-2 design's restart-stable `ReqId` (section 4.7). Kernel facts to keep (E28's words, `07:858-867`): `START_DEV` waits until every queue has a fetch on every tag; "a queue's commands must come from the task that issued its first fetch"; a read or write completes with its full byte count. The driver's rules behind the second fact (trap 38 has the lines): the queue is bound to the task whose fetch *completes* it (`ublk_mark_io_ready` sets `ubq_daemon = current` when `nr_io_ready == q_depth`, `ublk_drv.c:1621-1636`, `:1499-1502`); until then a fetch is accepted from any task that issues it on the device's `/dev/ublkcN` file, whatever its process (`:1706-1707` tests the task only once `ubq_daemon` is set; nothing on the `uring_cmd` path tests the process); from then on every command must come from the bound task (`:1706-1707`); and a request on a tag whose command another task issued is never served, because its task work either runs in that task and aborts it (`:1198-1207`, `:1121-1124`: requeued under `USER_RECOVERY`, ended with `EIO` without it, `:1090-1098`) or hands it to that task's ring, where only the bound task may commit it (`:1706-1707`). So the effective rule is that every fetch of a queue comes from the one task that serves it, which E28's "first fetch" says in effect; its wording is inexact only about which fetch binds (the completing one), which matters to a mock, not to the one-engine-thread daemon (E38 `07:1332-1336`). The mock must model these rules, not either shorthand (lessons `08:777-780` and `08:749-750`; section 4.10, item 12). The front door drops `UBLK_IO_F_FUA` by design (`06:558-560`; `crates/otap-ublk/src/lib.rs:31-33`). A mock of a kernel driver must follow the driver's rules (lesson `08:777-780`).

### 2.5 Build etiquette on the development PC

58. **Every cargo command is prefixed with `export PATH="$HOME/.cargo/bin:$HOME/.cargo/mingw-tools/bin:$PATH"` in Git Bash** (`09:118-122`; `06:387-389`; `BUILDING.md:190-196`).
59. **One cargo process at a time; the lead builds with `-j 3`, a worker with `-j 2`; tests run with `--test-threads=6`; never two heavy jobs at once, never a stress test in parallel with a build** (`09:123-125`; E10 `07:227-230`; `BUILDING.md:198-199`).
60. **A worker touches only its own files and runs only the test binaries it owns; it never runs a workspace-wide gate while the lead may be building** (`09:126-127`).
61. **The 10,000-case gate takes about three hours (180 minutes after Step 5), runs in the background with its output captured to a file, and nothing else uses cargo meanwhile; the simulator random walks are single property tests that more threads do not shorten and can be run as separate processes after one build; seeds differ per run, so the gate is repeated over time rather than treated as final once** (`09:130-140`; `06:568-573`; timings `06:399`).
62. **Scripted edits of source files are limited to one-line literal replacements, never with `|` as the perl delimiter when the pattern holds a `\|`, and `cargo check` runs right after; multi-line edits go through exact-match replace or a whole-block splice** (`09:141-145`; `08:998-1004`).
63. **The owner prefers the work done well over done fast: case counts are never trimmed and the review is never skipped** (`09:146-147`).
64. **Rust floor 1.89 (set by `crc-fast` 1.10.0 and `proptest` 1.12.0); the tree is built and tested with stable 1.99** (`BUILDING.md:40-42`; `06:101-103`; `Cargo.toml:35`).

### 2.6 Design rulings and plan rows that bind the four scopes

65. **R25** (`05:393`): "`otap-stream` v1 freezes the 64-byte frame, the record kinds, the cursor and the credit semantics and treats the payload as opaque bytes with a CRC. `otap-format` v2 freezes the stripe image ... as the only chunk payload ... A chunk is re-derivable from disk by `(lseg, stripe_idx)`; chunk-aligned resume is the contract; the delta's segments are GC-pinned from `describe()` to `DeltaEnd`."

"Any later resend reads the stripe back through `DeltaSource::read_chunk` under `MediaProfile.ship_readback` (default `cache`; the shipper never issues I/O to the HDD pool itself). `Landed` credits govern flow only and are units of free receiver staging. 70. **R57** (`05:457`): "A `dbladed` package upgrade is the supervised restart through `USER_RECOVERY` with the same 2 s target and 5 s hard budget as a crash. ... No release writes a format that N-1 cannot read until the operator runs `otapctl format upgrade`." The timer table row (`05:505`): "| Daemon restart (C) | 2 s target, 5 s hard | `USER_RECOVERY` and `REISSUE`; no holder process |". What the 5 s hard budget binds: the row directly above it is the watchdog's, "| Watchdog (C) | 5 s, pet 500 ms, data-path check-ins | kernel command line as R16 |" (`05:504`), and the profile arms "`softdog soft_margin=5` without `soft_panic`; watchdog pet 500 ms" (`05:546`), so the restart's hard budget is the watchdog's margin; round 2, which `06:84` keeps standing, ties the two: "The budget is 2 s target and 5 s hard, and a supervised restart suspends the watchdog's worker check-ins so the restart does not become an 8 s fence" (`docs/03-architecture-brainstorm-02.md:22`); and 6.7 promises the owner, for a "Daemon crash or package upgrade of `dbladed`" in Phase C, "2 s target, 5 s hard; zero acknowledged writes lost" (`05:567`). R57's last sentence is the rule a format 2.4 meets in the forward direction (section 4.6). 74. **The 7.7 invariants every crate's property tests encode** (`05:832-845`): #1 "no acknowledged write is lost across a daemon re-attach" (`05:834`); #2 "`diff(base)` over the map equals the union of CP write sets for `cp > base` with later writes winning, over random snapshot pairs including discards, resizes and GC between the pair" (`05:835`); #3 every byte under a CRC, encode-decode-re-encode byte-identical, N decodes N-1 (`05:836`); #5 "A torn superblock or data stripe falls back to CP N-1 intact; a torn CP on a `flush-opaque` backstore falls back to N-2 intact (dm-flakey)" (`05:838`); #6 "A dirty boot engages nvfail for exactly the checker's set of volumes with unflushed acknowledged writes; a clean shutdown never trips it; a volume idle for two CPs never appears in precise mode" (`05:839`); #8 "The replica is at a sender CP boundary after every `Committed`; a BLAKE3 over the pinned root at a common CP is equal on both sides; a `DeltaBegin` with a known `cp_seq` and a different `cp_id` discards exactly one partial; duplicate applies equal zero and resends equal the duplicate count (the loopback harness)" (`05:841`); #9 "Every snapshot retained on the sender and younger than the base exists on the receiver with identical content after catch-up (ordered increments)" (`05:842`). As built, #5 is E21's `N+2` deferral and the boot's rewind (rules 45, 48, 50) and #6 is E17's dirty boot and nvfail (rules 39, 40); #4 (`05:837`, the dm-log-writes proof of stripe-aligned bios) belongs to the lane rule 80 describes and is not built; scope A's re-attach tests answer #1 and #6, scope B's verify meets #5 as the designed fall-back (sections 3.A, 3.B). The other four, and why they bind or not: #7 (`05:840`, a held promotion acknowledges nothing; no two nodes acknowledge writes for one SVM) is Phase B's promotion and binds none of scopes A to D; #11 (`05:844`, SVM create and destroy cycles leak no namespace and no mount; a snapshot exported with its own `fsid`) is `nbladed`'s and binds none; #10 (`05:843`): "The slot check is correct under loom against a concurrent writer; the control plane performs zero syscalls on the data path over 60 s of I/O (`perf trace`)": the slot is 7.5's and not built (section 3, 7.5), but the second clause bears on scope A and on rule 83, because the as-built daemon executes every control request on the engine thread between ticks (E38 `07:1332-1337`) and creates, starts and deletes devices there (`07:1352-1358`), so the syscalls of a control request (a ublk control command, a recovery command, a `device list` or `reap`, a verify's reads) run on the thread that serves the data path; #12 (`05:845`): "The reconciler, killed mid-apply 100 times, converges to the desired hash and never deletes a device": the reconciler is `nbladed`'s (`05:863`) and not built, but this is the design's only invariant about deleting devices, and the brief's `device reap` is to be weighed against it (question 5); the same invariant's `write_cache` and `fua` assertion before every LUN link is `nbladed`'s too, and the device already advertises "a volatile cache with FUA" (E38 `07:1358-1360`).

81. **The 7.1 invariant of superblock selection** (`05:621`): "a reader selects the superblock with the highest `(epoch, cp_seq)` whose map roots verify and whose summary pages pass CRC; `freed_pending` makes a one-CP (two-CP on `flush-opaque`) rewind safe. Boot takes the union of the selected superblock's `write_active` and any `IntentSlot` with a higher `intent_seq`." As built, the rank is F7's `(owner_epoch, cp_seq, cut_seq)` with A winning a tie and a newer major a hard error (`format/lib.rs:111-117`), the regions a candidate must verify are rule 50's, and the deferral is E24's `N+1` / `N+2` (rule 48; E21 `07:580-581`). This is the design's statement for the brief's verify item 1, "Superblock ring (`A0/A1/B0/B1`) CRC and epoch/sequence monotonicity" (`10:616`): a verify pass that ranks the ring must rank as the boot does, and report the slots the boot would reject rather than re-decide the selection.
82. **The 7.6 posture table's boot rows** (`05:812-828`, the per-volume nvfail state machine). The crash row (`05:820`): "| Online(active) | power loss or crash | nothing (volatile) | Offline(dirty) |"; the clean-shutdown row (`05:818`): "clean shutdown or UPS low battery | final CP, `run_state = CleanShutdown` | Offline(clean)"; the dirty-boot row under the default posture (`05:821`): "| Offline(dirty) | boot; posture `Hold` | verify summaries (rewind on failure, cause `TornCp`), set `nvfail[v]`, superblock before export, alert; the engine answers EIO; `nbladed` presents per protocol | NvFailed |"; the clear (`05:826`): "`otapctl volume nvfail-clear <vol> [--restore <snap>]` | bump `rollback_gen`; optional rollback; re-export per `LunIdentity.policy`". As built: the verification is rule 50's, the rewind cause `TornCp` and the hold are E17's dirty boot (rule 40, `07:422-429`), "superblock before export" is the boot commit of rule 37 (`07:391-392`) and the durable-before-serving rule (rule 41), and the clear is `Event::NvfailCleared` (rule 41). The `Replica(applied K)` rows (`05:823-825`) are Phase B's (section 4.8, question 28). The `Fence` row (`05:822`: "| Offline(dirty) | boot; posture `Fence` | bump `rollback_gen`, alert, export under the new identity | Online(idle) |") is not: it is a single-node dirty-boot row, and 6.6 makes `Fence` the default posture of v0.1's file, object and SVM-root classes ("`Fence` serves at once under a new identity and raises the CRIT with the window", `05:550`; the class rows, `05:556-558`), a table that is owner decision D5 (6.6's heading, `05:548`; "D5. The nvfail class table (6.6). The defaults as prepared", `05:923`) and is unanswered ("the nvfail class table, the failover identity and `nvfail_force_lag` remain unanswered", `06:420-425`). As built every dirty boot holds (rule 40), which is the `Hold` row; the `Fence` row waits on D5, not on Phase B, and binds none of scopes A to D (question 28).
83. **The Part 7 conventions** (`05:587`): "Traits are synchronous and reactor-local unless marked; nothing on the data path takes a lock, performs an RPC or touches a futex." The one trait Part 7 marks is the transport's, `DeltaStream: Send` (`05:696`); `Backstore`, `Allocator`, `FrontDoor`, `Clock`, `Net` (`05:641-663`), `DeltaSource` (`05:686`) and `DeltaSink` (`05:704`) are unmarked, so reactor-local. The design also says which reactors call the stream's engine halves, and they are not the ublk reactors: `dbladed` holds "the shipper and receiver reactors" (`05:863`), "on the non-isolated cores at a `CPUWeight` below the ublk reactors" (`05:178`; the cores line, `05:542`, puts "the shipper and receiver threads on the non-isolated cores" and the CP flusher and GC on the ublk reactors' isolated set); the shipper re-reads a stripe "through `DeltaSource::read_chunk`" (`05:54`; R31 `05:405`; the sender table's "`read_chunk`, compress, encrypt, `SEND_ZC`", `05-record:3565`); `DeltaSink` is "the receiver, inside dbladed; Storage implements the engine half" (`05:704`), whose `land()` the receiver calls after `IORING_OP_RECV`, decryption and the CRC (`05:168`); and in the loopback harness "the receiver reactor of the same process lands into aggregate 1's `DeltaSink` through the CP assembler with shadow roots and `ShipApply`" (`05:875`). So in the design the engine halves are local to the shipper and receiver reactors, threads other than the ones that serve the ublk queues and run the CP flusher. As built, none of the four system traits is marked `Send` or `Sync` (`traits.rs:227`, `:438`, `:455`, `:494`), the engine is driven by `tick()`, never by a thread it owns (rule 24; E13 `07:271-273`), "The engine of Step 3 is one thread by design" and concurrent reactors are left to a partitioning of the arena or an `otap-sys` cell type (E16 `07:375-379`; `06:500-502`), and the daemon's engine thread "executes every control request between ticks, so nothing else ever touches the engine and no lock exists" (rule 55; E38 `07:1335-1337`), which is said of the engine as a whole: inside it an accepted entry already departs from `05:587`'s lock clause ("nothing on the data path takes a lock"), a departure no entry records (E15 records only its departure from the brief's `crossbeam-epoch`, `07:314`). E15: writers "insert under the volume's `parking_lot` mutex and drop the guard" (`07:319-321`); `crates/otap-index/src/lib.rs:393` declares `vols: Vec<Mutex<VolumeDirty>>` in `pub struct Generation` (`:391-398`; `parking_lot::Mutex` is imported at `:50` and the vector built at `:404-406`), locked on insert and lookup (`:458-501`), with the `frozen` and `cut_lock` mutexes of `Index` beside them (`:515`, `:518`), and `Cargo.toml:58` calls them "the small engine locks: fast when uncontended". With one engine thread these locks are never contended, so no futex is touched: the as-built form, E15 with E38, meets `05:587`'s futex clause because one thread touches the engine, and not its lock clause, since every insert and lookup of the index still takes E15's per-volume lock (`crates/otap-index/src/lib.rs:458-501`). Step 6 must choose between the two forms, and either choice is a decision to record (rule 2; section 4.3; question 17). (a) The engine halves (a `DeltaSource` walk or chunk read, a `DeltaSink` land or commit) run on the one engine thread, tick-driven and answering `Busy`, and only the transport (sockets, framing, TLS) runs on a thread of its own, exchanging frames with the engine thread without taking a lock or touching a futex on the data path (a lock-free hand-off, or a further departure from the lock clause to record). This keeps E38, E15's uncontended locks and `05:587`'s futex clause, and departs from the design's shipper and receiver reactors (`05:863`, `05:875`, `05:178`), so it needs its own E-entry. (b) The design's form, the engine halves on shipper and receiver threads of their own. This reverses E38's "nothing else ever touches the engine and no lock exists" (a new entry that points back to it, `07:5-6`) and must still reach the engine's state on the data path without taking a lock or touching a futex (`05:587`), E15's uncontended locks being a departure from the lock clause the tree already has: shared through the as-built index, E15's mutexes become contended and touch a futex, a lock of its own breaches the lock clause, and the arena's single writer needs E16's partitioning or cell type first (`07:375-379`). On the receiving side the two forms come closer when the target pool has an engine thread of its own that nothing else writes through (section 4.8, "One pool per daemon"): that thread is then the receiver's. Under either form a tick that blocks breaches rule 24's `Busy` contract and stalls the data path (trap 11). The choice also decides how 7.3's synchronous returns can be kept (section 3.C; section 4.8, "The trait signatures"), and 7.7 #10's "zero syscalls on the data path" (rule 74) counts what a control request does on the engine thread. The daemon's `Io*` channel (`07:1333-1334`) is no precedent: it feeds a test aid, not a data path (trap 9). The paragraph's other conventions are rules already listed: `repr(C)` views with `const` size and offset assertions, zeroed reserved fields under the CRC, golden vectors and an N/N-1 lane (rules 17, 29, 31); `unsafe` in `otap-sys` only (rule 15); the startup probe that builds the opcode allowlist, written in `otap-sys` (`IORING_REGISTER_PROBE` and `UBLK_U_CMD_GET_FEATURES`, `probe.rs:3-4`, `:306-318`) and called by nothing (rules 26 and 79). Its home for on-wire structures, "`otap-format` (disk) or `otap-stream` (wire)", was departed from in part by E07, which put the 64-byte frame header in `otap-format` and left `otap-stream` to build its bodies on top (`07:164-171`; rule 35).

- The re-attach semantics are E16's (rule 36, `07:358-370`): `Placed` kept and replayed in sequence order, `Filled` dropped, reservations committed, the sequence number taken as the maximum, any untrusted slot reported and treated like a power loss. ### 3.B Scope B: incremental catalogue and snapshot tables, and the pool attestation pass

**The tables as they are.**

- The cost, as the documents record it: `06:524-527`: "The catalogue and the snapshot table are rewritten whole in every CP that changes them; with 1,024 volumes and 271 snapshots each that is over 270,000 records per naming CP, and a region that outgrows a segment needs a run of free segments. Step 6's incremental tables." E39 `07:1528-1529` lists the same as a hazard left as a limit. `08:1051-1053` adds a reader's claim, "not yet checked": "The snapshot table is rewritten in every CP that has a snapshot, changed or not, so `06` section 8 and E39 understate the cost." The code bears it out: `prepare_meta` places the snapshot table in every CP whose snapshot set is not empty, with no comparison against the committed table (`crates/otap-cp/src/engine.rs:5175-5179`), while it carries the catalogue forward when it is unchanged (`:5222-5234`). The `06` "Next" list names a *different* trio as "the incremental tables": "The segment table is still written whole at every CP and a fold rewrites a dirty volume's whole index; the cleaner's scan compares against every snapshot tree" (`06:456-459`; the segment table's cost at `06:547-550`: "At 100 TiB with 8 MiB segments that is 400 MiB per CP"). Two more regions are written at every CP whatever changed, and neither list names them: the roots table, one `MapRoot` per volume index up to the highest present one (`crates/otap-cp/src/engine.rs:5249`, built at `crates/otap-map/src/lib.rs:1359-1376`; F14), and the directory, which names every delta region since the last fold (`engine.rs:5252`; `crates/otap-map/src/lib.rs:1350-1356`; F12). The first grows with the volumes and the second with the CPs since the fold, so the brief's "O(1) CP metadata overhead even with hundreds of volumes and snapshots" (`10:612`) is to be checked against every region a CP writes, not against the two tables alone.
- The design foresaw table deltas: "the metadata stream (CP log at 16 B per block, table deltas, map checkpoint pages when due)" (`05:46`).

**The precedent an incremental table must follow** (the map's own design, E22): "Every CP writes its changes as a *delta region* ... and a *directory* (`CpLogDirPage`, F12) that names every delta region since the last fold in CP order ... A *fold* rewrites, copy on write, every map page the overlay and the CP's own records touch ... and empties the directory; a fold CP writes no delta region of its own ... Replay at boot applies a delta region's records iff the region's CP is above the fold CP" (`07:632-642`); the fold's freed regions follow the deferred-free rule "so a crash during the fold still has them" (`07:661-662`); F12's wording: "Every region is named exactly (block, length, CRC), as E14 requires" (`format/lib.rs:165-166`). The boot "verifies the directory's pages in every CP, not only the fold's" (E35 `07:1133-1134`).

**What the boot and the lifecycle already do with the tables, which an incremental form must preserve.**

- Loads "the catalogue and the offline flags with the roots" (E35 `07:1135`); a catalogue that fails its CRC drops the names with `OperatorWarning::CatalogDamaged`, "the next naming CP writes a fresh region, and the daemon addresses a nameless volume as `#<index>` so it can be renamed. A read error of the region still fails the candidate, as every root's does" (E39 `07:1482-1488`). (E35 `07:1136-1137` still says a catalogue region that does not verify "tears the candidate like any other root region"; E39 supersedes it without naming E35 among the entries it amends, `07:1432-1433`.)
- The snapshot table's rules: records leave the table with the deleting commit, "and the catalogue entry with it" (E36 `07:1170-1172`); pins live in `SnapRecord::flags` (`07:1189-1190`); a damaged snapshot stays in the table flagged damaged (E30 `07:923-927`); snapshot ids are "monotonic between rewinds, not across one: a boot that rewinds below a snapshot's CP loses the snapshot and its id is reused. The catalogue and the daemon key snapshots by uuid and name" (`06:555-557`); the limits are 255 user plus 16 reserved per volume (E36 `07:1191-1194`) over `MAX_VOLS == 1024` (F1).
- The one-view rule (rule 54) and E39's exclusions (rule 53) govern any CP that carries a table delta beside a deletion, a rollback or a clean.
- The format-change procedure (rule 31) and the 2.3-only boot (rule 32): a new region type or a new superblock field is `FORMAT_MINOR` 4, a `v2.4/` vector set, new F-rulings, and a boot that refuses 2.3 unless the lead decides to read both.

**"Attestation" in the design is something else.** Every use of the word in `05` is the operator's attestation of a hardware-RAID cache: "ordering rests on the attestation alone: `cache_protection = { controller: Bbu | FlashBacked | None, disk_cache: Disabled | Enabled | Unknown, learn_mode: ... }` ... The attestation is shown as 'attested, not verified' in `otapctl pool show` and in every alert" (`05:52`); `CacheProtection { ..., attested_by: Actor, attested_at: u64 }` (`05:630-631`); R50 (`05:443`); the installer's "attestation dialogue" (R56 `05:455`); D10 (`05:928`). `06` carries the word with that meaning: "E2 (week 5): `otap-geom`, the attestation | the planner done; the attestation (section 7.3) not written" (`06:365`) and "4. **The attestation** (section 7.3) and the metadata device class" (`06:460`). Note the citation: `05`'s section 7.3 is the replication stream (`05:666`); the attestation lives in 1.3 (`05:52`), 7.2 (`05:630-631`) and R50. The reference is a slip, not a pointer to a verify pass.

**What the design says about verifying a pool** (the brief's "pool verify"):

- R60 (`05:463`): "the engine's summary-driven scrub is kept for data CRCs"; R53 (`05:449`): "the engine's catch-up share and scrub budget are subordinate to client QoS"; 8.1 (`05:855`) lists "the engine scrub" among what is "Deferred, in the order they return (each with the time it saves inside the twelve weeks)", with no release named for it: the line's one "v0.1.x" is S3's and Veeam Object Lock's ("v0.1.x after a tagged versitygw release"), and neither the stretch list of weeks 13 to 16 (`05:895`) nor the phase map's "v0.1.x (the stretch list, each a point release with no format change)" (`05:911`) includes it, so it is deferred past v0.1, to no named release: "v0.1 keeps a simple cleaner and read-time CRC verification". R22's "our scrub replaces `checkarray`" is withdrawn (`05:391`).
- R55 (`05:453`): the support bundle collects "the attestation report, superblock and intent slots, CP-log statistics, relationship cursors".
- 7.7 #3 (`05:836`): "Every byte of every structure is covered by a CRC".
- 7.7 #5 (`05:838`): "A torn superblock or data stripe falls back to CP N-1 intact; a torn CP on a `flush-opaque` backstore falls back to N-2 intact (dm-flakey)". For the brief's item 1 (the ring) and item 3 (the stripes): a slot or a stripe that fails its CRC behind the selected CP is the designed fall-back, kept intact by E21's `N+2` deferral (rule 45) and the boot's rewind (rule 50), to be reported as what the boot would reject, not as damage to the pool the boot serves; the dm-flakey proof of #5 belongs to the lane rule 80 describes and is not built.
- 7.1's invariant (`05:621`; rule 81): "a reader selects the superblock with the highest `(epoch, cp_seq)` whose map roots verify and whose summary pages pass CRC; `freed_pending` makes a one-CP (two-CP on `flush-opaque`) rewind safe". This is the design's own wording for the brief's item 1 (ring CRC and epoch/sequence monotonicity, `10:616`); the as-built rank is F7's `(owner_epoch, cp_seq, cut_seq)` (`format/lib.rs:111-117`) and the daemon already probes the whole ring (E39 `07:1489-1492`).
- The brief's item 2, "`MapPage` CRCs, bounds, and LBA continuity" (`10:617`). The design describes the map, "a page index (16 B per 4 MiB: `page_pba`, `max_birth`) and 16 KiB pages of 1,024 entries ...; every read verifies its CRC against the entry, which also catches misdirected writes" (`05:48`), with 7.1's `MapEntry` "1,024 per 16 KiB page" (`05:612`) and E22's "one `PageIndexEntry` per 1,024-entry `MapPage`" (`07:629-630`), but no document defines "bounds" or "LBA continuity" for it. As built the addressing is positional: "An LBA `l` lives in map page `l >> 10` at slot `l & 1023`; map page `p` is described by index entry `p`" (`crates/otap-format/src/map.rs:17-18`; "Entry `i` describes LBA `page_no * 1024 + i`", `:199`; the index page likewise, `:334`), so no page stores an LBA, and continuity can only be the shape: an index of exactly the pages the volume's size needs. What the parsers already check: a root's volume index, size (at most `MAX_LBA + 1`), CP and index length against its size (`MapRoot::validate`, `map.rs:419-447`); the index's length, CRC and entries (`MapRoot::verify_index`, `:455-471`; an absent entry may carry no birth or CRC, `:321-327`), with `otap-map` also refusing an entry past the volume's last page that is not absent (`index_entries`, `crates/otap-map/src/lib.rs:295-314`); a page against its index entry, by CRC, every entry and `max_birth` (`MapPage::verify`, `map.rs:251-264`); an entry, refusing a data entry with `lseg == 0`, a `plen` of 0 or above 8 sectors, or a zero birth, and a hole or unmapped entry with a CRC (`MapEntry::validate`, `:175-192`); and a lookup or a replayed CP-log record at or past the size (`crates/otap-map/src/lib.rs:393-398`, `:834-839`). What none of them checks: an entry's `lseg` and `off` against the pool's segments and their state, and a page's births against the CP that names it, which the format crate cannot check, having neither the segment table nor the CP (`pack_addr` bounds only the field widths, `map.rs:71-100`); and, though they need neither, the entries of the last page past the volume's size and a root's `max_birth` against its index (a grep of `max_birth` over `otap-map` and the boot finds it read for `diff`'s page skips and recomputed at a fold, never compared). Those are the candidates for item 2's two words; which of them the pass checks is open (section 4.4, question 11).

**The as-built pieces a verify pass can be assembled from** (all named by the documents):

- The boot's verification (rule 50): the ring ranked by F7 `(owner_epoch, cp_seq, cut_seq)` (`format/lib.rs:111-117`); the stripe list by summary CRC and identity (F17); the directory's pages; snapshot roots and indexes under E30's rule, "A snapshot root page or pinned index that does not verify tears the candidate only when the candidate itself wrote it" (`07:921-923`), the snapshot otherwise kept and flagged damaged (`07:923-927`).
- `audit_liveness`: "a walk of every tree, counting per segment" that "checks the result in every simulator recovery" (E36 `07:1166-1167`); "reports any segment whose live count drifted" (`06:267-268`).
- The cleaner's scan: "`cleaner::scan` reads the candidate's stripes and, through the `References` trait, keeps only the blocks whose `(vol, lba)` still maps to exactly this `(lseg, off)` in the live map or in a snapshot" (E37 `07:1278-1283`), with E39's rules: "A summary of zeros is a stripe never written; anything else that does not parse skips the segment (`SkipReason::Summary`)" and "the scan reports every referenced block it saw (`Scan::referenced` ...): a count below the table's live count means a stripe it could not read as written vouches for blocks it cannot see" (`07:1451-1459`).
- The accounting the brief names: `SegEntry::live_bytes` is a format field (`crates/otap-format/src/records.rs:137`); the engine keeps `data_live` and `meta_live` per segment (E24 `07:718`) and derives `data_live` from `live_bytes` at load (`crates/otap-cp/src/engine.rs:1905`); the deferred frees are `freed_pending` with `boot_protect` and `discarding` (E24 `07:733-734`).
- Containment the verify must keep: a damaged map page "answers `Corrupt` to the reads of its blocks (and a device read error answers `Failed`), never failing the engine's tick" (E32 `07:984-986`); parsers verify before they expose (rule 18).
- The control plane is one serialized thread: "Requests are answered one at a time, so a long operation (a rollback, a shutdown) delays the next request behind it; the control plane is not a hot path" (E38 `07:1345-1347`); `--op-timeout` 120 s (`07:1341-1342`); `otapctl` waits ten minutes (`07:1521-1522`).
- A recorded accounting drift the verify will meet: "The boot's metadata liveness counts a region shared by the live tree and a snapshot once per tree, so such a metadata segment cannot be freed until the next boot: the Step 4 review's hazard 12, never closed and never recorded as a limit" (`08:1054-1057`; a reader's claim, "not yet checked", `08:1051-1052`).

**The brief's words** (`10:610-619`): "Replace full-table rewrites with incremental catalogue and snapshot table updates across Consistency Points (logging incremental `SnapRecord` / volume catalogue deltas in `CpLogPage` or CoW catalogue pages and folding them periodically), ensuring O(1) CP metadata overhead even with hundreds of volumes and snapshots"; "Maintain backward/forward format clarity and update golden vectors if required by pre-release format rules"; the verify "in `otap-cp` (exposed via `dbladed` and `otapctl pool verify`) that audits: 1. Superblock ring (`A0/A1/B0/B1`) CRC and epoch/sequence monotonicity. 2. Every active volume's two-level radix map (`MapPage` CRCs, bounds, and LBA continuity) and pinned `SnapRecord` roots. 3. Every live segment's on-disk stripe summary headers and block payload CRCs against the radix map's expected `(lseg, off, birth_cp)`. 4. Exact reconciliation between recomputed live block references and `SegEntry::live_bytes` / deferred-free accounting, returning a structured attestation report without panicking on corrupted sectors."

### 3.C Scope C: the replication transport (sender, receiver, loopback TCP, file sink)

**The contracts of 7.3** (`05:666-713`), abridged to what the sketch fixes:

- `FrameHdr` (`05:670-672`): 64 bytes, `magic, ver, kind, flags /* codec */, rel, idx, cp_seq, base, cp_id /* the CP nonce */, owner_epoch, wire_len, raw_len, payload_crc, hdr_crc`. As built, the header is `otap_format::StreamHeader` (E07 `07:169-171`) and `FrameMeta` is "the header context a frame travels under: `rel`, `chunk_idx`, `cp_seq`, `base`, `cp_nonce`, `owner_epoch`" (`06:164-165`).
- `Kind` (`05:673`): `Hello, HelloAck, DeltaBegin, VolEvent, Chunk, Holes, DeltaEnd, Landed, Committed, Abort, Ping, Pong`; built as the twelve kinds with fixed little-endian bodies and trailing records `SnapTag`, `AckedBytes`, `ChunkRange`, a volume name of at most 255 bytes (`06:160-163`).
- `DeltaDesc` (`05:674-677`): `rel, base, target, cp_id, direction_epoch, chunks, bytes, tags: Vec<SnapTag>, cut_mono, mode: Steady | Increment { from: SnapUuid, to: SnapUuid }, write_active, acked_bytes`.
- `VolEvent` (`05:678-679`): `Create { vol, geom, class }, Resize { vol, size }, Delete(VolId), SnapTag { uuid, name, retention }`. `Hole { vol: u32, len: u32, lba: u64 }` (`05:680`).
- `Cursor` (`05:681-682`): `applied, applied_epoch, landing: Option<(CpSeq, CpId)>, landed_contig, landed_sparse, credits /* 4 KiB units of free receiver staging */`; built as `Cursor` "keyed by `(cp_seq, cp_nonce)`: a `ResumeBitmap` of landed chunks (at most 2^24 chunks), the wire form carried by `HelloAck` (at most 4,096 sparse ranges), and a 4 KiB `CursorPage` (`OTCU`, 500 ranges) persisted per pipe" (`06:170-173`; `crates/otap-stream/src/cursor.rs:73`, `:307`, `:505`, `:522`, `:622`).
- `Event` (`05:683-684`): `Sent, Landed { idx, credits }, Committed(CpSeq), Reconnected(Cursor), Dead(EndpointId), Aborted(AbortReason /* Corrupt(idx) | NoSpace | BaseMismatch | Version | StaleEpoch | UnknownVol */)`.
- `DeltaSource` (`05:686-695`): `describe(rel, base, target) -> DeltaDesc` ("GC-pins the delta's segments"), `events`, `holes`, `read_chunk(d, idx, dst, bypass_cache) -> u32` ("stripe image, identical bytes"), `committed(cp)` ("DeltaEnd may now go"), `applied(rel, cp)` ("base pin and lag only"), `pin(rel, cp) -> SnapId`, `unpin`, `detach`.
- `DeltaStream: Send` (`05:696-703`): "impl TlsTcp (and FileSink for dump --since); never leaks sockets, TLS, codec or timers": `open(pipe, epoch) -> Cursor`, `begin(d, ev, holes)`, `send(d, idx, stripe)` ("Err(Window) without credits; encrypts into the bounce"), `end(d, digest: [u8; 32])`, `throttle(endpoint, kbps)` (R62), `poll(out) -> usize`, `close`.
- `DeltaSink` (`05:704-712`): "the receiver, inside dbladed; Storage implements the engine half": `cursor(pipe)`, `begin(d)` ("BaseMismatch, NoSpace, StaleEpoch; a new cp_id discards a partial"), `vol_event` ("UnknownVol"), `land(d, idx, stripe) -> credits` ("idempotent by (cp_id, idx); CP assembler"), `holes`, `commit(d, when: Immediate | NextCp) -> Applied` ("replica CP; durable on return"), `abort`.
- Not settled, though written in the sketch: its synchronous returns. `DeltaSink::commit(d, when) -> Applied` is "replica CP; durable on return" (`05:710`) and `DeltaSource::pin(&self, rel, cp) -> Result<SnapId, SrcErr>` hands back a snapshot id at once (`05:693`), while the as-built engine records a snapshot, a pin or a base for the next CP and reports it by an event when that CP commits (`create_snapshot`: "Returns nothing until then", `crates/otap-cp/src/engine.rs:2295-2308`; `set_snapshot_pins` and `set_replication_base`, E36 `07:1185-1189`, the daemon's base request then waiting for the CP, `crates/otap-daemon/src/pool.rs:1149-1155`), a CP spans many ticks (its writes go out in E17's order, `07:393-398`, through E13's asynchronous `Backstore`, "tagged asynchronous writes ... `poll` for completions", `07:264-266`, and E38 says so outright: "A request that needs a consistency point ticks the engine until the event it waits for arrives ... and the data path keeps flowing because those ticks serve it", `07:1337-1343`), and nothing is observable before its CP commits (rule 22). With the engine halves on the engine thread (rule 83's form (a)) a call durable on return either blocks inside a tick or departs from the sketch; with them on a thread of their own (form (b), the design's) it is that thread waiting for the engine thread's CP, a hand-off the as-built daemon does not have (its requests wait by ticking the engine themselves, `crates/otap-daemon/src/pool.rs:476-520`) (section 4.8, "The trait signatures").
- `05:715`: the sender relationship states "`Idle -> CatchUp` at creation; `Steady -> Lagging` when the hold is exceeded or the link is down over 10 s; `Lagging -> CatchUp` when the link returns (pin T); `CatchUp -> Steady` once the last increment is applied; `any -> Resync` on a base mismatch; `any -> NoCommonBase` ...; `any -> Paused` on operator `quiesce`. The transport's sender session (Idle, Connecting, Describing, Streaming, Ending, NoCommonBase), receiver (Listening, Sessioned, Landing) and endpoint selector (Preferred, Secondary, Down) tables are in the record and adopted as written. `dump --since <snap>` is the `FileSink` implementation of `DeltaStream`: a file of frames with the same header, so the backup format and the wire format are one."

**The adopted state tables** (`05-record:3557-3586`; the earlier draft at `05-record:847-888`, whose endpoint table `3586` says is unchanged):

Sender session, one per pipe (`05-record:3559-3572`):

| State | Event | Action | Next |
|---|---|---|---|

**The design's data-path words.**

- Sender (`05:54`): "each staged ingest stripe of an outbound group goes to the flusher and the shipper at once ... Later resends re-read the stripe from cache or disk by `(lseg, stripe_idx)` through `DeltaSource::read_chunk` ... Catch-up and resync use `Increment` mode: for each retained snapshot S_i in (base, T], walk S_i's pinned page index for `birth in (S_{i-1}, S_i]` in PBA order, apply as one receiver CP and materialize S_i; then the live root for (S_last, T]; capped at 30% of pool read bandwidth; the round ends when the live root's increment is one CP. Relationship state is per consistency group (default: the SVM's volumes, root included); the transport is per aggregate pair."
- Receiver (`05:56`): "Chunks are containers of `(vol, lba, birth, data)` records staged through the receiver's own CP assembler into shadow roots; the receiver builds full stripes for its own geometry and commits through its own `Backstore`. At `ShipApply` every volume of the group switches roots together, so a replica is always at a sender CP boundary. The receiver forces a CP on `CpEnd` when none is in flight and runs a 2 s CP timer while a relationship is inbound ... Resume is a per-CP chunk bitmap plus one byte offset per open connection, keyed by `(cp_seq, cp_nonce)`; a `CpBegin` with a known sequence and a different nonce discards the partial."
- The pipe and the map-walk delta (3.3, `05:162`): "A pipe is a TLS session set between two aggregates (one per direction per pair). A delta is `(rel, base, target, cp_id)`: steady state ships one committed CP's ingest stripes in staging order; catch-up, resync and coalesced deltas are map walks in PBA order per consistency group, chunked as the live blocks of each on-disk stripe born after `base`, with the delta's segment list GC-pinned from `describe()` to `DeltaEnd`. A chunk is one stripe image, at most 8 MiB (2.5 MiB on a 12-drive HDD RAID6, 256 KiB on flash), opaque to the transport except for its CRC." So the sender selects a map walk's blocks, one chunk per source stripe (section 4.8, "What a `Chunk` carries").
- What ships (`05:46`): "stripes are homogeneous in kind and ingest is packed per consistency group, so only ingest stripes of outbound groups ship"; `05:78`: "relocations kept off the wire by `kind` bits and per-group packing". R25 (`05:393`): the stripe image is the only chunk payload, re-derivable by `(lseg, stripe_idx)`, segments GC-pinned from `describe()` to `DeltaEnd`. R31 (`05:405`): the arena is never a send source; resends come from disk or cache.
- The receiver's CP trigger: `CpTrigger::ShipApply` (`05:660`); "the receiver lives inside `dbladed`" (`05:473`); `commit: Immediate` for cutovers (R30 `05:403`).
- Memory: the Phase C column budgets "Shipper hold / receiver staging and landing index | 0 / 0" and "Transport buffers (TLS bounce, read-back, receive, sockets) | 0" (`05:528`, `05:533`); the 2 GiB staging is Phase B's (`05:528`, R38 `05:419`).
- Week 11 (`05:893`; rule 76): E1 "`DeltaSource` in `Steady` and `Increment` modes; `dump --since` and `restore` through the `FileSink`"; E2 "The loopback `TlsTcp` stream and `DeltaSink` harness". - Workspace (`05:863`): "`otap-stream` (v1 frames, cursor, credits, `TlsTcp` and `FileSink`)" and "`dbladed` (reactors, the ublk front door, the shipper and receiver reactors)". ### 4.7 Scope A's open points

- `UBLK_F_USER_RECOVERY_REISSUE`: the design names "`USER_RECOVERY` and `REISSUE`" (`05:505`, `05:888`); the code sets `USER_COPY | USER_RECOVERY | CMD_IOCTL_ENCODE` (`device.rs:95`) and lists the same three as required (`probe.rs:37-38`; a list nothing checks, rule 79); `ublk.rs:284-286` documents `REISSUE` as "requests in flight at the server's death are reissued to the new server". What becomes of the dead server's requests is written down in three places, and the code meets none of them yet. (a) The saved driver (trap 38): without `REISSUE`, OpenTAP's case, each request the dead server had taken and not committed ends with `EIO` (`ublk_abort_queue`, `ublk_drv.c:1387-1408`, marks it aborted; `__ublk_fail_req`, `:1061-1070`, drops it to `__ublk_complete_rq`, which answers `BLK_STS_IOERR` for an aborted request, `:999-1001`); with `REISSUE` it is requeued to the new server (`:1066-1067`); a request not yet handed to a server is requeued under `USER_RECOVERY` either way (`__ublk_abort_rq`, `:1090-1098`); a request the server had committed has already left the driver. (b) The round-2 design, "standing where the revision-3 charter did not re-open it" (`06:84`; the charter is `04`, `06:85`), defines the "`ReqId` dedupe" that round 3's week 6 still names (`05:888`): the struct `ReqId { pub dev: u32, pub queue: u16, pub tag: u16, pub generation: u32 }` with the comment "stable across restarts: the REISSUE dedupe key" (`docs/03-architecture-brainstorm-02.md:632`), carried in every record header as `req_id` (`:531`), and the record asks for a `req_id` "derived from (device, queue, tag, generation), not a counter that restarts with the daemon" (`docs/03-architecture-brainstorm-02-record.md:878`). (c) Round 1's record, citing the ublk documentation: "plain `USER_RECOVERY` *aborts* requests already issued to the daemon; only `UBLK_F_USER_RECOVERY_REISSUE` requeues them", and `REISSUE` "may issue the same I/O request twice" (`docs/01-architecture-brainstorm-record.md:750`). As built the request id's generation starts at 0 in every process (`crates/otap-ublk/src/frontdoor.rs:208-215`, `:269`) and the arena descriptor holds no request id (E16 `07:347-349`), so the design's dedupe key does not exist. The decision is therefore whether to set `REISSUE` (naming the flag in `device.rs` breaches no rule the code enforces, though it extends that file's unrecorded departure from E08's documented rule, rule 26) and, if so, how a reissued write whose data the re-attach already replays (a `Placed` slot "may be acknowledged", E16 `07:352-353`; rule 36) is recognised, which needs a request id that survives the restart; if not, whether an `EIO` for a write the engine had already placed is acceptable under the brief's "reconcile in-flight `ublk` I/O tags without duplicating or dropping acknowledged writes" (`10:606`) and R57's restart "with the same 2 s target and 5 s hard budget as a crash" (`05:457`).
- Identifying a quiesced device: the daemon has no durable state (`07:1408-1409`) and boots every volume from the disk (`07:1371-1372`); the design's only hook is R39's "Every ublk device records its SVM's slot index at creation" (`05:421`). How the restarted daemon matches `/dev/ublkbN` (device id, dead server pid, `UBLK_S_DEV_QUIESCED`) to `(aggregate, volume)` is open: a naming or serial convention, a record in the pool (a format change), a run-state file beside the socket, or the hook the UAPI itself provides. `struct ublksrv_ctrl_dev_info` carries `__u64 ublksrv_flags`, "For ublksrv internal use, invisible to ublk driver" (`ublk_cmd.h:237-238`); `ADD_DEV` copies the whole structure it is given into the device (`memcpy(&ub->dev_info, &info, sizeof(info))`, `ublk_drv.c:2434`; it then rewrites the id, the flags, the queue count and the buffer size, `:2437-2466`, not that field) and `GET_DEV_INFO` returns it (`ublk_ctrl_get_dev_info`, `:2569-2582`), with the device's `state` and `ublksrv_pid` beside it. `otap-sys` already models the field (`UblksrvCtrlDevInfo::ublksrv_flags`, `ublk.rs:463`, at offset 32, `:944`) and builds the command (`CtrlCommand::get_dev_info`, `ublk.rs:789`), and `device.rs:90-97` leaves it zero. So a device can carry 64 bits of owner identity with no run-state file; 64 bits hold neither the aggregate's identity ("sixteen bytes", E38 `07:1362-1365`) nor it and an index, so the value would be a digest. A digest of the aggregate and the index alone cannot tell a removed volume's leftover device from a new volume at the same index: a deleted volume's "index number may be reused" and volumes are created "at the lowest free index" (E36 `07:1216-1218`; `.position(|v| !v.present)`, `crates/otap-cp/src/engine.rs:2731-2736`), and a device matched to the new volume would serve the old volume's requeued writes, and its open `/dev/ublkbN` holders, against the new one. The digest needs the volume's incarnation too: a volume has no uuid (its catalogue record carries `Uuid::NIL`, `crates/otap-format/src/catalog.rs:129-130`); the only durable per-volume stamp is the catalogue's `created_wall_ns` (`engine.rs:5190-5196`), which a damaged catalogue loses (E39 `07:1482-1488`); anything else is a new field, which is a format change.
- The reaper's authority: "orphaned/wedged `ublk` device instances left behind by dead daemons or removed volumes" (`10:607`); whether `device reap` may delete a device that is `UBLK_S_DEV_LIVE` under another process, or one of another pool on the same host, and whether `device list` reads `/dev/ublk-control` without a booted pool (the format path already runs a daemon with no pool, `smoke:183-192`), is open. Five facts bound it. The design's only invariant about deleting devices is 7.7 #12, "The reconciler, killed mid-apply 100 times, converges to the desired hash and never deletes a device" (`05:845`; rule 74), which says what the design expects of automatic cleanup. A `STOP_DEV` of a quiesced device ends every request it holds with `EIO` (`force_abort`, `ublk_drv.c:1593-1618`, `:1271-1272`; trap 38), so reaping a device a restarted daemon could have recovered turns held I/O into errors. `DEL_DEV` does the same, because it stops the device first (`ublk_remove`, `:2162-2170`, called at `:2522-2524`), and then waits, interruptibly, until the device's number is freed (`:2546-2547`), which happens only when the last holder of `/dev/ublkbN` and of `/dev/ublkcN` lets go, the deleting server's own descriptor, ring and mapping included (trap 42 (a)), so a synchronous `DEL_DEV` on the engine thread can stall it, and one sent by a server that still holds the device waits on itself. And every added device counts against `ublks_max`, 64 by default, until it is deleted (or the module unloaded, `ublk_exit`, `:3031`), past which `ADD_DEV` fails with `EACCES` for any caller (`:494`, `:2126`, `:2169`, `:2417-2419`; trap 42), so devices left quiesced use the limit up. And a `STOP_DEV`, `DEL_DEV` or `DEL_DEV_ASYNC` of a `LIVE` device with `USER_RECOVERY` first quiesces it and waits, with no timeout and no signal check, until no request is started (`ublk_stop_dev`, `:1600-1602`; `__ublk_quiesce_dev`, `:1547-1556`; `ublk_wait_tagset_rqs_idle`, an `msleep` loop, `:1532-1545`; `ublk_check_inflight_rq`, `:1521-1530`), that is until the device's server has committed every request it holds; both deletes reach the wait through `ublk_remove` (`:2162-2170`; `DEL_DEV_ASYNC` differs only in `wait == false`, `:2946-2951`) and hold the host-wide `ublk_ctl_mutex` throughout (`:2518-2530`), which every `ADD_DEV` takes too (`:2413`). So a reap of a `LIVE` device whose server is wedged never returns, stops the data path for good when issued on the engine thread (`execute` waits for the completion and retries an interrupted wait, `ublk.rs:1248-1270`, `:1251`), and, as a delete, holds up every later `ADD_DEV` and `DEL_DEV` on the host, any daemon's; and a server that stops its own `LIVE` device while it holds an uncommitted request deadlocks (trap 42 (d)). The driver's own way down for a wedged `LIVE` device is the death of its server: the teardown of the server's ring cancels its commands and aborts every request it held (`ublk_uring_cmd_cancel_fn`, `ublk_drv.c:1464-1497`; `ublk_abort_requests`, `:1410-1440`), the timeout handler does the same once the server is dying and has no fetch left to cancel (`ublk_timeout`, `:1224-1245`), and the quiesce work then marks the device `QUIESCED` (`ublk_quiesce_work_fn`, `:1558-1570`), after which a `STOP_DEV` or a delete proceeds and the held I/O ends with `EIO` (trap 38); the io_uring half of that chain is not among the saved sources (trap 42 (d)). How `device list` and the reaper find the devices they act on is open as well, because the 6.12 driver has no command that lists devices: its control commands are `ublk_cmd.h:15-25` (`GET_QUEUE_AFFINITY`, `GET_DEV_INFO`, `ADD_DEV`, `DEL_DEV`, `START_DEV`, `STOP_DEV`, `SET_PARAMS`, `GET_PARAMS`, the two recovery commands, `GET_DEV_INFO2`) plus `GET_FEATURES` and `DEL_DEV_ASYNC` (`:50-53`), dispatched at `ublk_drv.c:2932-2969`, and a command for an id that has no device answers `-ENODEV` (`:2921-2925`). A device appears as `ublkc%d`, its id as the minor, under the `ublk-char` class (`:477-478`, `:2112-2117`) from `ADD_DEV` until `DEL_DEV` removes it (`cdev_device_del`, `:2167`), and as the disk `ublkb%d` (`:2259`) from `START_DEV` until a stop deletes the disk (`del_gendisk`, `:1605`). Nothing in `otap-sys`, `otap-ublk` or `otap-daemon` enumerates them: `UblkChar::open` opens `/dev/ublkc{dev_id}` by id (`ublk.rs:1116-1122`), and a grep of the crates for `ublk-char`, `/sys/class` and `read_dir` finds none. So discovery is either a scan of `/sys/class/ublk-char` (or of the `/dev/ublkc*` nodes) followed by `GET_DEV_INFO` per id for the state, `ublksrv_pid` and `ublksrv_flags` (question 4), or a `GET_DEV_INFO` probe over ids, which must cover the driver's whole id space, `UBLK_MAX_UBLKS = UBLK_MINORS` (`ublk_drv.c:49`, `:493`; the driver picks a free id in `[0, UBLK_MAX_UBLKS)`, `:2075`, and another tool may ask for any id below that bound, `:2069-2073`, `:2405-2409`), not merely the ids below `ublks_max`.
- The 2 s target: "resume serving within the 2-second recovery budget" (`10:606`) is a design target that is "not measurable here" (`06:356`); round 2's record says what it contains, a crash being "START_USER_RECOVERY, re-FETCH of every tag of every device, END_USER_RECOVERY, with LIO commands hanging meanwhile; my 2 s re-attach budget must include it for 16 x 128 tags" (`docs/03-architecture-brainstorm-02-record.md:878`); "Performance numbers are recorded, never asserted" (`05:873`), and 8.6 publishes "re-attach time" ungated beside its functional 2 s gate (`05:903`; rule 70). What the Windows tests assert instead (a bounded number of ticks? a bounded number of control commands?) is a decision.
- **The 5 s hard bound and the supervisor.** The design binds the hard bound to the watchdog (section 3.A: `05:504-505`, `05:546`, `05:567`), and round 2's supervised restart "suspends the watchdog's worker check-ins so the restart does not become an 8 s fence" (`docs/03-architecture-brainstorm-02.md:22`); the brief names only the 2 s target (`10:606`). As built there is no watchdog and no supervisor (section 3.A), so nothing enforces the bound, and the recovery has no deadline of its own: `END_USER_RECOVERY` waits until every queue has a fetch on every tag (`ublk_drv.c:2747-2749`; trap 38), and `UblkControlRing::execute` waits for each command's completion and retries an interrupted wait (`ublk.rs:1248-1270`, `:1251`), so a deadline needs a way to stop waiting for a command, which `otap-sys` does not have. Open, and a decision to record (rule 2): what Step 6 does at the 5 s bound (a recovery deadline after which the daemon gives the device up and deletes and recreates it, which fails the I/O the device holds, trap 38, and which must first drop the daemon's own hold on `/dev/ublkcN`, its descriptor, ring and mapping, or send `DEL_DEV_ASYNC`, or the delete waits on itself, trap 42 (a); or a recorded gap, the bound unenforced until a watchdog exists); who supervises the restart (systemd units written now, which `06:451-452` lists as a leftover, or the operator and the harness, as the smoke script does, `smoke:251-277`); and whether week 8's watchdog (`05:890`) is built in Step 6 or recorded as not done, since no `06` table carries it (section 4.10, item 14) (question 6).
- The mock: "A mock of a kernel driver must follow the driver's rules, or the state machine ends up defending against ghosts" (`08:777-780`), and "The kernel facts a worker cites from memory must be checked against the saved sources before they are asserted in tests" (`08:749-750`); the driver's recovery rules were read by the lead from the saved sources (`08:1037-1039`) and are not in any document; the mock's model of `QUIESCED`, `START_USER_RECOVERY`, the new server's open and mapping of `/dev/ublkcN`, a fetch per tag, `END_USER_RECOVERY` (in that order, trap 38) needs those rules written down (an E-entry like E28's kernel facts, `07:858-868`); trap 38 lists them from the saved 6.12 `ublk_drv.c` with their lines: the three task checks behind E28's "first fetch" (the completing fetch binds the queue; commands, dispatch and cancel each test the bound task; so every fetch of a queue must come from the task that serves it), what becomes of the dead server's requests, `STOP_DEV` on a quiesced device, and `END_USER_RECOVERY` as a control command with no task check; traps 41 and 42 list the rules a restart and a reaper meet (the capacity and limits fixed at `START_DEV`, `DEL_DEV`'s stop and wait, `ublks_max`, a built-in driver, and the stop's own wait on a `LIVE` device until its server has committed every request it holds). And the as-built seam models none of it: `Transport` is the queue as the state machine sees it, its events, the two copies and a commit that also "fetches the tag's next request", with no fetch command, no device state and no control command (`crates/otap-ublk/src/frontdoor.rs:61-76`); `MockTransport` is that queue in memory (`crates/otap-ublk/src/mock.rs:14-37`); and the device lifecycle is Linux-only (`#[cfg(target_os = "linux")] pub mod device;`, `crates/otap-ublk/src/lib.rs:45-46`). Modelling `QUIESCED`, the two recovery commands and the per-tag task binding on Windows ("via the mock transport in `otap-ublk` and `otap-sim`", `10:608`) therefore needs a new abstraction beside `Transport`.

### 4.8 Scope C's open points

- **Phase B pulled forward.** Section 1.8 gives Phase C "`DeltaSource` in both modes with `dump --since` and `restore`" and says "Phase B adds the TCP `DeltaSink`, `ShipApply`, nonce-keyed resume, per-group relationship state, the conservative promotion set, resync in both directions, `on_space_pressure`, the 2 GiB hold and receiver staging" (`05:82`); Part 8 builds the TCP `DeltaSink` only as the loopback harness, "a test vehicle until Phase B" (`05:875`, `05:893`), and defers "the receiver as a user feature" (`05:855`). The brief's receiver, "staging incoming chunks, enforcing credit windows, maintaining the 4 KiB `CursorPage` / `ResumeBitmap` across disconnects, committing the received delta as an atomic CP on the target pool" (`10:623`), is that Phase B list: receiver staging, nonce-keyed resume and the `ShipApply` commit. The plan's own harness already runs `ShipApply` and the chunk-bitmap resume (`05:875`), so the line the design draws between the week 11 harness and the Phase B receiver is the receiver's standing as a user feature (`05:855`), not the mechanism. Open, and a decision to record either way (rule 2; a narrowing of the brief is also a departure under rule 6): whether Step 6 builds the receiver as the week 11 test harness, saying the brief was read so, or as the Phase B receiver ahead of the plan. The bullets below are its details in both cases (question 18).
- **Steady or Increment.** The brief's sender walks the map for `birth_cp > base_cp` (`10:623`), which is the design's `Increment` mode between snapshots (`05:54`, `DeltaDesc.mode`, `05:676`); the design's steady state ships staged ingest stripes per CP from the staging pool (`05:54`, R31). The plan builds both in Phase C: week 11's E1 cell is "`DeltaSource` in `Steady` and `Increment` modes" (`05:893`; rule 76), while the memory table budgets Phase C no shipper hold and no transport buffers (`05:528`, `05:533`) and the brief names only the map walk. Open: whether a delta's target is a snapshot taken for the transfer (`SnapOrigin::Transfer`, one fold per delta, E25 `07:761`, within the 16 reserved slots, E36 `07:1191-1194`) or the live root (`live_diff`), and whether Step 6 builds `Steady` as week 11 says (then from what source, with no hold: R31's read-back by `(lseg, stripe_idx)`) or `Increment` alone, recording the departure from the week 11 row.
- **What a `Chunk` carries.** R25 and F3 fix the chunk payload as the stripe image "byte for byte", re-derivable by `(lseg, stripe_idx)` (`05:393`, `format/lib.rs:97-98`); the brief says "extents and holes" (`10:623`); the receiver takes "containers of `(vol, lba, birth, data)` records" and "builds full stripes for its own geometry" (`05:56`). An ingest stripe of a pool with one consistency group holds blocks of every volume and births of one CP; a relocation stripe holds old births and is "kept off the wire by `kind` bits" (`05:78`). The design settles who filters a map walk: its deltas are "chunked as the live blocks of each on-disk stripe born after `base`" and "A chunk is one stripe image, at most 8 MiB" (3.3, `05:162`), so the sender selects the blocks, one chunk per source stripe. Open: how such a chunk is laid out against R25's and F3's "byte for byte" (stripe-shaped chunks of the delta's blocks: a new stripe kind on the wire, or `Applied`), and how the receiver orders blocks whose births differ within one delta ("later writes winning", 7.7 #2 `05:835`); shipping verbatim stripe images for the receiver to filter by the delta's `(vol, lba, birth)` set departs from `05:162` and is recorded as such (rule 2; E11, rule 10).
- **Pinning against the cleaner.** R25: "the delta's segments are GC-pinned from `describe()` to `DeltaEnd`" (`05:393`). As built, a snapshot pins blocks by birth (E25 `07:753-756`) but the cleaner *moves* a snapshot's blocks and rewrites its tree (E37 `07:1284-1286`; "nothing on disk says a block moved; the map simply names the new address", `07:1290-1292`), so a chunk address resolved at `describe()` can be a drained segment by `read_chunk`. Open: hold the cleaner off the segments of a delta in flight (a new exclusion under the one-view rule, rule 54) or re-resolve every chunk through the pinned tree at send time.
- **Per volume or per group.** `set_replication_base(vol, ..)` and the 16-slot limit are per volume (E36); the design's relationship is "per consistency group (default: the SVM's volumes, root included)" (`05:54`) with `DeltaDesc.rel: RelId` and `write_active: VolBitSet` (`05:674-677`), and its pipe is "a TLS session set between two aggregates (one per direction per pair)", whose map walks run "per consistency group" (`05:162`). Without a `StateStore` (D3 open, `06:414-419`) nothing holds a relationship. Open: what a pipe covers in Step 6 (one volume, a set, the pool) and where its state lives.
- **The receiver's commit.** "committing the received delta as an atomic CP on the target pool" (`10:623`): `CpTrigger::ShipApply` is deferred (E17 `07:459-462`) and absent (`engine.rs:241-258`); `StripeKind::Applied` exists only in the format (`stripe.rs:59-60`); the one-view rule and E39's exclusions apply to a CP that lands a delta beside a deletion, a rollback or a clean (`07:1435-1443`). Open: the trigger, the stripe kind, the exclusions, and the state of a target volume while it receives (the design's `Replica(applied K)` row, `05:823-825`, is Phase B; `VOL_OFFLINE` exists, F18; a new flag is a format change).
- **One pool per daemon.** The loopback harness is "Two aggregates in one `dbladed`", where "the receiver reactor of the same process lands into aggregate 1's `DeltaSink`" (`05:875`), and the brief commits the received delta "as an atomic CP on the target pool" (`10:623`). The daemon as built hosts one pool: `pool: Option<Pool>` in `struct Daemon` (`crates/otap-daemon/src/daemon.rs:20-29`, the field at `:24`); a second `pool boot` is refused with `PoolBooted`, "a pool is booted; stop it (`otapctl pool stop`) before booting another" (`daemon.rs:173-175`, the error at `:45-50`); each boot names its own device and arena (`daemon.rs:162-185`); and one engine thread, `dbladed-engine`, runs one loop over that pool (`daemon.rs:243-254`, `:278-288`; E38: the engine thread "owns the `Engine`", `07:1332-1337`). So the loopback test needs one of two shapes, and either is a decision to record (rule 2): one daemon with two pools, which makes `Daemon` hold several pools and either gives the second engine a thread of its own or has one thread tick both, so rule 83's and E38's "the engine thread" becomes one of two threads or the thread of two engines (and, in the first case, the receiving side meets rule 83's remark on a target pool with a thread of its own); or two daemons, each with its own control endpoint (`--control`, `smoke:145`; the endpoint syntax, E38 `07:1323-1325`), arena and device, with the stream between them on a TCP port (the design's `127.0.0.1:7430`, `05:875`). The harness's "`kill -9` of the whole process at 50 random points" (`05:875`) kills both sides at once in the first shape and one side at a time in the second (question 18).
- **The `Net` contract and a lost connection.** `Net` promises "ordered, reliable byte streams to named endpoints ... nothing is dropped silently (a partition holds chunks until it heals)" and offers only `send` and `poll_recv` (`traits.rs:489-501`), with the errors `Busy` and `Unreachable` (`traits.rs:468-476`); E13 fixed that shape, "ordered reliable byte chunks to named endpoints with `Busy` back-pressure" (`07:269-270`). The simulator's `LoopbackNet` keeps the contract, "nothing accepted is ever dropped" (`crates/otap-sim/src/net.rs:1-4`), and its controls are a delay, a partition switch and a queue limit (`net.rs:58-91`). Neither can lose bytes in flight, close a connection or tell an end that one was lost. The design's transport is built around that event: `DeltaStream::open(..) -> Result<Cursor, StreamErr>` and the events `Reconnected(Cursor)` and `Dead(EndpointId)` (`05:697`, `05:683-684`); "a bad header CRC drops the connection" and "a dead connection re-queues its unlanded chunks" (`05:166`, `05:170`), which is what a poisoned decoder needs (S5; trap 30); the adopted tables have "endpoint dead" for the sender (`05-record:3570`) and "connection lost or restart" for the receiver, which takes the "cursor from the last receiver CP" and re-lands the rest (`05-record:3584`). Four requirements need a connection lost with bytes in flight: the harness's "`ss -K` on the connection resumes from the chunk bitmap with duplicates equal to resends" (`05:875`), turmoil's "partition, duplicate, reorder across connections" (`05:871`), the brief's cursor "across disconnects" (`10:623`), and that receiver row. Open: whether `Net` gains a notion of connection (a lost-connection event, a close, a way for the simulator to drop what is in flight), a change to E13's trait to record under rule 2, or the transport keeps its connections above `Net` and the simulator gets a fake of that layer (question 17).
- **The cursor's home.** "a 4 KiB `CursorPage` ... persisted per pipe" (`06:173`). The design says where: "persisted in a 4 KiB page per pipe at every receiver CP" (`05:166`; `05-record:3523`), "kept with the aggregate's metadata (Storage's area)" in the record's Round 1 words (`05-record:786`), and the adopted receiver table resumes from the "cursor from the last receiver CP" (`05-record:3584`; the Round 1 draft, `05-record:877-878`: "cursor persisted at the next receiver CP", "rebuild cursor from the last persisted resume page"), so a reboot "can lose up to 10 s of received chunks, which are re-sent" (`05-record:322`). The superblock carries the `inbound[]` reservation of the sketch (`05:602-603`; `06:338` says the reservation is done), which holds a group's applied state and ages, not a landing bitmap (question 19); and the daemon "holds no durable state at all beyond its command line" (`07:1408-1409`), so a file beside the socket would depart from the design and from E38. Open: which structure of the receiver's CP names the page, a superblock root of its own (as F16's catalogue and F17's stripe list took theirs, E35 `07:1119-1130`) or an entry in a region an existing root names; either is a format change (rule 31).
- **Credits and staging on the Windows host.** `INITIAL_GRANT_BYTES = 64 MiB`, `MAX_STAGING_BYTES = 2 GiB` (S4) against Phase C's "0 / 0" memory line (`05:528`). Open: the staging size and whether staged chunks live in memory or on the target pool before the commit.
- **Handshake details without a cluster**: `Hello` "authenticated by the cluster CA" / "valid cluster certificate, current direction epoch" (`05-record:3578`, `:870`); `Abort(UnknownVol)` "for a volume Raft does not yet know" (`05-record:3581`); `direction_epoch` and `owner_epoch` (`05:674-677`, `05:671`). Open: what Step 6 puts in these fields and whether `VolEvent::Create` creates the volume on the target.
- **Ports and names**: the loopback harness uses `127.0.0.1:7430` (`05:875`); the control port is `127.0.0.1:7421` (E38 `07:1325`); the design's user-visible verbs are `otapctl volume dump --since <snap>` and `restore` (`05:381`, `05:875`); R63's `rel` group is Phase B (`05:469`). Open: the `otapctl` verbs and flags for Step 6's sender, receiver, dump and restore.
- **Throttle**: R62 (`05:467`) and `DeltaStream::throttle` (`05:701`) are in the contract; whether Step 6 implements them is open.
- **The trait signatures.** 7.3's sketch returns synchronously what the as-built engine produces only at a later CP: `DeltaSink::commit(d, when) -> Applied`, "replica CP; durable on return" (`05:710`), and `DeltaSource::pin` returning a `SnapId` (`05:693`). The engine records a snapshot, a pin or a base for the next CP and reports it by an event ("Returns nothing until then", `crates/otap-cp/src/engine.rs:2295-2308`; E36 `07:1185-1189`), a CP spans many ticks (its writes go out in E17's order, `07:393-398`, through E13's asynchronous `Backstore`, "tagged asynchronous writes ... `poll` for completions", `07:264-266`, and E38 says so outright: "A request that needs a consistency point ticks the engine until the event it waits for arrives ... and the data path keeps flowing because those ticks serve it", `07:1337-1343`), the daemon's own waits loop over ticks (`crates/otap-daemon/src/pool.rs:476-520`), and nothing is observable before its CP commits (rule 22). Under rule 83's form (a) a call durable on return either blocks inside a tick or departs from the sketch; under form (b) it is a shipper or receiver thread waiting for the engine thread's CP, a hand-off the daemon does not have (its waits tick the engine themselves). Open: the threading choice first (rule 83), then the signatures (on the engine thread, a request and an event or a poll, as the engine's own API is shaped, recorded as a departure from 7.3) (question 17).
- **Long operations.** A transfer or a catch-up outlasts `--op-timeout` (120 s) and, as one waiting request, holds every control request behind it (trap 11); the protocol has no request that starts a job and returns (`crates/otap-control/src/protocol.rs:44-210`). Open: a start, status and cancel form for the sender, the receiver and `dump --since` (questions 17 and 22).

## 7. Risks, pitfalls and traps

Things an implementer would get wrong without being told, each with the
rule or the precedent that says so.

### 7.1 Gates and tests

1. **`PROPTEST_CASES` is not advisory.** It "overrides an explicit `cases` in a `proptest!` configuration, so no property test is exempt from the gate" (`09:134-137`). A walk written for 64 cases runs 10,000 in the gate; a walk that takes 20 s at 64 cases took 53 minutes (`08:947-949`). Size a new random walk for the gate, and read the variable yourself as the Step 5 walks do (E39 `07:1508-1510`).
2. **`prop_assert!` without a message fails to compile when the condition holds braces** (`08:735-736`; E09 `07:211-213`).
3. **Three clippy lanes and rustdoc are all `-D warnings`**: host, `--target x86_64-unknown-linux-gnu` and the fuzz crate under `--no-default-features` (`09:52-55`). Linux-only code is linted without a Linux host; every new public item, variant and field needs a doc comment (`09:68-69`); lints are "met and fixed rather than allowed" (`08:737-740`).
4. **A test is never weakened and nothing is deleted to make a suite green** (`09:94-95`; E09 `07:217-218`); a reviewer's `bug_*` test is ported in place with the defect's number named (`09:89-95`).
5. **The 10,000-case gate is three hours and runs alone** (`09:130-133`); its seeds differ per run, so one green run is not final (`09:139-140`). Never a stress test beside a build; one cargo process on the machine, WSL included (`09:123-125`).
6. **Hand-computed layout and count expectations need an oracle**: "a 128 MiB file under 2 MiB segments holds 63 segments, not 64, because the first region is the superblock ring" (`08:1009-1011`); "a 1 MiB stripe holds 254 blocks with an 8,192-byte summary" (`08:741-744`).
7. **A harness that issues one request at a time cannot reach real races**; the worst Step 3 defect needed two writes in flight (`08:763-765`). The Step 5 harness waits for `is_quiet()` before `request_cp`, `request_fold` and `request_clean` (`08:866-870`).
8. **`pool format` refuses a non-blank device or file without `--force`** (E39 `07:1493-1494`); the smoke script passes `--force` (`smoke:188`); a harness that reuses a file must too.
9. **The `Io*` requests are a test aid** ("whole blocks as hexadecimal, 256 per request, serialized with every other control request", `06:528-530`), not a data path to drive a transfer test through.

### 7.2 Serialisation and the control plane

10. **Serde's two hidden clauses**: "an internally tagged enum cannot serialize a newtype variant that holds a bare sequence (the list replies are struct variants), and a report field named `kind` collides with the tag" (E38 `07:1390-1395`; `08:1005-1008`); `deny_unknown_fields` on every request, reply and report (E39 `07:1499-1501`). A new `device` or replication request must join the round-trip test of every variant (`07:1390-1391`).
11. **Every control request executes between ticks on the one engine thread, one at a time** (`07:1332-1347`). A request that waits does so by ticking the engine (`wait_for` calls `tick_raw` on every pass, `crates/otap-daemon/src/pool.rs:476-520`), so "the data path keeps flowing because those ticks serve it" (`07:1342-1343`); what stalls is the control plane: "Requests are answered one at a time, so a long operation (a rollback, a shutdown) delays the next request behind it" (`07:1345-1347`), and the wait ends at `--op-timeout` (`ErrorCode::Timeout` after 120 s, `pool.rs:504-511`) or at `otapctl`'s ten minutes (`07:1521-1522`); a signal interrupts it (`07:1515-1517`). What does stall the data path is work done without ticking: a verify that reads a 100 TiB pool in one call, a transfer that blocks on a socket inside a request, a tick that blocks (rule 24). So a long operation (a whole-pool verify, a catch-up transfer) fits neither shape: as one waiting request it holds every control request behind it and fails at the timeout; as one call it stalls the data path. It needs a start-then-poll shape, a request that starts a tick-driven job and returns, a status request and a cancel, which the protocol does not have: every request answers when its operation is done (`crates/otap-control/src/protocol.rs:44-210`; rule 55). Questions 11, 17 and 22.
12. **A non-loopback TCP control address is refused without `--allow-remote-control`** (`07:1517-1518`); a replication listener on TCP has no such rule yet (section 8).

### 7.3 The consistency point

13. **The one-view rule.** "the cleaner's plan, the snapshot set and the volume operations were decided at three different moments of one CP (the plan at the cut, the deletions and operations at the metadata, the in-flight snapshot at the commit) and nothing stopped a request that landed in between" (E39 `07:1530-1535`). A receiver commit, a table delta or a base-pin move that joins a CP must be taken at one of those moments against the same view, or refused (`VolumeBusy`) until the next CP; "A guard that checks 'nothing waits' must count what the CP in flight already took" (`08:1025-1027`).
14. **A CP with clean targets takes no deletion and no volume operation** (`07:1435-1443`); a rollback "refuses deltas of the volume" (`07:1204-1205`); a shrink and a deletion need "a volume with no deltas" (`08:864-865`). Whatever lands a delta on a target volume is such an operation or such a delta.
15. **A fold must not write what its pages already hold** (`08:771-773`): a fold CP writes no delta region (F12); an incremental table that folds is held to the same test, "a counter that is not zero right after the event that resets it is the smell" (`08:771-773`).
16. **Regions freed by a CP are reusable after `N+1` (`N+2` flush-opaque), never at once** (E24 `07:718-721`; E21 `07:580-581`); "A discard is a write that lands late: a segment is free when its discard completes, not when the discard was issued" (`08:781-782`); a free that lands during a CP's staging belongs to the table copy that existed before it (`08:786-788`).
17. **A snapshot's content is everything acknowledged before the request**: the CP that takes it must carry the generation active when it was made, "never one cut before" (`08:789-791`; E31 `07:960-963`). A transfer snapshot taken "now" does not include writes acknowledged after the request.
18. **An empty CP is still a CP** ("a request on an idle engine still produces an empty CP", E17 `07:390-391`): a receiver that commits per delta pays a CP per delta; a snapshot costs a fold (`07:761`), **and a fold is the one CP that can be dropped**: a fold that fails for space is dropped and the snapshot requests it held wait until more segments are free than at the failure; a fold blocked by a map page that does not verify stays blocked until the volume is repaired, answering `Event::SnapshotFailed` to the held requests and `EngineError::MapDamaged` to new ones; only a shutdown's fold is retried at once, as a plain CP (E31 `07:953-960`; rule 43). A transfer snapshot per delta (section 4.8) and a table delta that folds (scope B) inherit both outcomes: a sender must handle `SnapshotFailed` on the snapshot it meant to pin, and a fold-driven table delta must not wedge a nearly full pool the way E31's context describes a forced fold did (`07:946-947`).

### 7.4 Durability and sets

19. **Durable before observable** (`09:82-85`): a volume the receiver creates, a base it advances: neither is served or reported until the CP that records it commits; "the two defects that broke it both let a crash undo something a client had already seen" (`08:760-762`). Two things fall outside the rule by design. A chunk's `Landed`, which the adopted receiver table sends "when its stripes are written" (`05-record:3582`), before the receiver CP; a receiver restart takes the "cursor from the last receiver CP" (`05-record:3584`) and "re-lands whatever its last CP did not record" (`05:166`), so holding `Landed`, and its credits, until a CP would depart from the design. And a re-attached device, which no CP records: the daemon "holds no durable state at all beyond its command line" (`07:1406-1409`).
20. **Intersection, never assignment**, for a set that says what the disk guarantees (`09:86-88`): "Twice now a durability bug was a union or an assignment where an intersection was meant" (`08:757-759`).
21. **A rewind holds the volumes even when the arena re-attached whole** (E17 `07:425-428`): a re-attach test must separate "arena whole" from "boot rewound"; a heap arena never re-attaches (`06:512-514`; `smoke:265-269` asserts the hold).
22. **Every byte under a CRC includes the structures the code trusts about itself** (`08:766-767`); a cursor page, a device record, a table delta page all carry their own seal and are verified before use (rule 18).
23. **"When an image is ambiguous (zeros after a punch over a write), the checker's prefix must be the largest consistent operation number"** (`08:774-776`); a replication checker comparing images across two pools inherits the same ambiguity, and `diff` reports a hole punched over an unmapped block (rule 47).

### 7.5 Snapshots, pins and the cleaner

24. **The cleaner moves a snapshot's blocks and rewrites its tree** (E37 `07:1284-1286`); "nothing on disk says a block moved" (`07:1290-1292`). An address taken at `describe()` and read at `read_chunk` time is a drained, possibly discarded, segment unless the cleaner is held off or the address is re-resolved (section 4.8).
25. **`SnapshotLimit` counts pending requests** (E36 `07:1193-1194`): sixteen reserved slots per volume for "replication baselines and divergent heads"; `set_replication_base` clears the old base's pin "in the same CP" but does not delete it (`07:1186-1189`); a sender that pins a snapshot per delta without deleting superseded bases wedges at the seventeenth.
26. **`snapshot_diff` refuses a base that is not older than the snapshot** (`SnapshotOrder`, `07:994-995`) and a damaged snapshot refuses reads and diffs (`07:925-926`); **snapshot ids are reused across a rewind**, key by uuid (`06:555-557`).
27. **Rollback, resize and deletion refuse while a snapshot request of the volume waits or rides the CP in flight** (`07:1444-1450`); the daemon's `snapshot create` waits for its own uuid, "not any snapshot of the volume" (`07:1520-1521`).
28. **A damaged snapshot's deletion releases nothing** (`07:1172-1174`); a deletion next to a damaged newer neighbour releases nothing (`07:1465-1466`); a verify pass that reconciles liveness must expect these leaks and the boot's once-per-tree count of shared metadata (`08:1054-1057`).

### 7.6 The stream and the transport

29. **The builder refuses what the parser refuses** (S3): a sender must never construct a frame its peer's decoder would drop; `Cursor::new` caps credits "as a constructor convenience; a public field set over a bound afterwards is refused at the boundary" (`07:126-128`); `Cursor::to_page` returns a `Result` (`07:124-125`).
30. **A bad header poisons the decoder for good** (S5 `07:135-138`): "it repeats that error on every call, drops further input"; the connection must be torn down and resumed from the cursor, never "retried" (the design: "a bad header CRC drops the connection", `05:166`; a `Net` cannot drop one, section 4.8, "The `Net` contract and a lost connection"). A bad payload CRC does not poison: the receiver answers `Abort(Corrupt, idx)` and the sender resends (`07:138-141`); the record's sender table re-reads from disk and verifies CRCs on the "third `Abort(Corrupt, idx)`" (`05-record:3567`), which 3.3 puts as "three `Abort(Corrupt, idx)` for one chunk make the sender re-read the stripe from disk bypassing cache and verify every 4 KiB CRC" (`05:166`).
31. **`drain` never loses a decoded frame**: an error after some frames is held for the next call, and `needed()` is zero while one is held (`07:141-143`); "A transport-facing accessor (`needed`, `pending`) is part of the protocol: its documented meaning has to hold in every decoder state, including the error states" (`08:751-753`).
32. **Delta byte counts are raw image bytes** bounded between `chunks` smallest and `chunks` largest stripe images, and `DeltaEnd.digest` is BLAKE3 over the chunk images *in index order* (S6 `07:144-148`): a sender that resumes out of order must still hash in index order; a receiver that recomputes must land every chunk before it can check.
33. **`MAX_WIRE_RANGES` truncates a fragmented resume to 4,096 ranges and the rest is resent** (S4 `07:130-132`): a test of 7.7 #8's "resends equal the duplicate count" (`05:841`) or of the loopback harness's "duplicates equal to resends" (`05:875`) must count the truncation's resends as legitimate.
34. **Nothing proportional to an untrusted count before the check** (S10), proved by a counting allocator in the stream suite (`07:162-163`; E09 `07:218`): a receiver that reserves staging from `DeltaBegin.chunks` or `bytes` checks them against the bounds and its free staging first.
35. **No sockets in `otap-stream`** (`09:77`); the sockets are `dbladed`'s `Net`; a transport that leaks "sockets, TLS, codec or timers" into the engine breaks the trait rule that lets the simulator drive it (`09:77-79`; `05:696`).
36. **`StripeKind::Applied` exists only in the format crate** (defined at `stripe.rs:59-60`, parsed by `from_u8` at `:72`, asserted at `:718` and `:722`, named in F4 at `format/lib.rs:101`; nothing outside `otap-format` references it); the engine's stripe builder writes `Ingest` "group 0" (E17 `07:393-394`); the boot verifies every stripe a CP lists (F17) by summary CRC *and identity, the CP's nonce included* (`07:1131-1133`), the identity being the whole `StripeId`: aggregate, `lseg`, `stripe_idx`, `cp_seq` and `cp_nonce` (`crates/otap-format/src/stripe.rs:274-285`, checked by `parse_expected`, `:590-593`, against the booting CP's own, `crates/otap-cp/src/boot.rs:645-653`). A stripe the receiver lands must carry the receiver's identity in its summary (its aggregate, where it lands, the receiver CP's sequence and nonce), not the sender's, or the boot tears the commit; a sender image with only its nonce patched still tears.
37. **The frame header is never stored** (F3 `format/lib.rs:97-98`); a file sink that stores frames stores the *wire* form, which is the design's intent ("the backup format and the wire format are one", `05:715`), but it is not a pool image and `restore` must decode it like a peer.

### 7.7 ublk and the daemon

38. **`addr = 0` on every fetch and commit under `USER_COPY`** (`ublk.rs:830-833`; the driver answers `-EINVAL` to a user-copy fetch that carries an address, `ublk_drv.c:1754-1757`); **every fetch of a queue must come from the one task that will serve it.** E28 and E38 put this as "the task that issued its first fetch" (`07:863-864`; `07:1353-1354`), which is right in effect and inexact about which fetch makes the binding. In the saved 6.12 driver the binding is made by the fetches, not by the control commands, and by the last one: `ublk_mark_io_ready` counts the fetch and sets `ubq->ubq_daemon = current` only when the count reaches the queue depth (`ublk_drv.c:1621-1636`, called from the fetch path at `:1761`; a queue is ready when `nr_io_ready == q_depth`, `:1499-1502`). Three task checks then decide what another task can do. (1) Commands: `__ublk_ch_uring_cmd` (`:1683`; the `.uring_cmd` file operation `ublk_ch_uring_cmd`, `:1864` and `:1988`, reaches it through `ublk_ch_uring_cmd_local`, `:1838-1855`) tests `if (ubq->ubq_daemon && ubq->ubq_daemon != current) goto out;` (`:1706-1707`), which accepts a `FETCH_REQ` from any task while `ubq_daemon` is still `NULL` and refuses every command from another task afterwards. (2) Dispatch: `ublk_queue_cmd` puts each request on the queue's list and, when the list was empty, schedules the list's task work through that request's tag command, `io_uring_cmd_complete_in_task(io->cmd, ...)` (`:1198-1207`), so the whole batch runs in the task that issued that command (`ublk_forward_io_cmds`, `:1179-1188`); `__ublk_rq_task_work` aborts every request of the batch when `current != ubq->ubq_daemon` (`:1121-1124`), and `__ublk_abort_rq` requeues it under `USER_RECOVERY` and ends it with `EIO` otherwise (`:1090-1098`); a request that passes is handed to the server through its own tag's command (`ubq_complete_io_cmd`, `:1072-1086`, called at `:1176`), so it lands on the ring of the task that issued that command, and only the bound task may commit it (check 1). (3) Cancel: `ublk_uring_cmd_cancel_fn` refuses a command whose task is not the bound one (`WARN_ON_ONCE(task && task != ubq->ubq_daemon)`, `:1480-1482`). So a tag fetched by another task before the queue completes is accepted and never served, and a batch it opens aborts the bound task's requests with it. A mock written to "first fetch" refuses that fetch where the driver accepts it; a mock written to "the task whose fetch completes the queue serves it" alone would serve a split queue the driver cannot serve, which is looser than the driver; the mock, and the E-entry of question 7, must carry all three checks, and the **recovery fetches** must all be issued from the engine thread that will serve the queue, because the last one binds it and every tag fetched elsewhere is dead. The process-level limits are separate: `/dev/ublkcN` opens once at a time (`UB_STATE_OPEN`, set by every open, `test_and_set_bit` in `ublk_ch_open`, `:1301-1310`, `:1306`, and cleared only at release, `:1312-1318`, `:1316`) and the command buffer maps for one `mm` (`ublk_ch_mmap` `:1330-1333`); no I/O command consults either, and of the control commands only `START_USER_RECOVERY` does (below); a task of another process that holds the same open file (a forked child, a descriptor passed over a Unix socket) meets no owner test, only the task checks above. **What becomes of the dead server's requests** (OpenTAP sets `USER_RECOVERY` without `REISSUE`, `device.rs:95`; section 4.7): when the dead server's commands are cancelled, `ublk_abort_queue` (`ublk_drv.c:1387-1408`) marks every request the server had taken and not committed `UBLK_IO_FLAG_ABORTED` and fails it through `__ublk_fail_req` (`:1061-1070`), which requeues it when `REISSUE` is set (`:1066-1067`) and otherwise drops it to `__ublk_complete_rq`, which answers `BLK_STS_IOERR` for an aborted request (`:999-1001`); a request not yet handed to the server is requeued under `USER_RECOVERY` (`__ublk_abort_rq`, `:1090-1098`, reached from the task work of a dead task, `:1121-1124`, and from `ublk_queue_rq` while the queue is cancelling, `:1274-1277`) and waits for the new server; a request the server had committed has left the driver. A `STOP_DEV` of a device with `USER_RECOVERY` unquiesces it with `force_abort` set (`ublk_stop_dev`, `:1593-1618`; `ublk_unquiesce_dev`, `:1572-1591`), and `ublk_queue_rq` then ends every requeued and new request with `BLK_STS_IOERR` (`:1271-1272`): reaping a quiesced device fails the I/O it holds (a `LIVE` one it first quiesces, waiting until its server has committed every request it holds, trap 42 (d)). **`END_USER_RECOVERY` is a `/dev/ublk-control` command with no task check** (`ublk_ctrl_end_recovery`, `:2738-2774`, dispatched at `:2964-2965` by `ublk_ctrl_uring_cmd`, `:2896`; the control path's only permission check is `ublk_ctrl_uring_cmd_permission`, `:2821-2894`, called at `:2927`: `CAP_SYS_ADMIN` for a device created without `UBLK_F_UNPRIVILEGED_DEV` (`:2831-2842`), which is OpenTAP's case (`device.rs:95`), or, for an unprivileged device, a permission check on the char device path (`ublk_char_dev_permission`, `ublk_drv.c:2882`, under `MAY_READ | MAY_WRITE` for both recovery commands, `:2874-2876`); no function from `:2600` to the end of the file reads `current`): it waits on `ub->completion` until every queue has a fetch on every tag (`:2747-2749`, interruptible, `-EINTR`), then requires the device still `UBLK_S_DEV_QUIESCED` (`-EBUSY` otherwise), stores the pid from `data[0]` as `ublksrv_pid`, unquiesces the request queue, kicks the requeue list and sets `UBLK_S_DEV_LIVE` (`:2754-2770`). "`START_DEV` waits until every queue has a fetch on every tag" (E28 `07:862-863`), and so does `END_USER_RECOVERY` (`ublk.rs:811-813`; `ublk_drv.c:2747-2749`): one missing fetch wedges the command, and the thread that owes a fetch must not be the thread blocked in the command. `START_USER_RECOVERY` (`ublk_ctrl_start_recovery`, `:2694-2736`) answers `-EBUSY` while anyone holds `/dev/ublkcN` open (`UB_STATE_OPEN` set, the new server's own open included) or the device is not `QUIESCED` (`:2706-2723`); it then resets every queue (`ublk_queue_reinit`, `:2669-2692`: `nr_io_ready = 0`, `ubq_daemon = NULL`, every tag's flags, command and address cleared, so the recovery fetches remake the binding the same way, at the last one), clears `ub->mm` so the new server can map the command buffer, zeroes `nr_queues_ready` and re-arms the completion (`:2725-2731`). So the recovery's order is fixed: `START_USER_RECOVERY` first, while nobody holds `/dev/ublkcN`; then the new server opens `/dev/ublkcN` and maps the descriptors (the reset of `ub->mm`, `:2727-2728`, is what lets a new process map them, `:1330-1333`); then a fetch on every tag from the thread that will serve the queue; then `END_USER_RECOVERY`, which completes only once every tag has its fetch. A mock that lets the new server open `/dev/ublkcN` and then accepts its `START_USER_RECOVERY` accepts what the driver refuses (`-EBUSY`). A `FETCH_REQ` is refused with `-EBUSY` once its queue is ready and refused on a tag the server already owns (`:1734-1745`). These are the driver's rules trap 40 says must be written down before the mock models them; a mock that demanded `END_USER_RECOVERY` from the serving thread would defend against a ghost.
39. **A stale completion must be dropped by its generation** (`07:843-845`); after a re-attach the old process's tags are the driver's to reissue or abort, and "a tag whose fetch fails is retired" (`06:562`).
40. **A mock must follow the driver's rules**: two Step 4 "defects" were the mock delivering "a request on an aborted tag, a request the abort had already withdrawn" (`08:777-780`); the driver's recovery rules live in the saved sources, not in any document (`08:1037-1039`), and must be written down as E28 wrote its facts (`07:858-867`) before the mock models them. **And what the mock asserts is checked against those sources, not cited from memory**: "The kernel facts a worker cites from memory must be checked against the saved sources before they are asserted in tests" (`08:749-750`). Every rule the scope A mock and its tests assert (trap 38's list) carries its `ublk_drv.c` line; this map's own first reading of the driver missed the dispatch check (`ublk_drv.c:1121-1124`), which is the lesson's point.
41. **The device bounds its requests by half the arena** (`07:1359-1360`; `DeviceSpec::for_arena`, `07:998-999`), and **a re-attached device keeps every parameter it was started with.** `START_DEV` builds the queue limits from the parameters (`max_hw_sectors`, the block sizes, `ublk_drv.c:2193-2204`), allocates the disk with them (`:2254`) and sets the capacity (`ublk_apply_params`, `:2266`; `set_capacity`, `:523`); `END_USER_RECOVERY` applies nothing (`:2738-2774`), and `SET_PARAMS`, refused only on a `LIVE` device, stores on a quiesced one values that nothing applies before a `START_DEV` (`:2651-2663`; `05-record:2326`, and `:2331`: "the END_USER_RECOVERY path does not re-apply params"). So an arena of another size at restart is a mismatch to detect, and so is a volume whose size on disk differs from its device's: the daemon's resize recreates the device only after the resize's CP commits (`crates/otap-daemon/src/pool.rs:925-932`; E36 `07:1208-1213`; E38 `07:1358`), so a crash between the two leaves a quiesced device at the old size, which a restarted daemon must delete and recreate rather than recover; a rollback to a snapshot of another size (`07:1202-1203`) takes the device down first (`pool.rs:1083-1089`; E38 `07:1355-1356`) and leaves none.
42. **The daemon's shutdown path deletes its devices** (`07:1356-1357`, `07:1423-1424`); a reaper that runs in a live daemon must not delete the devices that daemon is about to re-attach, nor another process's live devices. Four driver rules govern what a reaper does (the saved 6.12 `ublk_drv.c`). (a) **`DEL_DEV` is `STOP_DEV` and then a wait.** `ublk_ctrl_del_dev` runs `ublk_remove` (`ublk_drv.c:2522-2524`), which calls `ublk_stop_dev` first (`:2162-2170`), so it fails a quiesced device's held I/O exactly as `STOP_DEV` does (trap 38). The synchronous form, which `CtrlCommand::del_dev` builds (`UBLK_U_CMD_DEL_DEV`, `ublk.rs:752-756`) and the driver dispatches with `wait == true` (`ublk_drv.c:2946-2948`), then waits, interruptibly, until the device's number is freed (`:2546-2547`); that happens only when the device's last reference goes (`ublk_cdev_rel`, `:2094-2103`, freeing the number at `:2086-2092`), and the disk holds a reference from `START_DEV` (`:2272`) until its own release (`ublk_free_disk`, `:693-699`), that is until the last holder of `/dev/ublkbN` lets go ("a synchronous DEL_DEV likewise waits for that release", `05-record:2331`). Any open `/dev/ublkcN` holds it as well: `ublk_ch_open` takes no reference (it finds the device by `container_of` on the inode's `cdev`, `ublk_drv.c:1301-1310`), the `cdev` is embedded in the device that `ublk_cdev_rel` frees (`kfree`, `:2094-2103`), and what keeps both alive while the character device is open is the reference `cdev_device_add` (`:2122`) gives the `cdev` on its parent, `cdev_dev`, which the cdev core drops only after the last file of `/dev/ublkcN` is released (the driver relies on it: "The ublk char device won't be closed when calling cancel fn, so both ublk device and queue are guaranteed to be live", `:1460-1462`). So the wait also lasts while anything holds `/dev/ublkcN`: the server's descriptor, a mapping of the command buffer, a ring's commands in flight. A server that sends a synchronous `DEL_DEV` for a device it still holds waits on itself, and since `execute` retries the interrupted wait (`ublk.rs:1251`) its thread hangs for good. As built, `create_device` does exactly that when `START_DEV` fails: it calls `device.delete()` while `front` still holds the queue (`crates/otap-daemon/src/device.rs:26-37`; the queue holds the `UblkChar`, the ring and the mapping, `ublk.rs:1299-1306`); `destroy_device` escapes only because it drops the front door first (`crates/otap-daemon/src/device.rs:50-53`); and the recovery fall-back of section 4.7 and question 6 (give the device up, delete it, recreate it) meets the same wait unless the new server first drops its queue or sends `DEL_DEV_ASYNC`. The cdev core's parent reference, and a file's lifetime under a mapping or a command in flight, are `fs/` and io_uring code, not among the saved sources, so they are to be checked there before a test asserts them (`08:749-750`). The driver runs a control command in an io-wq worker (it answers `-EAGAIN` under `IO_URING_F_NONBLOCK`, `ublk_drv.c:2904-2905`), but `UblkControlRing::execute` waits for the completion (`submit_and_wait(1)` until the CQE, `ublk.rs:1248-1270`), so a `DEL_DEV` issued on the engine thread, where the daemon runs every control request and creates and deletes its devices (E38 `07:1335-1337`, `07:1352-1358`), stalls the data path for as long as anything holds the device open. The driver's `DEL_DEV_ASYNC` skips that final wait (`ublk_drv.c:2949-2950`) but not the stop, whose own wait on a `LIVE` device is rule (d); `otap-sys` defines its opcode (`ublk.rs:135-137`) and has no named builder for it, as it has for `DEL_DEV` (`CtrlCommand::del_dev`, `ublk.rs:752-756`), but the public `CtrlCommand::new` ("Any control command for `dev_id`, with an optional buffer", `ublk.rs:722-742`) builds it, as `otap-sys`'s own test does (`CtrlCommand::new(ublk::UBLK_U_CMD_DEL_DEV_ASYNC, 3, None)`, `crates/otap-sys/tests/sys_tests.rs:503`), and `UblkControlRing::execute` takes any command (`ublk.rs:1213`). (b) **`ublks_max` counts every device until it is deleted.** It defaults to 64 (`ublk_drv.c:494`); `ADD_DEV` counts the device (`ublk_add_chdev`, called at `:2484`, counting at `:2126`) and only `ublk_remove` uncounts it (`:2169`), which a delete reaches (`DEL_DEV` or `DEL_DEV_ASYNC`, `:2522-2524`) and the module's unload runs for every device (`ublk_exit`, `:3031`; a reload starts the count afresh), so while the module stays loaded, always for a built-in driver (rule (c)), only a delete frees a slot; at the limit `ADD_DEV` fails with `EACCES` for any caller, `CAP_SYS_ADMIN` included (`:2417-2419`; `05-record:2331`). Quiesced devices left by killed daemons therefore use the limit up: each run of the smoke script leaves one (its `SIGKILL` restart, `smoke:251-262`), and nothing in the tree sets the limit (no `ublks_max` in the crates, the scripts, `BUILDING.md` or `README.md`; only the design names it, `05:546`, `05:873`). (c) **A built-in driver** (the `CONFIG_BLK_DEV_UBLK=y` of the kernel the brief's script builds, `10:595`) cannot be reloaded, which removes E38's "or the module is reloaded" (`07:1422-1423`), and takes its limit from the kernel command line or `/sys/module/ublk_drv/parameters/ublks_max` (`ublk_drv.c:3058`), not from `modprobe` (section 4.9). (d) **On a `LIVE` device, `STOP_DEV` and both deletes wait until its server has committed every request it holds.** Under `USER_RECOVERY` (`ublk_can_use_recovery`, `ublk_drv.c:688-691`, true for OpenTAP's devices, `device.rs:95`), `ublk_stop_dev` quiesces a `LIVE` device before anything else (`ublk_drv.c:1600-1602`): `__ublk_quiesce_dev` (`:1547-1556`) runs `ublk_wait_tagset_rqs_idle` (`:1532-1545`), which sleeps in a loop, with no signal check and no timeout, until `ublk_check_inflight_rq` (`:1521-1530`) finds no started request, all under the device's mutex (`:1597`). `STOP_DEV` reaches it through `ublk_ctrl_stop_dev` (`:2560-2566`), `DEL_DEV` and `DEL_DEV_ASYNC` through `ublk_remove` (`:2162-2170`; the async form is only `wait == false`, `:2946-2951`), and a delete holds the host-wide `ublk_ctl_mutex` while it waits (`:2518-2530`), the mutex every `ADD_DEV` takes too (`:2413`). So on a `LIVE` device whose server is wedged all three never return; issued on the engine thread, they stop the data path for good, since `execute` waits for the completion and retries an interrupted wait (`ublk.rs:1248-1270`, `:1251`); a delete also holds up every later `ADD_DEV` and `DEL_DEV` on the host, any daemon's; and a server that stops its own `LIVE` device while it holds an uncommitted request deadlocks, because the thread that would commit it is the one waiting. A quiesced device skips the wait (the test is `state == UBLK_S_DEV_LIVE`, `ublk_drv.c:1601`) and goes straight to trap 38's `force_abort`; a synchronous delete's own final wait, rule (a), still applies to it. The as-built teardown does not meet the wait: the front door answers `ENODEV` "while the requests the engine holds drain, then `STOP_DEV` and `DEL_DEV`" (E38 `07:1355-1358`), and `destroy_device` drops the front door, and with it the queue's ring, before `UblkDevice::delete` sends `STOP_DEV` and `DEL_DEV` (`crates/otap-daemon/src/device.rs:50-53`; `crates/otap-ublk/src/device.rs:196-219`; the queue moved into the front door at `:242-247`); the ring's teardown cancels its fetches, which the driver marks cancelable (`ublk_prep_cancel`, `ublk_drv.c:1668-1681`, called at `:1798`) and takes through `ublk_ch_uring_cmd`'s `IO_URING_F_CANCEL` branch (`:1864-1869`) into `ublk_uring_cmd_cancel_fn` (`:1464-1497`), whose `ublk_abort_requests` (`:1410-1440`) fails every request the server still held (`ublk_abort_queue`, `:1387-1408`). The io_uring half of that chain, the cancel issued when a ring is torn down, is not among the saved sources (the folder keeps `io_uring.h`, `io_uring_h` and `rsrc.c`, not the core's command code), so it is to be checked before a test asserts it (`08:749-750`). A Step 6 path that stops a `LIVE` device while its queue ring is open, a reaper's or a recovery's, meets the wait.
