## 3. Invariants and rules in force

Rules the Linux halves and the smoke test rely on today; each with where it is stated or enforced.

- **R-L1. `otap-sys` is the only crate with `unsafe`; thirteen blocks, all Linux-only; the fallback has none** (otap-sys/src/lib.rs:1-7, 41-88; the count is lib.rs:53, "Thirteen blocks, all Linux-only; the fallback contains none", inventoried at 55-88). E08 (docs/07:178-189) states the only-crate rule, but its count is stale: "Five blocks exist, all Linux-only" (docs/07:178-179) is the count when E08 was written, before Step 3 (it keeps `libublk` "until Step 3 decides", docs/07:200-201); E27 added "five new `unsafe` blocks" in `block.rs` (docs/07:818-819; inventory items 6-10) and the inventory's items 11-13 are the `ublk` control ring and queue (lib.rs:81-88). Every engine crate is `#![forbid(unsafe_code)]` (otap-backstore lib.rs:27, otap-ublk lib.rs:41, otap-daemon lib.rs:33, otap-geom lib.rs:34). A Step 6 recovery path that needs a new kernel interaction (a new SQE push, a new mmap) must add its block to `otap-sys` and its proof to the inventory at lib.rs:52-88; `clippy::undocumented_unsafe_blocks` is denied workspace-wide (Cargo.toml:86).
- **R-L2. Two platforms, one API.** Linux code under `cfg(target_os = "linux")`, a fallback under `cfg(not(...))`, and items whose signatures name Linux types exist on Linux only (otap-sys/src/lib.rs:22-39; E08 docs/07:181-184). The workspace must keep building on Windows and type-checking for `x86_64-unknown-linux-gnu` under `clippy -D warnings` (BUILDING.md:52-55).
- **R-L3. No engine crate names an opcode or a command the startup allowlist does not contain** (otap-sys/src/lib.rs:4-7; probe.rs:4-6 says "issues"). The allowlist holds io_uring opcodes and ublk feature bits (`Allowlist { opcodes, ublk_features }`, probe.rs:134-137), so for ublk the rule can only mean the features and the commands they gate, such as the recovery pair under `UBLK_F_USER_RECOVERY` (my reading; neither text says what "command" covers). E08 states a stronger rule, "the startup `Allowlist` is the only place an opcode or ublk feature is named" (docs/07:188-189), and that one is already false: `otap-ublk` names `UBLK_F_USER_COPY | UBLK_F_USER_RECOVERY | UBLK_F_CMD_IOCTL_ENCODE` at `ADD_DEV` (device.rs:95), `BlockRing` names `opcode::Write` and `opcode::Fsync` (block.rs:240, 268), and `uring.rs` and `ublk.rs` name every opcode and feature bit as data (uring.rs:18-138, ublk.rs:275-298). Today's names satisfy the crate docs' rule: the features at device.rs:95 are exactly `REQUIRED_UBLK_FEATURES` (probe.rs:37-38), and the opcodes issued, `WRITE` and `FSYNC` (block.rs:240, 268), `URING_CMD` (ublk.rs:1083, 1153) and `READ` in the still uncalled `user_copy_read_sqe` (uring.rs:525), are all in `REQUIRED_OPCODES` (probe.rs:25-33). Nothing enforces it, though: the daemon never consults the allowlist (checked here, section 2.2), so no gate stops a new name. The Step 6 consequence: setting `UBLK_F_USER_RECOVERY_REISSUE` at `ADD_DEV` (5.1's open design point; section 8, question 2) names a feature `REQUIRED_UBLK_FEATURES` lacks, so under lib.rs:4-7 it must be added there (and to its doc comment, probe.rs:35-36), and once the startup gate is wired (5.2; question 7) it becomes a boot requirement, which 6.12 meets (`UBLK_F_ALL` includes it, kernel 59). E08's sentence should be reworded to the crate docs' rule (its `unsafe` count is stale too, R-L1).
- **R-L4. The arena file is never truncated and is exclusively locked for the mapping's life** (hugetlb.rs:63-64, 79-98, 336-355, 371-389); it must be on a hugetlbfs mount whose page size matches, checked with `statfs` before anything is created and `fstatfs` on the file (hugetlb.rs:84-88, 331-345, 437-458). The daemon passes exactly `--arena-bytes` bytes, a multiple of 2 MiB and at least 64 MiB (units.rs:7-14, 50-71; arena.rs:11, 39). Re-attach is the engine's: `Arena::can_attach`/`Arena::attach` against `cfg.agg_id` (engine.rs:1687-1709); a wrong aggregate fails the boot (1696-1701); an unusable arena is formatted anew and reported as `arena_lost` (1702-1708; E16 docs/07:362-370 says what a re-attach keeps, drops and reports).
- **R-L5. A heap arena dies with the process**: a crash under `--heap-arena` is a dirty boot that holds the write-active volumes under nvfail (hugetlb.rs:119-125; S5-1 at docs/07:1049-1052; dbladed.rs:30-31; docs/06 §8). The smoke test's `--heap-arena` branch asserts exactly that (linux-smoke.sh:265-269).
- **R-L6. Block-device I/O is `O_DIRECT`, whole 4 KiB pages, through staged slots the kernel reads until the completion is reaped** (block.rs:7-13, 155, 191-204, 245-252, 344-349, 406-425; E27 docs/07:806-814). The pool is dropped only after the ring: `ring` is declared at block.rs:133 before `pool` at 135 and Rust drops fields in declaration order, which the SAFETY comment at 250-252 relies on ("the pool is dropped only after the ring (field order) once nothing is outstanding"); `Drop` (406-425) reaps everything outstanding first and leaks the pool's pages if it cannot.
- **R-L7. Barrier semantics on Linux**: `flush` is `IORING_OP_FSYNC` + `FSYNC_DATASYNC`; `commit` and `write_intent` are one whole stripe written with `RWF_DSYNC`; the engine orders A before B and the driver completes in reaping order (block.rs:262-281; backstore/uring.rs:189-224; E27 docs/07:810-814; lib.rs:12-25 of otap-backstore for the trait contract: `Busy` means nothing was done, a `commit`/`write_intent` is durable when reported, a `flush` covers every write completed before it was submitted).
- **R-L8. The ublk device is created with `USER_COPY | USER_RECOVERY | CMD_IOCTL_ENCODE`, one queue, 128 tags, 4 KiB blocks, a volatile cache with FUA, discard limits, a fetch on every tag before `START_DEV`** (device.rs:79-97, 127-177, 184-190; E28 docs/07:849-853). Every fetch and commit carries `addr = 0` (ublk.rs:830-833, 847-876). `START_DEV` and `END_USER_RECOVERY` carry the server's **positive** pid in `data[0]` (ublk.rs:415-417, 758-766, 811-819; kernel/ublk_drv.c:2208-2209 refuses pid <= 0).
- **R-L9. A queue's commands come from the thread that issued its first fetch** (otap-daemon device.rs:9-11, otap-ublk device.rs:239-241, ublk.rs:1293-1298; kernel/ublk_drv.c:1621-1636 pins `ubq->ubq_daemon = current` when the last tag is fetched, and 1706-1707 refuses any other task with `-EINVAL`). The daemon therefore creates, serves and tears down every device on the engine thread (daemon.rs:243-254; pool.rs:678-709; E38 docs/07:1352-1358). **A re-attach must issue the recovery fetches from the engine thread too.** The rule binds the fetches and commits only (the task check, kernel 1706-1707, is in the char device's I/O path), not the control commands, and the code's one-thread design does not survive `START_DEV`: `execute` waits for it synchronously on that thread (ublk.rs:1248-1270), while for a root daemon the kernel's partition scan in `START_DEV` reads through the queue only that thread serves, so it never completes (7.2, "`START_DEV` on the serving thread"; one link unverified). The fix keeps the fetches and the serving on the engine thread and moves only the wait for `START_DEV` off it.
- **R-L10. A tag the driver aborts (`UBLK_IO_RES_ABORT = -19`) is never fetched again** (ublk.rs:167-170, 1437-1440; device.rs:297-303; frontdoor.rs:37-41, 138-139).
- **R-L11. Device lifecycle rule**: a device exists for every present, online volume while `ublk` is on; it is created at boot, `volume create` and `volume online`, dropped at `volume offline`, before a rollback, at `pool stop` and at exit, and recreated after a resize; dropping means `set_offline(true)`, drain, `STOP_DEV`, `DEL_DEV` (pool.rs:675-739, 842-845, 895-911, 929-932, 1083-1112; E38 docs/07:1352-1361). `volume delete` only forgets the path (pool.rs:888) because deletion needs the volume offline. A clean stop deletes its devices; a crash leaves them (E38 docs/07:1419-1424).
- **R-L12. The daemon holds no durable state of its own** (otap-daemon lib.rs:29-31; E38 docs/07:1406-1409). Anything a re-attach needs to find its devices must come from the pool, the arena file, or the kernel (the `ublksrv_flags` field the driver stores verbatim: ublk.rs:462-463; kernel/ublk_drv.c:2434 copies the whole `info`, 2578 returns it).
- **R-L13. The Unix socket is bound before the pool boots, stale sockets are taken over, live ones refused, mode 0660, removed on drop** (dbladed.rs:162-176; server.rs:181-219, 172-179; E38 docs/07:1385-1386). The default socket directory `/run/opentap` must exist (server.rs:200-210); `/run` is tmpfs on Debian, so it is gone at every VM boot (unverified: general knowledge).
- **R-L14. A block device goes through the geometry planner and `UringBackstore`; a file never does** (backstore.rs:237-239, 304-336; E38 docs/07:1373-1376). The planner reads `/sys/block/<file_name>` (backstore.rs:312-316; geom.rs:97-99), requires `size`, `queue/logical_block_size` and `queue/rotational` (geom.rs:360-365, 379), and refuses a non-zero `alignment_offset` (geom.rs:640-650).
- **R-L15. The recorded geometry wins at boot; an override that disagrees is refused; the device must hold the recorded capacity** (backstore.rs:263-292 for files; for a block device the planner's geometry is used as planned and `UringBackstore::open` checks only that the device is at least the profile's capacity, uring.rs:60-70; `probe_superblock` supplies the identity, pool.rs:222-231). Note the asymmetry: `open_block` never receives `recorded` (backstore.rs:304-336), so a loop device whose sysfs facts changed between format and boot (for example `rotational`) is planned afresh; the engine then checks the superblock's geometry itself (E29/E30, outside my scope).
- **R-L16. Smoke-test text contracts**: `pool status` prints `  last boot:    <last_boot>` and `  arena:        <kind>, ...` (render.rs:180-184, 208); `volume show` prints `  state:      online|offline|nvfail:<cause>|pending:<op>|creating` and `  device:     /dev/ublkbN|-` (render.rs:77-79, 231-246); `--json volume show` carries `"device": "/dev/ublkbN"` (protocol.rs:240-241, pool.rs:636-641); the daemon's log says `dbladed: pool <dev> stopped cleanly` on a clean stop driven by a signal or the loss of the last handle (daemon.rs:217-225, 281-283, 298-309; the smoke test's `kill -TERM` path), but not after `daemon stop` or `pool stop`, which stop the pool inside their request arms (200-207, 196-199) without that line and `dbladed: volume N is /dev/ublkbN` / `left` (pool.rs:696, 731); the boot line starts `clean boot at cp` or `dirty boot at cp` and contains `arena re-attached (N blocks replayed)` when the arena came back (pool.rs:346-357).

- **R-L18. Kernel rules the recovery must obey (v6.12, verified in the saved sources):**
  - `UBLK_F_ALL` is the feature set, and `GET_FEATURES` reports `UBLK_F_ALL & ~UBLK_F_SUPPORT_ZERO_COPY` into exactly 8 bytes (kernel/ublk_drv.c:55-63, 2776-2789; ublk_cmd.h:59).
  - Control commands need `IO_URING_F_SQE128` (2909-2910), `CAP_SYS_ADMIN` for a privileged device (2831-2833), and a device id that exists (`-ENODEV`, 2921-2925); unknown commands answer `-ENOTSUPP` (2967-2969); `ublks_max` (default 64) bounds the device count with `-EACCES` (494, 2418, 3058-3059).
  - `ADD_DEV` with `dev_id = U32_MAX` takes the **lowest free id** from 0 (2063-2077, 2430); flags are masked to `UBLK_F_ALL`, `CMD_IOCTL_ENCODE | URING_CMD_COMP_IN_TASK` forced on, zero-copy forced off, the whole `info` (including `ublksrv_flags`) kept and copied back (2434-2477).
  - Only one process may hold `/dev/ublkcN` open (`UB_STATE_OPEN`, `-EBUSY`, 1301-1318); the descriptor array may be mapped only by one `mm` (`ub->mm`, `-EINVAL` for another, 1329-1334), read-only (`-EPERM` for `VM_WRITE`, 1339-1340), exactly the page-rounded size (1351-1352).
  - When the serving task exits: its pending fetch commands are cancelled (`UBLK_IO_RES_ABORT`, 1442-1458) from `ublk_uring_cmd_cancel_fn` (1464-1497), which also marks the queue `canceling`, quiesces blk-mq and aborts the queue (1410-1440); with `USER_RECOVERY` the `quiesce_work` is scheduled (1491-1494), which waits until no request is started (1532-1545, `msleep(3)` loop) and sets `UBLK_S_DEV_QUIESCED` (1547-1556). That path needs a fetch still pending: when the server held every tag at its exit nothing is cancelled, and `ublk_timeout` does the same abort and schedules `quiesce_work` only once a held request's timer fires (1209-1248; 4.4 step 1). Requests the daemon had fetched and not committed are **requeued only with `UBLK_F_USER_RECOVERY_REISSUE`, otherwise completed with `BLK_STS_IOERR`** (1061-1070, 999-1001, 1403-1404); requests not yet handed out are requeued and wait (1090-1098, 1121-1124, 1274-1276).
  - `START_USER_RECOVERY` needs `USER_RECOVERY`, at least one queue ever ready, **no opener of `/dev/ublkcN` and state `QUIESCED`, else `-EBUSY`** (2694-2723); it forgets every tag, drops the dead daemon's task, clears `ub->mm` and the ready counters (2669-2692, 2725-2731).
  - `END_USER_RECOVERY` blocks until every queue has a fetch on every tag (2745-2749, `-EINTR` on a signal), then needs state `QUIESCED` (2758-2760), records the new pid, unquiesces, kicks the requeue list and sets `LIVE` (2762-2769).
  - `STOP_DEV`/`DEL_DEV` on a quiesced device work without a server: `ublk_stop_dev` unquiesces with `force_abort` (every requeued request fails), deletes the gendisk, sets `DEAD` and pid `-1` (1593-1618, 1572-1591, 1262-1272); `DEL_DEV` waits until the id is free again (2512-2549), so the id can be reused by the next `ADD_DEV`.
  - `START_DEV` refuses a `LIVE` or used device with `-EEXIST` (2248-2251); the disk is `ublkb%d` (2259), the char device `ublkc%d` under class `ublk-char` (2117, 477-478), the control node `/dev/ublk-control` is a misc device (2989-2993).

### 4.2 `dbladed` start-up and shutdown (bin/dbladed.rs, daemon.rs)

1. `parse` (56-136) builds a `DaemonConfig`; `--heap-arena` → `ArenaKind::Heap`, `--arena-file` → `Hugetlb { path }`, neither → `ArenaKind::default_for_host()` (the hugetlbfs default on Linux, units.rs:28-36).
2. `install_signal_flag()` registers `SIGTERM` and `SIGINT` (daemon.rs:361-366; dbladed.rs:155-161).
3. `Server::bind_with` binds the control endpoint **before** any pool exists (dbladed.rs:162-168; server.rs:93-127, 181-219).
4. `Daemon::spawn` starts `dbladed-engine`, which runs `boot_configured` (daemon.rs:243-249, 95-110) on that thread and sends the outcome back; a failed boot ends the process (dbladed.rs:170-176).
5. `serve` accepts connections (one thread each) until the stop flag or the engine thread's end (server.rs:224-248); each request goes to the engine thread through `DaemonHandle::call` (daemon.rs:342-350) and is answered between ticks (`run`, 278-318).
6. Shutdown on `SIGTERM`/`SIGINT` (the stop flag, read at the top of `run`, daemon.rs:281-283), `daemon stop` (`Request::DaemonStop`, 200-207, sets `exit`) or the loss of the last handle (298-300, 307-309): the loop calls `Daemon::shutdown` (284-287, 217-225) → `Pool::stop` (pool.rs:840-863): every device dropped (842-845: `set_offline`, drain, `STOP_DEV`, `DEL_DEV`), `engine.shutdown()` (846), wait for `Event::Stopped` (847-850); the engine thread then ends (`stopped` set, daemon.rs:253), `main` joins it and prints "dbladed: stopped" (dbladed.rs:180-182), and the exit status is 0 unless that thread panicked (183-187; a failed `Pool::stop` is logged, daemon.rs:221, or, under `daemon stop`, returned to the client, 202, and the status is 0 either way). **When the socket file goes depends on the trigger.** `Server`'s `Drop` removes it (server.rs:172-179) and `serve` takes the `Server` by value (224, called at dbladed.rs:177), so it goes the moment `serve` returns. After `daemon stop` that is after everything above: `serve` returns on `handle.is_stopped()` (server.rs:227), which turns true only once the engine thread has ended (daemon.rs:253). After `SIGTERM`/`SIGINT` it is before: `serve` returns as soon as it reads the stop flag (server.rs:227-228), within one `ACCEPT_POLL` of 20 ms (17, 240), while the engine thread has only just begun `Daemon::shutdown` → `Pool::stop` on its own read of the flag (daemon.rs:281-287); the file goes alongside, and normally before, the device drops and the final CP, and `main` then waits in `join` (dbladed.rs:180-181). The loss of the last handle comes after the socket too: `main` drops its own handle only once `serve` has returned (dbladed.rs:177-180), and the connection threads hold clones (server.rs:232). In that window a new `otapctl` connection fails as unreachable (exit 3, R-L17) although the process is still stopping its pool, and a second `dbladed` on the same endpoint would bind it (`bind_unix` finds no file, server.rs:186-199, 211-213) and could open the same pool device: nothing locks the device itself (block.rs:155 opens it `RDWR | DIRECT | CLOEXEC`; checked here: no `flock` or `O_EXCL` in otap-sys/src/block.rs, otap-backstore/src/file.rs or otap-daemon/src/backstore.rs), and only a hugetlbfs arena's `flock` stops that boot (hugetlb.rs:346-355; `open_arena` comes after `open_backstore`, pool.rs:233-241). So wait for the process, not for the socket, before starting the next daemon, as the smoke test does (`wait` at linux-smoke.sh:241, then `start_daemon` at 244). Two precisions: **`pool stop` is not a shutdown** — `Request::PoolStop` (196-199) takes the pool and calls `Pool::stop` directly, `exit` stays false and the process keeps serving (args.rs:40: "pool stop ... the daemon keeps running"), so a later `pool boot` works on the same socket; and the "pool ... stopped cleanly" line (daemon.rs:220) is printed by `shutdown()` only, i.e. after a signal or the handle loss — `daemon stop` has already stopped and taken the pool inside its own arm (201-204), so `shutdown()` finds none and prints nothing.

### 4.3 `Pool::boot` on Linux (pool.rs:209-295) and where the devices come from

1. `check_arena_bytes`, `check_cp_interval` (214-215); the device must exist (216-221).
2. `probe_superblock` → `(agg_id, recorded)` or "holds no OpenTAP superblock in its ring" (222-231).
3. `open_backstore(device, overrides, None, Some(recorded), Some(cp_timer_ns))` (233-239): for a block device `is_block_device` → `open_block` (backstore.rs:237-239): `plan_device(&Sysfs::new(file_name), ...)` (304-321), profile with the daemon's flush policy and the CP timer (322-326), `UringBackstore::open` (328-329) which opens `O_DIRECT`, builds the ring and checks the capacity (block.rs:148-165; uring.rs:53-81).
4. `open_arena(&spec.arena, spec.arena_bytes)` (241): `HugeArena::map_file` re-attaches an existing file with its contents or creates it (arena.rs:39; hugetlb.rs:324-395); `slots_for_len` (242-243).
5. `PoolEngine::boot(cfg, backstore, DaemonFrontDoor::new(), clock, memory)` (245-257): inside, `Arena::can_attach`/`attach` against `agg_id` (engine.rs:1687-1709) and the boot job (1713-1714).
6. The `Pool` is assembled with `last_boot: "booting"`, `rotational` from the media, `stripe_bytes` from the profile, `devices` empty (259-276); planner warnings logged (277-279).
7. `wait_until("the boot commit", is_serving)` (280) ticks the engine; the `Event::Booted` is noted and becomes `last_boot` (331-375).
8. For every present, online volume: `ensure_device(vol)` (281-293) → `create_device` (device.rs:12-45) → `UblkDevice::create` (ADD_DEV, SET_PARAMS, open `/dev/ublkcN`, mmap, 128 fetches, submit), `front_door`, `start` (START_DEV) → `/dev/ublkbN`; `add_device` and the path recorded (pool.rs:694-696). A failure stops the pool and fails the boot (289-292). **As written, a root daemon hangs at `start`** (7.2, "`START_DEV` on the serving thread"; one link unverified): `START_DEV` is waited for on the engine thread, whose queue must serve the partition scan `START_DEV` triggers, and the front door is added to the engine only after `create_device` returns (694). The same `create_device` runs for `volume create`, `volume online`, a resize and a rollback (7.2, the six `ensure_device` callers), so the smoke test meets the hang at its first `volume create` (linux-smoke.sh:200), before any boot with an online volume. **Today this always allocates a new device id, so after a crash the quiesced old device stays and the volume gets a new path** (E38 docs/07:1419-1424; the smoke test's note at 260-262).

### 4.4 What happens in the kernel at `kill -9` and what a re-attach must do (v6.12)

1. The daemon dies; io_uring tears down its ring; each pending `FETCH`/`COMMIT_AND_FETCH` command is cancelled through `ublk_uring_cmd_cancel_fn` (kernel/ublk_drv.c:1464-1497): `ublk_abort_requests` marks the queue `canceling`, quiesces blk-mq, and `ublk_abort_queue` fails every request the daemon owned (no REISSUE: `BLK_STS_IOERR`, 1387-1408, 1061-1070, 999-1001); each command completes with `UBLK_IO_RES_ABORT` (1442-1458); `quiesce_work` is scheduled (1491-1494). **That path needs at least one command still pending.** A command is cancelable only while it is queued (`ublk_prep_cancel` → `io_uring_cmd_mark_cancelable`, 1798 → 1680), and a fetch that has delivered its request is completed (`ubq_complete_io_cmd` clears `UBLK_IO_FLAG_ACTIVE` and calls `io_uring_cmd_done`, 1072-1086), so the ring has nothing of it left to cancel (unverified link, the same as in 7.2's teardown corner case: that io_uring cancels only commands still in flight, general knowledge). If the daemon held **every** tag when it died — 128 of them (otap-ublk device.rs:47), all of which the front door will take (`Watermarks::for_depth` sets `high = depth`, frontdoor.rs:90-96; the gate at 442), so a queue of 128 or more outstanding requests at the kill can produce it (a request counts as held once its task work has delivered it: `ublk_queue_cmd` 1198-1206 → `ublk_rq_task_work_cb` 1190-1195 → `__ublk_rq_task_work` 1176 → `ubq_complete_io_cmd` 1072-1086) — the teardown cancels nothing and the cancel callback never runs. The second path is `ublk_timeout` (1209-1248): while the server lives it re-arms a held request's timer (1224-1225); once the server is dying (`PF_EXITING`, 985-988) and every tag is held (`nr_inflight == q_depth`, 1227-1235; the comment at 1234: "cancelable uring_cmd can't help us if all commands are in-flight") it runs the same `ublk_abort_requests` and schedules `quiesce_work` (1238-1240). That happens only when a held request's timer next fires. The driver sets no timeout (`ublk_add_tag_set`, 2150-2160; checked here: no other timeout setting in the file), so blk-mq's default applies (30 s; unverified: general knowledge), and the device stays `LIVE` with the dead pid for up to that long after the kill.
2. `quiesce_work_fn` (scheduled by either path of step 1) waits for the started requests to drain and sets `UBLK_S_DEV_QUIESCED` (1558-1570, 1547-1556); new requests from the block layer are requeued and held (1090-1098, 1274-1276). `/dev/ublkbN` stays; I/O on it waits in the queue; `GET_DEV_INFO` reports `state = 2` and the dead `ublksrv_pid`.
3. The old `/dev/ublkcN` file is released (`UB_STATE_OPEN` cleared in `ublk_ch_release`, 1312-1318) when its last reference goes, which the driver's own comment ties to the dead process having exited **and** its io_uring ctx having been freed (2707-2711: "the dying process is exited and related io_uring ctx is freed so file struct of /dev/ublkcX is released"). Whether that precedes the process becoming reapable by `wait` is not checkable from the saved files (the io_uring exit path is not among them; unverified: general knowledge says the ctx can be freed asynchronously after exit), so treat the window as possibly extending past `wait`. Until it closes, `START_USER_RECOVERY` answers `-EBUSY` (2719-2722). The arena file is different: its `flock` has no io_uring reference and goes with the process's file table (7.2).
4. The new daemon must, in this order and on the engine thread: find its device id (section 5.1: its Identity bullet's `ublksrv_flags` stamp, which `GET_DEV_INFO` returns verbatim, kernel 2434, 2578, and its `ensure_device` bullet's vol → dev_id table, which `Pool::boot` fills once from `list_devices()` filtered by the pool's tag; section 5.3's `device list` only decodes the same tag for display); poll `GET_DEV_INFO` until `state == QUIESCED`, against a deadline longer than the device's request timeout (step 1's second path: up to 30 s by default after a crash with every tag held); `START_USER_RECOVERY(dev_id)` with a bounded retry on `EBUSY` **only while `GET_DEV_INFO` keeps saying `QUIESCED`** (2694-2736; a `DEAD` leftover answers the same `-EBUSY` from 2719-2722 and must be deleted instead, 5.1); **only then** open `/dev/ublkcN` (`UblkChar::open`), map the descriptors (`UblkQueue::new`; `ub->mm` was cleared at 2728), push a `FETCH_REQ` on every tag and submit (as `open_queue` does, device.rs:166-177); then `END_USER_RECOVERY(dev_id, pid)` (2738-2774), which returns once the driver saw every fetch and resumes the queue. Opening the char device before `START_USER_RECOVERY` makes the start fail with `-EBUSY` for as long as it stays open (2719); issuing `END` before the fetches blocks until a signal (2748-2749).
5. The requests the block layer requeued while quiesced are delivered to the new fetches after `END` (2765-2768); requests the dead daemon had fetched were already failed to their issuers (step 1), so nothing is duplicated. Whether anything acknowledged is lost depends on the arena. **With a hugetlbfs arena**, nothing is: an acknowledged write was committed to the driver before the crash, and its data is in the arena file, which outlives the process (hugetlb.rs:3-9) and which the engine replays at boot (E16 docs/07:362-370; pool.rs:353-357). **With `--heap-arena`** (the smoke test's other branch, linux-smoke.sh:265-269; 5.4 item 3's orphan daemon; the 6.2 recovery test) the arena dies with the process (hugetlb.rs:119-125): the writes acknowledged since the last CP are lost, by design, and the boot fences the volumes that held them under nvfail instead of serving them silently (R-L5); the device still re-attaches, answering `EIO` until `nvfail-clear` (5.4 item 1, 7.2).

## 5. Hook points for Step 6

### 5.1 The re-attach (scope A, Linux side): where it plugs in, smallest coherent change

- **`otap-sys` needs nothing new for the commands.** `CtrlCommand::get_dev_info` (ublk.rs:789-791), `start_user_recovery` (807-809), `end_user_recovery` (815-819), `get_params` (783-785), `del_dev` (754-756) exist and `UblkControlRing::execute` runs them synchronously (1213-1276); `UblkChar::open` (1120-1125) and `UblkQueue::new` (1316-1346) are the re-open and the re-map. No new `unsafe` block and no inventory change (lib.rs:52-88) unless a new kind of SQE is pushed.
- **`otap-ublk/src/device.rs`: add `UblkDevice::recover(dev_id: u32, spec: &DeviceSpec) -> io::Result<Self>` beside `create` (88-125)**, in this order: `UblkControlRing::new(UblkControl::open()?)` (as 89); `GET_DEV_INFO` into a 64-byte buffer (the `CtrlBuf` pattern of 98-109, with `UblksrvCtrlDevInfo::read_from_bytes`); **then settle the state before judging it**, because a restart with no settle (5.4 item 1) can find the device still `LIVE`: while `GET_DEV_INFO` reads `LIVE` with a dead `ublksrv_pid` (the cancel callback only schedules `quiesce_work`, kernel 1491-1493, which sets `QUIESCED` once the tagset is idle, 1547-1556, after the `msleep(3)` loop of 1532-1545; and after a crash with every tag held nothing schedules it until a held request's timer fires and `ublk_timeout` does, 1227-1245, up to blk-mq's default 30 s after the kill, 4.4 step 1; liveness as in 5.3, pid reuse as in 7.2), re-read it against a deadline longer than the device's request timeout plus a margin (readable from `/sys/block/ublkbN/queue/io_timeout`, in milliseconds; unverified: general knowledge of blk-mq's sysfs), not one sized to the 2 s budget, as 4.4 step 4 says; on `DEAD` recover nothing and return a distinct error, so that the caller deletes the device (`delete_device`) and creates afresh (the `DEAD`-with-our-tag case below); on `LIVE` with a live pid refuse (another server holds it). Refusing at the first `LIVE` reading instead would send the settle-free restart to question 4's policy, reap and recreate, which normally gets the same `/dev/ublkbN` back (7.2, "Ids are reused at once") but loses the surviving device the brief asks to re-attach (docs/10:606): the requests held during the quiesce fail with `EIO` and the old disk is deleted under whatever held it open (question 4); a deadline shorter than the request timeout does the same to every crash with all tags held. Only then refuse unless `info.state == UBLK_S_DEV_QUIESCED`, `info.flags & (UBLK_F_USER_COPY | UBLK_F_USER_RECOVERY)` is whole, `info.nr_hw_queues == 1` and `info.queue_depth == spec.depth` (the depth is the device's, not the spec's: `UblkQueue::new` maps `depth * 24` bytes and the kernel refuses any other size, ublk.rs:1323-1325, kernel 1351-1352); `START_USER_RECOVERY` with a bounded retry on `EBUSY` for as long as `GET_DEV_INFO` keeps reading `QUIESCED` (kernel 2719-2722; the window is the dead process's io_uring teardown, section 4.4 step 3; a `DEAD` reading ends the retry, as below); then `open_queue(spec)` (166-177: open `/dev/ublkcN`, mmap, a fetch per tag, submit), unchanged except that on this path an `EBUSY` from `UblkChar::open` is retried within the same deadline, since a reaper's probe open (5.3) can hold the char device for a moment; then `END_USER_RECOVERY(dev_id, std::process::id())` and `started = true` (so `delete()` at 214-219 still does `STOP_DEV` then `DEL_DEV`). `SET_PARAMS` is **not** reissued — not because the driver would refuse it (it answers `-EACCES` only while the state is `LIVE`, kernel 2651-2654, which is what ublk.rs:774-775 "refused while the device is live" records; on a `QUIESCED` device it is accepted and stored in `ub->params`) but because it would change nothing: the gendisk's limits were built from `ub->params` once at `START_DEV` (2190-2260) and `END_USER_RECOVERY` (2738-2774) only unquiesces, so a reissue on a recovered device is silently ineffective and **no error from the driver will catch it**; `max_io_bytes` must therefore be whatever the device was created with (read `info.max_io_buf_bytes`, and note the arena-derived cap at 60-66 could differ if `--arena-bytes` changed across the restart: compare and refuse or warn).
- **`otap-ublk/src/device.rs`: add `pub fn list_devices() -> io::Result<Vec<UblksrvCtrlDevInfo>>`** (enumerate ids from `/sys/class/ublk-char/ublkc*` — class name `ublk-char`, node name `ublkc%d`, kernel/ublk_drv.c:477-478, 2117 — or glob `/dev/ublkc*`; one control ring; `GET_DEV_INFO` per id, skipping `ENODEV`) and **`pub fn delete_device(dev_id) -> io::Result<()>`** (`DEL_DEV` on a quiesced or dead device needs no server, kernel 1593-1618, 2512-2549; the reaper's guarded form, 5.3, sends `DEL_DEV_ASYNC` instead, 2949-2950, while it holds a probe open of `/dev/ublkcN`). Both are the reaper's primitives and need `CAP_SYS_ADMIN` (kernel 2832-2833).
- **Identity: stamp `info.ublksrv_flags` at `ADD_DEV`** (device.rs:90-97, today 0). The driver stores it verbatim and returns it from `GET_DEV_INFO` (kernel 2434, 2578; ublk.rs:462-463). A `DeviceSpec` field `tag: u64` filled by the daemon with, for example, the low 32 bits of a BLAKE3 digest of `agg_id` in the high word and the volume index in the low word lets a restarted daemon find *its* devices without any file of its own (R-L12). `GET_PARAMS` gives `dev_sectors` to cross-check the volume size (ublk.rs:583-584, 783-785).
- **`otap-daemon/src/device.rs`: add `recover_device(vol, dev_id, size_blocks, stripe_bytes, rotational, arena_slots) -> Result<(VolumeDevice, String), ControlError>`** mirroring `create_device` (12-45) with `UblkDevice::recover` instead of `create` and no `start()` — its success path, not its error handling: `create_device`'s `START_DEV`-failure path deletes the device while `front` still holds `/dev/ublkcN` and would hang (36-37; 7.2, "Delete only after the front door is dropped"), so any step that can fail after `front_door` must `drop(front)` before `delete()`, while a failure inside `UblkDevice::recover` is safe as long as it deletes through `delete_inner`, which drops the queue first (otap-ublk device.rs:117-123, 203-208); the `front_door` call (26-35) is the same: a fresh `UblkFrontDoor` (every tag `Idle`, generation 0) is correct because `ublk_queue_reinit` forgot every tag (kernel 2684-2691) and the engine is freshly booted with an empty `DaemonFrontDoor` (pool.rs:248).
- **`otap-daemon/src/pool.rs`: `ensure_device` (678-709) is the one place.** Before `create_device` (687), consult a `BTreeMap<u32, u32>` (vol → quiesced dev_id) that `Pool::boot` fills once from `list_devices()` filtered by this pool's tag (between 280 and 281, after the boot commit, before the online loop at 281-293); if present, `recover_device` and the same `add_device`/`devices.insert`/log (694-696); log `volume {vol} re-attached {path}` so the smoke test can grep it. Devices carrying this pool's tag whose volume is absent or offline are reaped there too (a crash after `volume offline` cannot leave one — `drop_device` deletes synchronously — but a crash between `ADD_DEV` and `START_DEV` leaves a `DEAD` device with our tag, which must be deleted, not recovered. Why, exactly: `UblkDevice::create` submits all 128 fetches inside `open_queue` (otap-ublk device.rs:117-123, 166-177) before `create_device` calls `start()` (otap-daemon device.rs:26-42), and the kernel counts a queue ready on its last `FETCH_REQ`, not at `START_DEV` (`ublk_mark_io_ready` is called from the `FETCH_REQ` arm, kernel 1734-1762, and bumps `nr_queues_ready` at 1621-1636). So a crash before the fetches were submitted leaves `nr_queues_ready == 0` and `START_USER_RECOVERY` answers `-EINVAL` (2698, 2704-2705); a crash after them leaves `nr_queues_ready == 1` with the state still `DEAD` (never `LIVE`, and nothing moves it to `QUIESCED`: when the dead server's fetches are cancelled, the device has no disk yet (`ub_disk` is set only by `START_DEV`, 2264), so `ublk_abort_requests` returns false (1428-1430) and `quiesce_work` is not even scheduled (1485, 1491); and `ublk_quiesce_work_fn`, were it to run, would skip only `__ublk_quiesce_dev`, the state change, unless `LIVE` (1564-1566), still calling `ublk_cancel_dev` after the unlock, 1569), and `START_USER_RECOVERY` answers **`-EBUSY`** from the `state != QUIESCED` test (2719-2722) — the same errno as the transient char-device window. **Therefore the `EBUSY` retry must be gated on `GET_DEV_INFO` reporting `state == QUIESCED` (the precondition the `recover` bullet above already requires) and never driven by the errno alone**: `DEAD` → delete; `LIVE` with a dead pid → wait for `quiesce_work` (up to the request timeout, 4.4 step 1); `QUIESCED` and `EBUSY` → retry with a deadline.)
- **What must not break**: `drop_device` (714-739) and `Pool::stop` (840-863) work unchanged on a recovered device; the rollback and resize paths (1088, 1111, 929-932) still drop and recreate, and the recreated device usually keeps its `/dev/ublkbN` already today: `DEL_DEV` returns only once the id is free (kernel 2546) and `ADD_DEV` with `ANY_DEV` takes the lowest free id (2075; 7.2, "Ids are reused at once"), so only a lower id freed in between, or another process's `ADD_DEV` taking this one first, changes it, which is why callers keep re-reading the path (linux-smoke.sh:229); Step 6 changes none of this; the Windows build (`cfg(not(target_os = "linux"))` arms at 698-707, 734-737) must gain nothing; `--no-ublk` (`self.ublk == false`, 681) must skip the lookup as well as the create.
- **The 2 s budget**: the engine boot itself (`wait_until("the boot commit")`, 280) is paced by `IDLE_TICK` 200 µs (58) and the CP commit; the recovery adds `GET_DEV_INFO` polls plus the `START` retry window plus `END` (which returns as soon as the 128 fetches are seen). That holds only on 4.4 step 1's cancel path, i.e. when a fetch was still pending at the crash (the smoke test's quiescent kill; 5.4 item 4's `--iodepth=16`). After a crash with every tag held the device stays `LIVE` until a held request's timer fires (4.4 step 1's second path; up to blk-mq's default 30 s, unverified: general knowledge), and the re-attach cannot begin before that, since `START_USER_RECOVERY` needs `QUIESCED` (kernel 2719-2722). Lowering the device's request timeout when it is created (`/sys/block/ublkbN/queue/io_timeout`; unverified: general knowledge of blk-mq's sysfs, including whether a new value reaches requests already started) would bound that wait; the lead's call (section 8, question 9). Measure in the smoke test (section 5.4 item 2) rather than assert hard.
- **Open design point (section 8)**: adding `UBLK_F_USER_RECOVERY_REISSUE` at `ADD_DEV` (device.rs:95) would make the kernel requeue the requests the dead daemon had fetched (kernel 1066-1067) instead of failing them with `EIO`; the engine's re-attach drops `Filled` (never acknowledged) slots (E16 docs/07:362-364), so a reissued write would land again cleanly. It is in `UBLK_F_ALL` (kernel 59) and reported by `GET_FEATURES`. It is not a one-line change, though: under the crate docs' rule of R-L3 (otap-sys lib.rs:4-7) the flag must also join `REQUIRED_UBLK_FEATURES` (probe.rs:37-38), so the startup gate, once wired (5.2), refuses a kernel without it.

### 5.3 `otapctl device list` / `device reap` (the control plane)

- **Protocol** (`otap-control/src/protocol.rs`): `Request::DeviceList` and `Request::DeviceReap { dev_id: Option<u32>, orphans: bool, force: bool }` in the `op`-tagged enum (42-218; its `rename_all = "snake_case"`, 41, makes their wire names `"op": "device_list"` and `"op": "device_reap"`); `Response::Devices { devices: Vec<DeviceReport> }` as a **struct** variant (357-405; a newtype over a bare sequence cannot be internally tagged, E38 docs/07:1391-1393) and `Response::Reaped { dev_ids: Vec<u32>, busy: Vec<u32> }` (on the wire `"kind": "devices"` and `"kind": "reaped"`, by the same rule, 356; `busy`: the candidates the re-attach guard of the Daemon bullet skipped); a `DeviceReport { dev_id, block_path, char_path, state: String ("dead"|"live"|"quiesced"), server_pid: i32, server_alive: bool, owned_by_this_daemon: bool, pool: Option<String>, volume: Option<u32>, orphan: bool, queue_depth, max_io_bytes, size_bytes: Option<u64>, flags: u64 }` with `deny_unknown_fields` like the others (222). The JSON round-trip test in `protocol.rs`'s `tests` module (463-464) must gain the new variants. `PROTOCOL_VERSION` (9): bumping it makes a new `otapctl` refuse an old daemon through `Client::hello` (otap-ctl lib.rs:76-81); not bumping leaves an old daemon answering `BadRequest` "the request does not decode" (server.rs:270-273) to a new client — lead's call (section 8).
- **Daemon** (`daemon.rs::handle`, 127-213): the two arms go **before** `other => needs a pool` (208-211) because reaping must work with no pool booted (the orphan of a dead daemon). Linux only; elsewhere `ErrorCode::Unsupported`. Orphan rule: `state == QUIESCED && !server_alive`, and at reap time no process holding `/dev/ublkcN` (the re-attach guard below); a `LIVE` device with a live pid is reaped only with `force`. **A `DEAD` device is not an orphan by its state**: `ADD_DEV` stores the client's `info` verbatim (kernel 2434), and OpenTAP's carries state 0 = `DEAD` and pid 0 (otap-ublk device.rs:90-97), so a device another live daemon is creating reads `DEAD` with pid 0 from its `ADD_DEV` until that daemon's `START_DEV` records the pid and sets `LIVE` (2263, 2273); the creator's hold on `/dev/ublkcN` (`UB_STATE_OPEN`, 1301-1318) is a bit of `ub->state`, which `GET_DEV_INFO` does not report (it copies `dev_info` alone, 2578). A `DEL_DEV` in that window removes a live daemon's device mid-creation (`ublk_remove`, 2523, 2162-2170) — what the `force` rule exists to prevent, and exactly the two-daemons-per-host case of section 8, question 3. So `--orphans` leaves `DEAD` devices alone: they are deleted by the boot-time cleanup of the pool whose tag they carry (5.1), or by hand with `--dev-id N --force`. A heuristic that reaps more (a `DEAD` listing seen twice a grace period apart, plus a probe open of `/dev/ublkcN` that does not answer `-EBUSY`, 1306-1307, closed again before the `DEL_DEV`, since an open file pins the device number `DEL_DEV` waits for, 2546, or held across a `DEL_DEV_ASYNC` as for `QUIESCED` below) still races a creator that has not opened its char device yet, and the probe's own open can make that creator's open fail `EBUSY` (section 8, question 5). **Nor is every `QUIESCED` device with a dead pid an orphan.** A live daemon re-attaching it (5.1) leaves exactly that listing from its `START_USER_RECOVERY` to its `END_USER_RECOVERY`: `START` changes neither the state nor the pid (2694-2736; it reinitialises only the queues and the counters, 2725-2731), and `END` records the new pid (2762) and sets `LIVE` (2769) only after the new fetches arrived (2748); the recovering daemon's hold on `/dev/ublkcN` (`UB_STATE_OPEN`, 1301-1318) is, again, not in `GET_DEV_INFO`'s reply (2578). In the two-pools-per-host case (section 8, question 3) a second daemon's `--orphans` would `DEL_DEV` it: `ublk_stop_dev` unquiesces with `force_abort`, deletes the gendisk and sets `DEAD` (1600-1611), `ublk_cancel_dev` aborts the new fetches (1617), the recovering daemon's `END` fails `-EBUSY` (2758-2760), and the reaper's own `DEL_DEV` blocks its engine thread until that daemon closes `/dev/ublkcN` (2546, 2094-2103): a live server's device gone without `--force`. Guard: at reap time open `/dev/ublkcN` as a probe and skip the device if the open answers `-EBUSY` (1306-1307: a re-attach past its open holds it, or the dead server's file is not released yet, 4.4 step 3; either way a later scan can take it). While the probe is held no re-attach can pass `START_USER_RECOVERY` (`UB_STATE_OPEN` → `-EBUSY`, 2719-2722) or open the char device, so delete with `DEL_DEV_ASYNC` while still holding it and close it afterwards (`UBLK_U_CMD_DEL_DEV_ASYNC`, ublk.rs:137, sent with `CtrlCommand::new`, 724-742; the async form skips the wait for the id, kernel 2546, 2949-2950, which a plain `DEL_DEV` would spend waiting on the reaper's own open). The probe cannot see a re-attach that has passed its `START` but not yet opened `/dev/ublkcN` (4.4 step 4): that residual race fails the re-attach (its open answers `EBUSY`, then the device is gone) and sends it to question 4's policy. Requiring the same `quiesced` listing with the same dead pid at two scans a grace period apart narrows it further, at the price of a reaper that remembers its first sighting (section 8, question 5). `device list` computes `orphan` from the listing alone, without the probe, so that listing never disturbs a re-attach; `device reap --orphans` applies the guard and reports the candidates it skipped as busy. A `LIVE` device with a **dead** pid is in the quiesce window: either the cancel callback has scheduled `quiesce_work` and it has not set `QUIESCED` yet (kernel 1491-1493, 1555, 1564-1565; 7.2), or the dead server held every tag, nothing was cancelled, and nothing is scheduled until a held request's timer fires (`ublk_timeout`, 1227-1245; up to blk-mq's default 30 s after the kill, 4.4 step 1). List it as `live` with `server_alive: false`, do not count it as an orphan, and let the caller poll (5.4 item 3), for as long as the request timeout — `--orphans` picks it up once it is `quiesced`. Liveness: `kill(pid, 0)` or `/proc/<pid>/status` not `Z` (the daemon is root). A device whose tag names the pool currently booted here and whose volume is online is **never** reaped (it is this daemon's own). Reaping = `delete_device` (5.1), in its guarded form for a `QUIESCED` candidate (`DEL_DEV_ASYNC` while the probe is held, above).

### 6.2 Patterns to copy for the new Linux tests

- **File shape**: one integration file per crate, `#![cfg(target_os = "linux")]` at the top (the module form is `otap-sys/tests/sys_tests.rs:905`), each root-needing test `#[ignore = "needs root and /dev/ublk-control; run with --ignored on a Linux host"]` (the only `#[ignore]` in the tree, format_tests.rs:2516, is the model: a reason string, run on purpose with `-- --ignored`), and an early skip-with-message when `/dev/ublk-control` is absent or `std::fs::metadata("/proc/self")?.uid() != 0` (no new dependency: `std::os::unix::fs::MetadataExt`). Opt-in through an environment variable the way the sim suites read theirs: a flag by its presence, as `QA_TRACE` is (`std::env::var_os("QA_TRACE").is_some()`, review_step5_sim_tests.rs:908-910), and a value through `std::env::var` and a parse, as `PROPTEST_CASES` is (914-919).
- **A real device without the daemon** (`otap-ublk/tests/linux_device_tests.rs`): copy from `engine_tests.rs` the constants and helpers 14-68 (`STRIPE` ... `VOL_BLOCKS`, `geometry()`, `profile()`, `config()`, `config_for()`), `boot_with()` 85-97 and the `tick_until()` it calls, 112-120, plus the format step of `fresh_engine_with()` (105-110), with the `UblkEngine` alias (22) retyped over `LinuxTransport`; give `boot_with` a `HugeArena::heap` arena, because its `HugeArena::anonymous` (91) is `MAP_HUGETLB` on Linux and fails without reserved pages (6.1). Build the front door with `UblkDevice::create(&DeviceSpec::new(VOL_BLOCKS, STRIPE, false))` and `device::front_door(&mut dev, 0, &spec)` (device.rs:88-125, 344-360); tick on the creating thread (`device::serve`, 368-382, with an `AtomicBool`); from a second thread `pwrite`/`pread` with `O_DIRECT` on `dev.block_path()` and compare; then set the stop flag, let `serve` return, and **drop the engine before `dev.delete()`**, the order of the daemon's `destroy_device` (it drops the front door first, otap-daemon device.rs:50-56; 2.7, 2.9; `create_device`'s `START_DEV`-failure path does not, 7.2). **`dev.start()` must not run on the creating thread before `serve`**: `UblkDevice::start` (184-190) waits for `START_DEV` synchronously (`UblkControlRing::execute`, ublk.rs:1248-1270), and for a root test (a privileged device: the control commands need `CAP_SYS_ADMIN`, kernel 2831-2833) the kernel's partition scan of the new disk reads through the very queue only this thread serves, so `start` never returns (7.2, "`START_DEV` on the serving thread"). Until the library offers a non-blocking start (section 8, question 15), move `dev` into a helper thread that calls `dev.start()` and hands `dev` back (`UblkDevice` is `Send`: its fields, otap-ublk device.rs:70-76 and otap-sys ublk.rs:1050-1052, 1110-1113, 1184-1187, 1299-1306, are descriptors, plain data, `io_uring::IoUring`, which is `Send` and `Sync` (io-uring 0.7.15 src/lib.rs:116-117), and a `memmap2::Mmap` (memmap2 0.9.11 src/unix.rs:525-526); checked here), while the creating thread is already in `serve`; control commands are not tied to the queue's task (the `ubq_daemon` check, kernel 1706-1707, is in the char device's I/O path, `__ublk_ch_uring_cmd` 1683, not in `ublk_ctrl_uring_cmd` 2896). Why the drop order matters: `front_door` moves the queue, and with it the open `/dev/ublkcN`, into the engine (`take_transport`, device.rs:349-351, 242-247); `serve` only borrows the engine (368-370), so it is still alive after the loop; `delete_inner` (203-208) sets an already empty `queue` to `None` and then issues `DEL_DEV`, which waits until the device number is freed (kernel/ublk_drv.c:2546, `wait_event_interruptible(ublk_idr_wq, ublk_idr_freed(idx))`), and for a device that `ADD_DEV` completed, `ublk_free_dev_number` (2086-2092) runs only from the char device's release `ublk_cdev_rel` (2094-2103, call at 2100) — its only other caller is `ADD_DEV`'s own error path (`out_free_dev_number`, 2491-2492), which never applies to a created device — i.e. after the last open file on `/dev/ublkcN` closes (`ublk_remove` at 2162-2170 does `cdev_device_del`, 2167, but that the open file pins the release until it closes is general kernel knowledge, not in the saved files). A test that calls `dev.delete()` while the engine holds the transport therefore blocks in `DEL_DEV` until a signal interrupts the wait (`-EINTR`, 2546-2547); the command runs in an io-wq worker (control commands answer `-EAGAIN` to the inline issue, 2904-2905), which receives no signal but `SIGKILL` (unverified: general knowledge of io_uring), while `execute` retries `EINTR` on its side (ublk.rs:1248-1270), so in practice it blocks until the process is killed. So: `drop(engine)` (`UblkFrontDoor` → `LinuxTransport` → `UblkQueue` → `UblkChar`), then `dev.delete()` (`STOP_DEV` when `started`, then `DEL_DEV`, 214-219). Then the recovery variants: `dev.take_transport()` dropped and the process kept alive cannot simulate a crash, so the re-attach test is a **process** test (next item).
- **The re-attach and the reaper** (`otap-daemon/tests/linux_recovery_tests.rs`): spawn `env!("CARGO_BIN_EXE_dbladed")` (the `CARGO_BIN_EXE_otapctl` pattern of ctl_tests.rs:60; `dbladed` is a `[[bin]]` of the same package, otap-daemon/Cargo.toml:14-16) with `--control unix:<tempdir>/ctl.sock --device <tempdir>/pool.img --heap-arena --arena-bytes 64M --cp-interval 1` after a format (the `format_req` of daemon_tests.rs:60-71 through `Client`), talk `otap_control::Client` over `Endpoint::Unix`, `volume create` (which first needs the `START_DEV` fix: as the code stands a root daemon never answers it, 7.2), read `VolumeReport.device`, `Child::kill()` (SIGKILL) + `wait`, spawn again with the same arguments, assert the same `device`, then `Request::DeviceList`/`DeviceReap` (5.3; for a deliberate orphan — a second daemon killed, as in 5.4 item 3 — poll `DeviceList` until its device reports `quiesced` before expecting `DeviceReap { orphans: true }` to name it, retrying while the reply lists it as `busy`, 5.3; that expectation depends on questions 3 and 5 exactly as 5.4 item 3's does, with `DeviceReap { dev_id: Some(id), orphans: false, force: true }` as the fallback). ## 7. Risks, pitfalls and traps

### 7.1 WSL 2 specifics that will bite (item 3)

1. **No ublk in the stock kernel.** `# CONFIG_BLK_DEV_UBLK is not set` (unverified: from the lead's note) means `modprobe ublk_drv` fails silently (linux-smoke.sh:96) and the script dies at 97. The brief says `CONFIG_BLK_DEV_UBLK=y` (docs/10:595); the lead's note says `=m`. With `=m` the module must exist under `/lib/modules/$(uname -r)/` of the **custom** release inside the distro (`make modules_install`), and Microsoft's own `=m` modules (`DM_FLAKEY`, `DM_DELAY`) stop loading on a custom kernel because modules are built per release; `=y` for `BLK_DEV_UBLK`, `DM_LOG_WRITES`, `DM_FLAKEY`, `DM_DELAY` (and `BLK_DEV_DM`, which caps the three dm targets, 5.6 step 4) removes the whole module question, provided the build is checked for `=y` and not merely for presence (5.6 step 4); its one cost is that a built-in driver cannot be reloaded to clear leftover devices (item 14) (unverified: general knowledge that WSL ships the stock modules separately; the per-release rule is kernel fact).
2. **`.wslconfig`**: checked here it has `processors=8`, `memory=16GB`, `swap=0`, `localhostForwarding=true` and the `kernel=E:\\WSL\\kernel\\bzImage` form already in a comment (lines 5-11); `E:\WSL` does not exist yet. The path takes doubled backslashes; any change needs `wsl --shutdown` from Windows and a fresh start; verify with `uname -r` and `zcat /proc/config.gz` (unverified: general knowledge). `swap=0` gives the VM no swap, so a failed `nr_hugepages` reservation cannot be helped by swapping anonymous memory out; reserve early, before the kernel build fragments memory (unverified: general knowledge of WSL's `swap=` key and of how the kernel reclaims and compacts memory for huge pages; only the `swap=0` line itself is checked here).
3. **`/mnt/e` is a 9p (drvfs) share, not ext4.** `O_DIRECT` is not honoured there, so `losetup --direct-io=on` on a file under `/mnt/e` fails and the script falls back silently (116); builds there are slow; file modes are faked; and the Windows `target/` directory would be shared with the Linux build (cargo uses `target/debug` for both hosts, so fingerprints and `deps/` would clobber each other). Clone into `$HOME` (the ext4 VHDX) or set `CARGO_TARGET_DIR` on ext4, and make the script honour it (5.4 item 6). `/var/tmp` (the script's work dir, line 50) is on the ext4 root, which is right. (9p facts: unverified, general knowledge.)
4. **What the planner will make of a loop device** (geom.rs; the sysfs values are unverified: whether a 6.12 loop device over an ext4 file on a Hyper-V virtual disk reports `queue/rotational` 0 or 1 cannot be checked from files on this machine — the loop driver is not among the saved kernel sources — so both branches are worked out here and the prep script prints the values, 5.5 row 7). Common to both: a 1 MiB default stripe because `optimal_io_size` = 0 (711-716, no warning since the kind is `Loop`, 712-714); no `device/vendor` → classified by name (435-436). **`rotational` = 0** → `Media::Flash` (651-655) → an 8 MiB segment (`SEGMENT_FLASH` 605, 742-746); `discard_granularity`/`discard_max_bytes` non-zero over an ext4 file → `DiscardPolicy::WholeSegment` (812-822) → `BLKDISCARD` punches holes in `pool.img` (over a 9p file they are 0 → `Never` plus the `DiscardUnavailable` warning, 823-825); `MediaProfile::flash` (591-594); a 2 GiB image gives roughly 255 segments with a reserve of 21 (`reserve_for` = max(8, n/12), capped at n/2, otap-cp engine.rs:61-68). **`rotational` = 1** → `Media::Hdd` (651-655) → an 80 MiB segment target (`SEGMENT_HDD` 603, 742-743) → about 25 segments on a 2 GiB image (well above `MIN_SEGMENTS` 8, 613, so no `SmallDevice` shrink) with a reserve of max(8, 25/12) = 8; `DiscardPolicy::Never` **without** the `DiscardUnavailable` warning (812-825: both the `WholeSegment` branch and the warning are flash-only), so the backstore never issues `BLKDISCARD` to the loop device (the volume-level `blkdiscard` of the smoke test, 224, is unaffected: the ublk device's discard limits come from `DeviceSpec::new`, otap-ublk device.rs:44-53, 145-155, not from the media); `MediaProfile::hdd` (591-594); and `rotational: true` in the pool (pool.rs:268) → `UBLK_ATTR_ROTATIONAL` on every `DeviceSpec` (otap-ublk device.rs:131-133) → `/dev/ublkbN` itself reports `rotational` = 1 (kernel 2241-2242). The two layouts differ in the superblock, so a run must not change media between format and boot: to pin the smoke run, pass `--media flash` (or `hdd`) to **both** `otapctl pool format` (args.rs:31, 249) and the boot (`dbladed --media`, dbladed.rs:93-100, for the smoke test's `--device` boot at linux-smoke.sh:145; `otapctl pool boot --media` for the README's sequence, args.rs:35, 269); the `queue/rotational` value the prep script prints (5.5 row 7) says which branch the host takes on its own.
5. **A real disk under WSL** is a Hyper-V virtual disk (`vendor` `Msft`, `model` `Virtual Disk`, unverified: general knowledge) → `DeviceKind::Virtual` through the `MSFT` marker (geom.rs:321, 439-443), not `HwRaidVd`; `--device /dev/sdX` **wipes** it (linux-smoke.sh:120-122), so only a spare VHDX attached with `wsl --mount --vhd` (unverified: general knowledge) is a candidate.
6. **Huge pages inside the VM**: `HUGETLBFS` is in (unverified: from the lead's note); `Hugepagesize` is 2048 kB on x86-64; `nr_hugepages` needs free contiguous 2 MiB blocks, so reserve before building the kernel or after `echo 3 > /proc/sys/vm/drop_caches` (both unverified: general knowledge; 5.5 row 6 prints the first on the VM); 1 GiB pages would need `kernelCommandLine=hugepagesz=1G ...` in `.wslconfig` (unverified: general knowledge) and are not used (`HugePageSize::TwoMiB` everywhere in the daemon, arena.rs:19, 39). `vm.nr_hugepages` is a normal sysctl in WSL 2 (unverified: general knowledge).
7. **io_uring**: present in the stock config (unverified: from the lead's note). `kernel.io_uring_disabled` (6.6+; 0 enabled, 1 privileged only, 2 off; unverified: general knowledge) at 2 makes every `IoUring::builder().build()` fail `EPERM` (block.rs:157, ublk.rs:1195, probe.rs:334) with a message that does not say why; the prep script must check the sysctl and run `dbladed --probe` (5.2). `IORING_REGISTER_CLONE_BUFFERS` (io_uring.h:613) is 6.12+, but nothing calls `clone_buffers` yet (checked here), so a 6.6 stock kernel would not fail on it; `REQUIRED_OPCODES` tops out at `SEND_ZC` (6.0).
8. **The brief asks for a 6.12 kernel, the lead's note for 6.18, and the code was checked against 6.12.** docs/10:595 asks for "a reproducible script to compile a Linux 6.12 WSL 2 kernel"; the lead's note takes Microsoft's 6.18 line (`linux-msft-wsl-6.18.54.1`) while allowing "whichever 6.12+ line is wanted". Which one the VM runs is section 8, question 8, and it sets 5.6's `--tag`. On 6.18: its `ublk_drv.c` is not on this machine; later drivers added recovery flags (`UBLK_F_USER_RECOVERY_FAIL_IO` in 6.13 and more since; unverified: general knowledge), so `GET_FEATURES` returns bits `feature_name` does not know (printed as `ublk feature bit N`, probe.rs:259; harmless), and the quiesce/requeue behaviour of section 4.4 may differ in detail, so save the 6.18 sources beside the 6.12 ones in `OpenTAP-local` and re-verify 4.4 and R-L18 against them before writing the re-attach. On a 6.12-based kernel the saved v6.12 sources are the running driver's, up to the stable updates and Microsoft's patches on that line (not checkable here). Either way, record what the smoke test observes in docs/08 (docs/06 §7 asks for it).
9. **`wsl.exe` prints UTF-16LE when piped** (from Git Bash or PowerShell: NUL bytes in `wsl.exe --status | grep`); set `WSL_UTF8=1` or pipe through `iconv -f UTF-16LE -t UTF-8` / `tr -d '\0'` (unverified: general knowledge). Only Windows-side wrappers care; the distro's own programs' output passes through as bytes. Checked here: only the in-box `C:\Windows\System32\wsl.exe` exists and `C:\Program Files\WSL` does not, so the Store/MSI package (the one that ships the newer kernel line, unverified: from the lead's note) is still to be installed, as the memory note says. Reading `kernel=` is not what sets it apart: the in-box WSL 2 of build 19041 and later also reads `kernel=` from `.wslconfig` (unverified: general knowledge), so the custom kernel does not by itself require the package.
10. **systemd and udev are not needed** by the smoke test (it starts `dbladed` by hand; devtmpfs creates `/dev/ublk-control` and `/dev/ublkbN`; unverified: general knowledge), but `/run` is tmpfs (unverified: general knowledge, as in R-L13), so the README's `/run/opentap/arena` (143-145) and the default socket directory (server.rs:200-210) vanish at every VM start; `[boot] systemd=true` in `/etc/wsl.conf` (WSL's switch for systemd as PID 1; unverified: general knowledge) is needed for the future units (docs/06 §7 item 2) and for any `tmpfiles.d` file that is to recreate those directories at boot, since only `systemd-tmpfiles` applies one and WSL's own init does not (unverified: general knowledge); without systemd the hook is a `[boot] command=` line in `/etc/wsl.conf` (unverified: general knowledge; 5.5 rows 13 and 14).
11. **`sudo` and rustup**: `secure_path` drops `~/.cargo/bin` (Debian's sudoers default; unverified: general knowledge), so `sudo scripts/linux-smoke.sh` (README.md:123) reaches `cargo build` (107) with no `cargo` → `die "the build failed"`; and a build that does succeed as root leaves `target/` root-owned for the user. Neither `sudo --preserve-env=PATH` nor `env PATH="$PATH"` inside the script fixes it: Debian's `secure_path` takes precedence over a preserved `PATH`, and `env_reset` sets `HOME=/root`, so even a `cargo` found by its full path is rustup's proxy looking for `/root/.rustup` and finding no toolchain (unverified: general knowledge of sudo's and rustup's defaults, not checkable here); and inside the root-run script `$PATH` is already the `secure_path`. What works: build in the invoking user's own environment (`sudo -u "$SUDO_USER" -H bash -lc ...`, or that user's `~/.cargo/bin/cargo` by full path under `-H`; 5.4 item 6), or pre-build as the user and pass `--no-build`. The README's "stable Rust ... for the user who builds" (116-117) hides this, and its own sequence (122-123: build as the user, then `sudo scripts/linux-smoke.sh`) dies at 107 as the script stands.
12. **One cargo at a time, one core free** (the memory notes): a WSL build is a second cargo process on the same 6-core PC; do not run the Windows gate and the WSL build together. Inside the VM keep BUILDING.md's rule for the shared desktop, `cargo build -j 3` and tests with `--test-threads=6` (198-199; the memory note says builds at `-j 2` or `-j 3`): the VM's 8 vCPUs are 8 of the PC's 12 logical CPUs (`.wslconfig:2-3, 6`, checked here), so a `-j` derived from the VM's `nproc` still takes most of the shared desktop: `nproc - 2` keeps 6 of its 12 threads busy, twice the cargo rule. That figure is only the kernel build's default (5.6, the assignment's); lower it with `--jobs` while the desktop is in use.
13. **`wsl --shutdown` or `vmIdleTimeout` is a power cut for the arena** (unverified: general knowledge that both stop the WSL 2 VM and its kernel and that the distro's ext4 disk is a VHDX that outlives the VM; `.wslconfig` sets no `vmIdleTimeout`, checked here): the hugetlbfs file lives in the VM's RAM — its contents outlive the process (hugetlb.rs:3-9) but, being memory, not the kernel — while the pool on the VHDX survives; the next boot is dirty with nvfail (README.md:27-31). A useful extra lane, owner-driven, and a reason the arena directory must not be assumed to survive a VM restart.
14. **Device numbering across runs**: `ADD_DEV` takes the lowest free id (kernel 2063-2077); a smoke run that leaves quiesced devices (today's behaviour after SIGKILL, E38 docs/07:1419-1424) makes the next run's volumes `ublkb1`, `ublkb2`, ... and after 64 leftovers `ADD_DEV` fails `EACCES` (`ublks_max`, kernel 494, 2418). Until the reaper exists, three ways clear them, none of them free: `rmmod ublk_drv`, whose exit removes every device (`ublk_exit` → `ublk_remove`, kernel 3025-3031), but only on a `--modules` (`=m`) kernel, since the default `--builtin` (`=y`) kernel of 5.6, which item 1 recommends, has no module to unload; a `DEL_DEV` tool, for example ublksrv's `ublk del -n N` (unverified: general knowledge; whether Debian packages it is not checkable here, and nothing in this plan installs it); or a VM restart (`wsl --shutdown`), harmless between smoke runs, since each run formats a fresh pool in a fresh `$WORK` and unmounts its arena (linux-smoke.sh:50, 183-192, 75-77), but a power cut for any other running pool (item 13). Every smoke run that reaches its SIGKILL step leaves one such device (255-262) until Step 6's re-attach, and raising `ublks_max` (a parameter writable at run time, kernel 3043-3059) only postpones the limit. The prep script's row 19 (5.5) counts them against `ublks_max`, warns, names these ways out, and makes `--run-suites` skip its smoke step and its root-run ublk test files when fewer than two ids remain.

### 7.2 Traps for the implementer of the re-attach and the reaper

- **`START_DEV` on the serving thread never completes for a root daemon** (the code as it stands; one link unverified). `create_device` sends `START_DEV` through `UblkDevice::start` (otap-ublk device.rs:184-190) on the thread that serves the queue, the engine thread (otap-daemon device.rs:8-11, 36), and `UblkControlRing::execute` waits for it in a `submit_and_wait(1)` loop that retries `EINTR` (otap-sys ublk.rs:1248-1270). In the 6.12 driver: (1) the last `FETCH_REQ` counts the queue as privileged when its task has `CAP_SYS_ADMIN` (kernel/ublk_drv.c:1630-1631), so for a root daemon `GD_SUPPRESS_PART_SCAN` is not set (2268-2270) before `add_disk` (2281), which `START_DEV` runs holding `ub->mutex` after setting `LIVE` (2247, 2273, 2295); the command runs in an io-wq worker, since control commands answer `-EAGAIN` to the inline issue (2904-2905; the punt to io-wq is general io_uring knowledge). (2) A request the block layer sends reaches the server only as task work on the task that issued the fetches (`ublk_queue_rq` → `ublk_queue_cmd` → `io_uring_cmd_complete_in_task`, 1279-1280, 1198-1206; `ubq_daemon = current`, 1626): the engine thread, which sits in `execute` and does not reap the queue ring. (3) A privileged device's request never times out while its server lives (`ublk_timeout` re-arms, 1224-1225). (4) **Unverified** (general knowledge; block/genhd.c is not among the saved sources): `add_disk` scans the partition table synchronously, i.e. reads the new disk and waits. If so, `START_DEV` never completes. The smoke test's first `volume create` (linux-smoke.sh:200; 4.3 step 8) wedges the engine thread; `otapctl` gives up after its 600 s default (otap-ctl args.rs:25, 75); the EXIT trap's `daemon stop` waits on the engine thread for another 600 s (`DaemonHandle::call` has no timeout, daemon.rs:342-350); `kill -TERM` only sets the stop flag; `main` then blocks joining the engine thread (dbladed.rs:180-181), and the trap's untimed `wait` (linux-smoke.sh:73) never returns. A boot with an online volume hangs the same way inside `Pool::boot` (`ensure_device`, pool.rs:288-293; the smoke test's SIGTERM restart at 244), a device test that calls `dev.start()` before serving (6.2 gives the workaround), and 5.4 item 3's orphan daemon at its `volume create`. The fix keeps the fetches and the serving on the engine thread (R-L9) and moves only the wait: add the device's front door to the engine first (today `add_device` follows `create_device`, pool.rs:687-694), then wait for `START_DEV` off the engine thread while `wait_until` (pool.rs:523-556) keeps ticking the engine, either from a helper thread holding the `UblkDevice` (it is `Send`, 6.2) or a second control ring, or by pushing the command and polling its CQE from the tick (section 8, question 15). The recovery commands are not affected: `END_USER_RECOVERY` waits only for the fetches (2745-2749), not for I/O, and `START_USER_RECOVERY` does no I/O (2669-2736). Teardown has a corner case of the same kind: `STOP_DEV` on a `LIVE` device waits, holding `ub->mutex`, until no request is started (1597-1602, 1547-1556, 1532-1545), and `drop_device`'s drain waits only for the requests the front door took (`in_engine() == 0`, pool.rs:723-727), so a request the kernel delivers after the drain is ended only by the queue-ring teardown that `destroy_device` starts by dropping the front door first (otap-daemon device.rs:52-53): the cancel callback of a fetch still pending on that ring aborts it (`ublk_uring_cmd_cancel_fn` → `ublk_abort_requests` → `ublk_abort_queue`, 1464-1497, 1410-1440, 1387-1408; every fetch is marked cancelable, 1680). If every tag was consumed after the drain, no fetch is pending, nothing ends those requests, and `STOP_DEV` never returns on the engine thread (unverified link: that io_uring runs the cancel callback only for commands still in flight when the ring exits, general knowledge). The same remedy covers it: keep ticking the offline front door, which answers `-ENODEV`, until `STOP_DEV` returns, and drop the queue after it.
- **Order**: `START_USER_RECOVERY` before opening `/dev/ublkcN`; the fetches submitted before `END_USER_RECOVERY` (section 4.4 step 4; kernel 2719-2722, 2745-2749). `UblkDevice::create` (device.rs:88-125) does `ADD_DEV` (103-106), `SET_PARAMS` (118 → 127-164) and the open, mmap, 128 fetches and submit (119 → `open_queue`, 166-177), and stops there; `START_DEV` is `UblkDevice::start` (184-190), which otap-daemon's `create_device` calls separately, after `front_door` (otap-daemon/src/device.rs:26, 36). Recovery reuses only `open_queue`: no `ADD_DEV` or `SET_PARAMS`, `START_USER_RECOVERY` before the open, and `END_USER_RECOVERY` where creation has `START_DEV`.
- **Delete only after the front door is dropped**: `DEL_DEV` waits until the device number is freed, which for a created device happens only when the char device is released, i.e. after the last open file on `/dev/ublkcN` closes (kernel 2546, 2086-2092, 2094-2103; 6.2 has the chain). `destroy_device` gets this right (`drop(front)` at otap-daemon device.rs:52, then `device.delete()` at 53), but `create_device`'s `START_DEV`-failure path does not: it calls `device.delete()` (36-37) while `front` (26), which owns `LinuxTransport` → `UblkQueue` → `UblkChar`, the open `/dev/ublkcN`, is still alive until the function returns, so that `DEL_DEV` cannot complete and the engine thread blocks in `execute`, which retries `EINTR` (ublk.rs:1248-1270; 6.2 on why only `SIGKILL` ends it). The front-door failure path (28-29) is safe: `front_door` fails only when the queue was already taken (otap-ublk device.rs:349-351), so no `/dev/ublkcN` is open. Fix: `drop(front)` before that `delete()`. A `recover_device` (5.1) with any fallible step after `front_door` must drop the front door before deleting for the same reason; in 5.1's design `END_USER_RECOVERY` runs inside `UblkDevice::recover`, before `front_door`, where a failure deletes through `delete_inner`, which drops the queue first (otap-ublk device.rs:203-208).
- **Depth must be the device's**: `END` completes only when `nr_io_ready == q_depth` (kernel 1499-1502, 1621-1636); a `DeviceSpec::new` depth that differs from `info.queue_depth` makes `END` block until a signal (`-EINTR`) and `UblkQueue::new`'s mmap size wrong (`-EINVAL`, kernel 1351-1352). Read the depth from `GET_DEV_INFO`.
- **`EBUSY` is transient**: `GET_DEV_INFO` shows `LIVE` with a dead pid until `quiesce_work` ran — moments after the kill when a fetch was pending, up to the request timeout (blk-mq's default 30 s; unverified: general knowledge) when the dead daemon held every tag (4.4 step 1) — and `UB_STATE_OPEN` stays set until the dead process's io_uring teardown released the file (section 4.4 steps 1-3); retry `START` with a deadline (the `LIVE` wait needs one longer than the request timeout, 5.1). The smoke test's `sleep 1` (258) hides this today; remove it (5.4 item 1).
- **Rings**: control commands need an SQE128 ring (ublk.rs:1046-1048, 1184-1197; kernel 2909-2910); the queue ring is SQE64 (1337); `UblkControlRing` is per device (device.rs:89) and private — the reaper needs its own (5.1).
- **Pids**: `ublksrv_pid` is `i32` (ublk.rs:456-457), `-1` after a stop (kernel 1611), `0` for a never-started device; `std::process::id()` is `u32`. Pid reuse makes "pid alive" alone unsafe; combine with the `ublksrv_flags` tag.
- **A `DEAD` device with our tag** (a crash between `ADD_DEV` and `START_DEV`) cannot be recovered; delete it. Mind the errno: only a crash before the fetches were submitted gives `-EINVAL` (`nr_queues_ready == 0`, kernel 2704-2705); after them (the usual case: `open_queue` submits every fetch inside `create`, otap-ublk device.rs:117-123, 166-177, before `start()`, otap-daemon device.rs:36-42) the queue counts as ready (`ublk_mark_io_ready` from the `FETCH_REQ` arm, 1734-1762, 1621-1636), the state stays `DEAD` (1564-1565), and `START_USER_RECOVERY` answers `-EBUSY` (2719-2722), indistinguishable from the transient window by errno. Decide by `GET_DEV_INFO`'s `state`, never by the errno (5.1).
- **Ids are reused at once** after `DEL_DEV` (kernel 2546-2548, 2075): reaping then creating gives the same `/dev/ublkbN` for a different volume; never cache a path across a reap.
- **`ensure_device` is called from six places** (pool.rs:289, 876, 902, 931, 1098, 1111); only the boot-time call may consult the quiesced-device table; the others must create.
- **The device must be re-attached even under nvfail** (heap-arena crash): the block layer's requeued requests wait for a server (kernel 1090-1098, 2765-2768); without a re-attach they hang until the device is reaped. The front door answers `-EIO` while nvfail holds (frontdoor.rs:200) and `ok` after `nvfail-clear`.
- **`Pool::devices` holds paths** (129-141); `device_path` (311-313) and `volume_report_for` (628-642) must show the recovered path, else `otapctl volume show` prints `-` (render.rs:79) and `--json volume show` carries `"device": null` (protocol.rs:240-241), so the smoke test's `wait_device` polls 100 x 0.1 s (linux-smoke.sh:170-177) and then dies "volume smoke has no block device" (178); the failed command substitution in `BLK="$(wait_device smoke)"` ends the run under `set -e` (22) through the EXIT trap, about 10 s after the restart. A recovered path that is not recorded is therefore a FAILED run at the first `wait_device` after the restart (273 in the hugetlbfs branch, and 5.4 item 1's new call in both branches), not a hang.
- **`HugeArena::map_file`'s `flock`** fails `WouldBlock` while the old process still holds the file (hugetlb.rs:346-355): the restart must happen after the old process is reaped (`wait`, linux-smoke.sh:256). The lock goes with the dead process's open file description and its mapping, which the kernel tears down before the process becomes reapable (unverified: general knowledge of the exit path; the arena file has no io_uring reference), so after `wait` the arena is free. **`UB_STATE_OPEN` is not tied to `wait`**: the kernel releases `/dev/ublkcX`'s file struct once the dead process's io_uring ctx is freed (2707-2711), which is not shown to happen before `wait` returns (4.4 step 3) — that is the window the bounded `START_USER_RECOVERY` retry exists for (5.1), and why "the old process was reaped" is a necessary, not a sufficient, condition for the re-attach.
- **`SET_PARAMS` must not be reissued** on a recovered device, and the driver will not stop you: `-EACCES` is answered only while `LIVE` (kernel 2651-2654; ublk.rs:774-775), a `QUIESCED` device accepts and stores new params, but the block layer's limits were applied once at `START_DEV` (2190-2260) and `END_USER_RECOVERY` (2738-2774) never re-applies them, so the reissue is accepted and ineffective. The recovered device keeps its `max_io_buf_bytes` (the driver rounds it to a page, kernel 2141-2148, 2466) and `dev_sectors`; compare with the volume's size and the arena cap (device.rs:55-66) and refuse a mismatch instead of serving a device the engine will answer `EINVAL` to.
- **`open_block`'s sysfs name is `file_name()`** (backstore.rs:312-315): `/dev/disk/by-id/...`, `/dev/mapper/...` and partitions (`/dev/sda1` lives under `/sys/block/sda/sda1`) fail with "sysfs attribute size is missing"; `/dev/loopN` from `losetup --show` is fine. `readlink -f` plus `/sys/class/block/<name>` would fix all three.
- **Error text**: `UblkControlRing::execute` turns `-ENOTSUPP` (524) into "Unknown error 524" (ublk.rs:1272-1275); `feature_name` of a combined mask is `None` (300-301).
- **The planner's own flush default is dead code under the daemon**: `geom_overrides()` always passes `flush_policy: Some(...)` (config.rs:54), so `TrustBarrierWithNvfail` applies to every device unless `--strict-flush`; a loop device is therefore "trusted" too. Not a Step 6 item, but the first run's log will show `TrustBarrierWithNvfail` on a loop device and someone will ask.

### 7.3 Traps in the script and its surroundings

- The hugetlbfs branch's `grep -q "arena re-attached"` (271) is **also true after the clean SIGTERM restart**: the arena file persists under `$ARENA_FILE` and `Arena::attach` succeeds on every boot (engine.rs:1687-1689, 1991), so the clean restart's line is "clean boot at cp N, arena re-attached (0 blocks replayed)". Only the `pattern2` compare (274-275) proves the crash path; keep it as **the** assertion. A check that `replayed` is non-zero after the kill (`grep -E "arena re-attached \([1-9][0-9]* blocks replayed\)"`) would be unsound: a consistency point commits every placed slot (engine.rs:5872-5882 → `arena.commit`), `Arena::attach` replays only `Placed` slots (arena lib.rs:32-43, 59-66, 512-514), and the `FLUSH` behind `conv=fsync` does not force a CP (`RequestKind::Flush` answers `Status::Ok` at once, engine.rs:3481-3484), so the count after the kill is "blocks placed since the last timer CP". That count is fixed at the moment of the kill, and nothing the script does after the kill can change it: `sleep 1` (258) runs after `kill -KILL` and `wait` (255-256), when the daemon is dead and no CP can run, so neither it nor a `--kill-settle` in its place changes what the next boot replays; before the kill, only the CP interval and the size of the write shift its odds (end of this bullet). What decides the count is which CP committed before the kill, cut by `maybe_cut` (engine.rs:3874-3915) against the I/O the script issued: of its causes only `Timer` can fire here (3903-3904: `active_blocks > 0` and `cp_timer_ns` since `last_cut_ns`, which is set at engine construction (2065) and at each cut (3915) and not by the Boot CP (1713, a job without a cut)); `ArenaHalf` (3901-3902) needs `cfg.arena_half` = 0.5 (159, 184) of the 256 MiB arena, `BackToBack` (3905-3906) needs `back_to_back_bytes` = 1 GiB of unflushed data (traits.rs:192, 208), neither reachable by a 16 MiB write, and `Request` (3899-3900, which also needs the engine serving and idle) needs `cp_requested`, which only `Engine::request_cp` (engine.rs:2122-2125) and a deferred write (3375-3379: a write the arena cannot take yet) set. The daemon reaches `request_cp` in two ways. Directly: through `Pool::sync_now` (pool.rs:592-596) for `pool sync` (otap-ctl args.rs:38, 282; `Pool::sync`, pool.rs:824-827), `volume online`/`offline` (901, 908), `volume rename` (942), `snapshot rollback` (1092, 1097, 1110) and `snapshot replication-base` (1155), and through `request_clean` (engine.rs:2129-2132) for `pool clean` (pool.rs:832). And through the engine's own lifecycle methods, which call it themselves: `create_volume` (engine.rs:2291; `volume create` reaches it through `create_named_volume`, 2737, called at pool.rs:870), `nvfail_clear` (2265, skipped when the volume is not held or is already clearing, 2257-2262; pool.rs:953), `delete_snapshot` (2484; `snapshot delete` through `delete_snapshot_by_id`, pool.rs:1002, 1007, and a rollback's deletion of the newer snapshots, 1071), `set_snapshot_pins` (2515; `snapshot pin` and `unpin`, pool.rs:1139), `set_volume_online` (2578, only when the state changes, 2574-2576; pool.rs:899, 905, 1086, 1096 and 1108, each followed by a `sync_now` as well) and `set_volume_name` (2755; pool.rs:940); and `request_fold` (2224-2233, which calls `request_cp` at 2232 unless a damaged map page refuses the fold, 2225-2230), called from `create_snapshot_named` (2403; `snapshot create` through `create_named_snapshot`, 2323, pool.rs:967), `rollback_volume` (2659; pool.rs:1094), `resize_volume` (2689; pool.rs:923) and `delete_volume` (2713; pool.rs:883). So, once accepted and barring those three skips, every control request that changes the catalogue or a volume's state sets `cp_requested`: volume create, delete, online, offline, resize, rename and nvfail-clear; snapshot create, delete, pin, unpin, rollback and replication-base; pool sync and pool clean (`Pool::handle`, pool.rs:744-809). The third skip reaches two of these requests: while a map page is damaged, `request_fold` returns before `request_cp` and the request is still accepted (`resize_volume` and `delete_volume` set `v.op` and return `Ok`, engine.rs:2686-2690 and 2710-2714), and their `Pool` paths call no `sync_now` (`volume_resize` 915-934, `volume_delete` 881-890), so volume resize and volume delete then leave `cp_requested` unset. A snapshot create is refused instead, before its `request_fold` (`create_snapshot_named` returns `MapDamaged`, engine.rs:2370-2372), and a rollback still sets `cp_requested` through the `sync_now` at pool.rs:1092, which runs before `rollback_volume` (1094); the one at 1110 is not reached, since no fold runs while a map page is damaged (`should_fold`, engine.rs:4655-4657), a CP carries a volume operation only when it folds (4797), and so the `VolumeRolledBack` that 1102-1105 waits for never comes. Of the rest, the reports (`pool status`, `volume list` and `show`, `snapshot list`) never set it, and the io group (write, read and punch; there is no `io sync` command, otap-ctl args.rs:60-62, 373-441) only when a write or a punch is deferred (engine.rs:3364-3379; only those are handed back: a write at the stall occupancy, 3448-3449, or when the arena is full, `serve_write` 3497, and a punch when it is full, `serve_punch` 3565), since its requests enter the engine through the front door like any other I/O (`Pool::io`, pool.rs:1164-1169). This section issues none of the setters: between the SIGTERM restart (244) and the kill (255) the script sends only `daemon ping` (`start_daemon`'s loop, 147-153), `pool status` (245) and `volume show` (`wait_device` → `volume_device`, 246, 160), and a 16 MiB write into a 256 MiB arena defers nothing, so no `Request` cut falls in it. So the count is the phase of the 2 s timer relative to the `dd` at 253 (and the `dd`'s own duration, during which a cut commits only what was placed so far): anything from `0` to all 4096 blocks is the correct answer of a correct system, and no setting of the script shifts it except `--cp-interval` (145) and the size of the write. Log the count (`grep -o 'arena re-attached ([0-9]* blocks replayed)' "$LOG"`) and never assert on it; a kill that lands mid-write (5.4 item 4) makes a non-zero count likely, and even then it is a statistic, not a check.
- `grep -q "last boot:    clean boot"` (245) matches the same prefix; fine. The exact spacing comes from render.rs:208 and 77: any change there breaks the script silently.
- `wait_device` after the rollback (229) exists because the rollback recreates the device. The id is usually the same already today, not only after Step 6 (`drop_device`'s `DEL_DEV` returns once the id is free, kernel 2546, and `ADD_DEV` takes the lowest free id, 2075; 7.2, "Ids are reused at once"), but a lower id freed in between, or another process's `ADD_DEV`, can change it, so the script must keep re-reading.
- The EXIT trap's `wait "$DBLADED_PID"` (73) has no timeout; a wedged daemon hangs the script after a failure (7.2's `START_DEV` hang is one way to wedge it: the engine thread never returns, so neither `daemon stop` nor `SIGTERM` ends the process). `wait` is a shell builtin, so `timeout` cannot wrap it: poll `kill -0 "$DBLADED_PID"` against a deadline, then `kill -KILL` and poll again before a final `wait` (whether a daemon stuck in `START_DEV` dies at once on `SIGKILL` is not checkable here: its io-wq worker waits inside `add_disk`), report a daemon that outlives the deadline instead of hanging, and give the trap's `otapctl daemon stop` (69) a short `--timeout` instead of the 600 s default (otap-ctl args.rs:25, 75).
- `losetup --direct-io=on` fallback (116) is silent; print which happened.
- `numfmt --from=iec` accepts `256M` (131); `--arena 256MiB` does not (`iec-i` would) — document or accept both.
- `fio --ioengine=libaio` needs fio built with libaio (Debian's is; unverified).
- The script runs `cargo build` from `$ROOT` as root (107): see 7.1 item 11.
- The README's manual sequence (142-155) starts `dbladed` without `--device` (146) and runs `pool boot` **without** `--arena-file` or `--heap-arena` (148): the arena kind is then chosen by the **client**, not the daemon — `otapctl pool boot` builds the request with `(false, None) => ArenaKind::default_for_host()` (otap-ctl args.rs:259-266), which is `Hugetlb { path: DEFAULT_HUGETLB_PATH }` on Linux (units.rs:28-36, 22: `/run/opentap/arena/dbladed`), and the daemon takes the request's `arena` verbatim (daemon.rs:186). `dbladed`'s own default arena — `DaemonConfig::default()` at dbladed.rs:57, whose `arena` is `ArenaKind::default_for_host()` (config.rs:92; units.rs:28-36, the path at 22), kept by `parse` unless `--heap-arena` or `--arena-file` is given (128-132; USAGE documents it at 28-29) — only matters for a pool booted at start with `--device`. Either way the default path is why the README mounts hugetlbfs there first (143-144); on a VM restart the mount is gone.
